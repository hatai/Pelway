# Investigate Bug

バグやインシデントの報告が来たとき、修正へ直行せず、まず理解するための手順。調査は
「報告の読み取り → 修正済みでないかの確認 → 証拠集め → 根本原因 → 最小の修正案の報告」の
順で進め、修正案を報告した時点で止まる。`write-issue`・`implement-issue` と対になる。

## 決まり（毎回守る）

- 調査は修正案の提示まで。修正やリファクタリングのコードは書かない。実装は `write-issue` で
  起票して `implement-issue` に渡す（下の「引き渡し」）。
- 本番・共有環境（本番・ステージングのサーバーと DB、共有の検証環境、他のメンバーの
  ワークスペースとデータ）は**読み取り専用**。読むだけで、書き込み・再起動・再デプロイ・
  データの変更や削除はしない。証拠は読み取りのクエリとログで集める。
- 報告に不足があれば推測せず、報告者に聞く。Issue で報告されたなら `needs-info` ラベルを付ける。
- 秘密（トークン、鍵、ユーザーの非公開内容）は調査記録・コミット・Issue に貼らない。
  原因を証明するのに必要な最小の引用だけを残す。
- GitHub への操作は `scripts/agent-gh dev ...` で行う（素の `gh` を使わない）。
- 再現できない・確定できない原因を「見つけた原因」として報告しない。そのまま「未確定」と
  報告し、試したことと証拠を列挙する。
- 根拠・事例を書くときは、一次記録（ログの行、読み取ったデータ、キャプチャ、Issue・PR の
  コメント）からの引用を付ける。引用で裏付けられない内容は「想定」と明記する。

## 手順

### 1. 報告を読む

報告（Issue、部屋のメッセージ、ユーザーからの連絡）から、次を 1 行ずつ書き出す。

- 期待: 何を期待したか
- 実際: 何が起きたか
- 対象: だれの・何の話か（ユーザー、ワークスペース、対象のデータ）
- 場所: どこで（画面、API、コマンド、環境）
- 時刻: いつ（日付と時刻、タイムゾーン）
- 頻度: どのくらいの頻度（1 回だけ、常に、特定の操作のたび、あるリリース以降）

報告に無いものは推測で埋めず、この時点で報告者に聞く。スクリーンショットやログの
添付があれば先に受け取っておく。

### 2. 修正済みでないかを確認する

掘り始める前に、既知または修正済みでないかを確かめる。

```bash
git log -i --grep="<キーワード>"
git log -S"<シンボル>" -- <path>
scripts/agent-gh dev pr list --state all --search "<キーワード>" --json number,title,state
scripts/agent-gh dev issue list --state all --search "<キーワード>" --json number,title,state
ls docs/worklogs/bugs
```

- 過去の調査（`docs/worklogs/bugs/`）にも同じ症状が無いか探す。
- 修正が見つかったら、それが報告された場所に届いているかを確かめる（コミットは main に
  入っているか、リリースやデプロイに含まれているか）。
  - 未配備: 答えは「<PR> で修正済み、<環境> に未配備」。そこで止まる。
  - 配備済みで再発: 回帰か不完全な修正。修正された行の `git log` を辿り、旧修正とその
    試験から調査を始める。
- 対応中の PR や Issue があれば、二重に始めず、そちらを報告する。

### 3. 証拠を集める（本番・共有環境は読み取り専用）

- 報告時刻の前後のエラーとログ。DB の行は読み取りのクエリだけで取る。
- その日付の前後にその領域へ入った変更: `git log --since=... -- <path>` とマージされた PR。
- 再現は手元の環境だけで行う: `mise run verify`、対象クレートの `cargo test <名前>`、
  または失敗する試験を書く。再現できたら、再現手順をそのまま残す。再現できないときは
  試したことと結果を列挙し、証拠からの調査を続ける。推測で原因をでっち上げない。

### 4. 根本原因を突き止める

- 症状から、誤っている行（`file:line`）までコードの経路を逆向きにたどる。
- 原因は報告の**すべての**症状を説明しなければならない。1 つでも説明が残る症状があれば、
  掘り続ける。
- トリガー（ユーザーが何をしたか）と原因（コードの何が悪いか）を分けて書く。
- 同じ欠陥が他の場所に無いか: 見つけたら列挙する（直さない）。
- 原因が脆弱性の疑いだったら、その時点で調査の通常の流れ（報告の保存と起票）を止める:
  - その調査の報告ファイル（`docs/worklogs/bugs/<slug>/report.md`）を作らない。途中まで作った場合も、コミットも push もしない
  - 公開の場（Issue・PR・調査記録）に攻撃に使える詳細を書かず、概要だけを T3 スレッドの返答で人間に報告し、報告の対象の Issue に `needs-human` ラベルを付けて判断を仰ぐ
  - 証拠や修正案の保管場所は人間が決める。調査側で決めない

### 5. 報告して止まる

ここで止まり、次を報告する。

- 症状: 1 文。
- 修正済みか: 見つけた旧修正と配備状況、または「該当なし」。
- 再現: 再現手順、または「再現できず」と試したこと。
- 根本原因: `file:line` と理由、根拠（ログの行、読み取ったデータ、キャプチャ）。
- 修正案: 原因を取り除く最小の修正の内容。大きなリファクタリングが必要なら 1 行で触れる
  だけ（修正に畳み込まない）。
- 未解決の問い。
- 使ったスキル: この調査で使った skill 名を列挙する。輸入スキルは `.agents/skills/<name>` の
  パスで書く。無ければ「なし」。

同じ内容を `docs/worklogs/bugs/<slug>/report.md` に保存する（`<slug>` は症状の短い
英小文字とハイフン。ログの断片やキャプチャは同じディレクトリに置く）。保存したら、
報告ファイルだけを含む Draft PR を出す（skill `write-pull-request`。証拠のファイルは
PR に含めない。報告には必要な最小の引用を書く。ブランチは `agent/investigate-<slug>`、
本文の `Implementer:` の行には指示の 2 行目 `Assigned: role=investigate ...` の値を
`role=investigate` を除いて写す）。追い調査では同じブランチに積んで push する
（Draft PR が更新される）。スレッドの返答には、上の報告に `pr: <報告の PR 番号>` の行を
添える。脆弱性の疑いで止めた調査では、この PR を出さない。

## 輸入スキル（mattpocock/skills）

指揮役が試行として明示した割り当てでは、証拠集めと根本原因の方法として輸入スキル
`diagnosing-bugs`（`.agents/skills/diagnosing-bugs/SKILL.md`）を読んで使う。試行と明示
されていない割り当てでは使わない（通常運用への移行は hatai が別に判断する）。

読み替え:

- Phase 1〜Phase 4 を採用する。Phase 4 の計装は手元の環境に限る（本番・共有環境は
  読み取り専用のまま）。
- Phase 5（修正と回帰テスト）は含めない。調査は修正案の提示まで。
- Phase 6 は計装と一時成果物の後片付けだけとし、修正の成功確認は含めない。
- 再現ループを作れない場合は上流の厳格な規則（ループ無しでは仮説へ進まない）に従わず、
  試した内容と証拠と未確定事項を報告する。
- 必須の情報が不足する場合は、質問と `needs-info` ラベルを残し、進められる調査と
  回答待ちの作業を区別する。
- HITL 用テンプレート（`scripts/hitl-loop.template.sh`）と同梱スクリプトは使わない。

取り込みの discipline（輸入スキル全般）:

- 同梱のスクリプト（`scripts/` など）は実行しない。
- `agents/` のメタデータ（`openai.yaml` など）は使わない。
- 採用していないスキルへの参照は無効とする。
- 輸入品の本文と正本（AGENTS.md・docs/・この skill）や適用ルールが衝突した場合は、
  正本と適用ルールが優先する。
- 輸入スキルは名前の解決に任せず、上に示した repo 内の明示したパスで読む。人間側の
  同名のユーザーレベル版は読まない。

試行の割り当てでは、最初の報告に、起動時のリポジトリの版（`git rev-parse HEAD`）、
実際に読んだ解決先のパス（`.agents/skills/<name>/SKILL.md`）、補助文書の可読性を記録する。

## 引き渡し（実装は別工程）

- 調査は手順 5 まで。修正のコードは書かない。同じ欠陥の列挙も直さず報告に残す。
- 修正を進めるときは、報告と調査結果を `write-issue` の形にまとめて Issue を起票する。
  「関連情報」に `docs/worklogs/bugs/<slug>/report.md` へのリンクを置き、受け入れ条件には
  再現試験を含める。実装は `implement-issue` がその Issue を担う。
- 調査の結果「直す必要がない」（仕様どおり、誤報告など）と分かったら、そう報告して
  Issue は立てない。
