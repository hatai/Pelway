# Improve Skills

作業ログ（worklog）などの一次記録を根拠に、AI 開発チームの自前スキルを改善・作成・最適化する作業の手順。

command-team 手順 4（改善ループ）が、レビューの同種指摘などをきっかけとする改善の判断と、変更後の効果測定を担い、このスキルは「スキル改訂の作業そのものをどう進めるか」を担う。候補の出どころは、改善ループのほか、キュレーション（作業ログの定期走査）や、人間・指揮役からの直接の依頼もある。

既存手順との接続は次のとおり:

- command-team 手順 4 は、スキル改訂の候補をこのスキルの入口Aに渡す（手順 4 の「共有層への反映」は、編集作業そのものはこのスキルに委ねる）。
- スキル改訂の Issue の実装では、implement-issue の手順に加えて、このスキルの入口B以降の手順を読む。
- 裏取りと効果測定の決まりは command-team 手順 4 が正本であり、このスキルでは繰り返さない。

入口は2つあり、成果物が違う:

- 入口A（候補の調査と起票）: 改善ループやキュレーションで挙がった候補を調べ、Issue を立てるところまで。成果物は Issue 本文であり、候補・根拠（一次記録の引用）・対象スキルは Issue 本文に保存する（Issue 本文が正本）。着手は通常の流れの合図を待つ。
- 入口B（承認済み Issue の実装）: 割り当てられた Issue の実装として改訂作業を行う。成果物は PR。実装の進め方自体は implement-issue に従い、このスキルはスキル改訂の作業の進め方を定める。

どちらの入口でも、効果測定そのものは command-team 手順 4 の担当として残り、このスキルは測定に渡すところまでを行う。

## 使うとき

- レビューの同種の指摘や手戻りが繰り返され、原因がスキルの不足だと判断された候補を直すとき
- スキルが無いまま繰り返されている作業を、新しいスキルにするとき
- スキルが肥大した、他のスキルや AGENTS.md と重なった、実態とずれた記述が残った、という棚卸しをするとき
- 指揮役または人間から、特定のスキルの改訂を頼まれたとき

## 対象と対象外

- 対象は自前（local-managed）スキル: `.agents/skills/` のうち `skills-lock.json` の `skills` に登録されていないもの。欠陥の所在がスキルとは限らないので、AGENTS.md と docs/ も直す先に含める。
- `skills-lock.json` で管理される外部スキル（actionbook/rust-skills、penpot、mattpocock 等）は、本体を編集しない。外部スキルで不足が見つかったら、適用ルールを自前スキルや AGENTS.md に書くか、上流への還元候補として作業ログに記録する。
- `.claude/skills/<name>` は `.agents/skills/<name>` へのシンボリックリンクであり、実体は `.agents/skills/` 側だけを直す。新規スキルを作るときは、リンクも同じ変更で作る。

## 決まり（毎回守る）

- 根拠の無い書き換えをしない。変更の1つ1つに、一次記録（作業ログ、レビュー本文、セッション記録）への引用を対応づける。引用で裏付けられないものは変更に混ぜず、「想定」として分けて書く。
- 変更は小さく分ける。1 つの PR は 1 つのスキル（または 1 つのテーマ）まで。無関係な変更を同じ PR に混ぜない。
- スキルには時系列・経緯を書かない（AGENTS.md の決まり）。根拠と経緯は PR 本文と作業ログに残し、スキルには事実と手順だけを書く。
- 直したら終わりにしない。期待する変化（どの種類の指摘・手戻りが減るはずか）を PR 本文に書き、効果測定（command-team 手順 4）に渡せる形にする。

## 手順

### 1. 候補を切り分ける

- 材料は command-team 手順 4 の材料表の場所から集める（実装者メモ、セッション記録、レビュー本文、指揮役の作業ログ）。
- 材料の裏取りは command-team 手順 4 の決まりに従う（実装者メモは自己申告として扱い、成果物とセッション記録を優先する、等）。
- 候補を3つに分ける: 改善（既存スキルの不足）、作成（スキル化すべき繰り返し作業）、最適化（肥大・重複・陳腐化）。対象のスキルと、直す先が AGENTS.md や docs/ でないかもこの段で決める。

### 2. 起票して、着手の合図を得る（入口A）

- 候補の整理が済んだら、write-issue の手順で Issue を立てる。書く内容の置き場所は write-issue の本文構成に従う: 対象スキル・変更の種類（改善／作成／最適化）・根拠の一次記録は背景・前提と関連情報に、期待する変化は目的に書き、受け入れ条件には検証できる到達状態だけを書く。
- タイトルは「スキル改訂: <対象スキル> に<何をどう変えるか>」の形にする（例: 「スキル改訂: implement-issue に積み上げ PR の pr-size 計測を明記する」）。先頭の「スキル改訂:」は、指揮役が割り当てのときにスキル改訂の Issue を見分ける目印になる（command-team の割り当て指示の 1 行目がこれで変わる）。対象が AGENTS.md や docs/ の場合も <対象スキル> の位置にそのファイル名を書く。
- 受け入れ条件は、write-issue の「受け入れ条件の書き方」に従い、確かめ方を 2 種類に分けて書く。スキル改訂の条件の多くは文の意味についての条件なので、確かめ方を「目視で確認」だけにすると、何を見れば満たしたことになるかが実装担当にもレビュー担当にも決まらない。
  - 構造の条件（symlink の一致、参照先の実在、行数、既存テストの合格）: コマンドで書く（例: `→ diff -r .claude/skills/<name> .agents/skills/<name> が空`、`→ wc -l が 330 未満`、`→ mise run script-test が pass`）。
  - 内容の条件（ある決まりや手順が書かれていること）: 確認の手順で書く。どの節に、どの内容が書かれていれば満たすかを条件の文に含め、確かめ方は「PR 本文の根拠の対応表で、該当箇所を引用して示す」にする（例: `- 手順 6 に、積み上げ PR では --base <親ブランチ> で測ることが書かれている → PR 本文の対応表で手順 6 の該当文を引用`）。レビュー担当は、引用が条件の文を満たすかを読んで判定する。
  - 内容の条件を、文言の grep で合否を出すテストに置き換えない。文の意味の判定はキーワードでは決まらない（AGENTS.md の「LLM judges」）。
- 着手は通常の流れの合図を待つ（`ready-for-agent` とボードの Todo）。このスキルは、候補の調査から起票までを認めるもので、着手までを認めるものではない。入口A の作業は起票で終わる。
- 既に Issue が割り当てられている場合（入口B）はこの段を飛ばし、その Issue の実装として手順 3 以降を行う。

手順 3・4・5 は、手順 1 の分類に対応する節を実行してから手順 6 へ進む（全部を連続して行うものではない）。分類が重なる場合（陳腐化した記述の棚卸し、重複の解消が矛盾の解消でもある場合など）は、主たる変更の節を主とし、関係する節の決まりも併せて適用する。

### 3. 改善する

欠陥の種類を特定してから直す。

- 手順の欠落: 起きている作業に手順が無い → 手順を足す。具体例と禁止事項も一緒に書く。
- 文言が効いていない: あるモデルでは守られるのに別のモデルでは守られない → 抽象的な原則の言い換えで済ませず、手順・具体例・禁止事項の形に書き直す（command-team 手順 4 の「共有スキルとして未達」の扱い）。
- 前提の陳腐化: ツール・手順・体制が変わったのに記述が古い → 実態に合わせて直すか、消す。
- 矛盾: 他のスキルや AGENTS.md と食い違う → まず既存の正本指定（スキル内や AGENTS.md で正本と明記されている指定）を確認してそれに従う。文書とコード（実装）が食い違う場合は、コードを優先し、文書をコードに合わせて直す（AGENTS.md の Code over docs）。正本指定が無い場合は、承認済み Issue の範囲内で文言・構成の整理として決められるものに限り、どちらを正本にするかを決めて明記してから片方に寄せる。運用・役割・権限の変更になるものは自分で決めず、implement-issue の停止条件に従って止まり、判断を仰ぐ。

### 4. 作成する

- 繰り返しの証拠を確認する: 同じ種類の作業が複数回起きていて、そのたびに判断や手順の組み立てが発生していること。1 回だけの作業はスキルにしない。
- 既存の全スキル（外部スキルを含む）と重なりを調べる。似た自前スキルがある場合は、新規作成ではなく改善として扱う。似たスキルが外部スキルの場合は、次の基準で行き先を決める:
  - 不足が「このチームでの適用の仕方」にある → 適用ルールを自前スキルか AGENTS.md に書く（改善として扱う）。
  - 必要な手順が外部スキルの守備範囲と別の仕事になっている → 自前スキルを新規に作る（この手順で作成する）。
  - 不足が外部スキル自体の内容にある → 本体は直さず、上流への還元候補として作業ログに記録する。当面の手当が要る場合は、適用ルールの追加を併せて行う。
- 名前は動詞中心の短い英語にし、frontmatter の description に「いつ使うか」と検索用のキーワードを書く（既存スキルの形式に合わせる）。
- 最小の構成で書く: 使うとき、決まり、手順、やってはいけないこと。検証できる段取りがある部分は、ヘルパー（実行ファイル＋テスト）の同梱を検討する（自前スキルのみ。docs/agents/skill-helpers.md の決まりに従う）。

### 5. 最適化する

- 重複: 同じ決まりが AGENTS.md・複数のスキルに書かれていたら、既存の正本指定を確認してそれに従い、他は参照に寄せる。指定が無く、どちらを正本にするかが運用・役割・権限に触れる場合は、手順 3（改善する）の矛盾の扱いと同じく、自分で決めずに判断を仰ぐ。
- 死んだ記述: 対象のツール・手順・体制がもう無いのに残っている記述は消す。
- 肥大: 常時必要な判断と手順はスキル本文に残す。読む条件が限られる詳細（特定の場合だけ必要になるもの）は、その条件を明記したうえで参照先（docs/ 側の文書など）へ移し、スキルからは条件つきで参照する。条件なしに毎回必要な内容は移さない。
- 文言の移動・言い換え・削除をするときは、その文言を grep で固定している既存のテスト（`scripts/tests/*-docs.test.sh` など、冒頭に「文言を変えるときはこのテストと同じ PR で直す」とあるもの）を探し、同じ PR で参照先と文言を直す。探し方は、移す・変える文の特徴的な語句で `grep -rnF '<語句>' scripts/tests/` を実行する。テストを消して通すのではなく、正本の新しい置き場所を確かめる形に向け直す。
- 統合と廃止: 役割が重なったスキルは統合を、使われなくなったスキルは廃止を、それぞれ候補として挙げる。実行は人間の判断を経てからにする。

### 6. 検証する

- `diff -r .claude/skills/<name> .agents/skills/<name>` の差分がゼロであること。
- ヘルパーを足した・直した場合は、そのテストが通ること（`mise run script-test`）。テストは `scripts/script-test.sh` が `scripts/tests/*.test.sh` と `.agents/skills/<name>/*.test.sh` を自動収集するため、置くだけで検証対象になる。
- pr-size の計測は base 側の `.gitattributes` で判定されるため、同じ PR で `.gitattributes` の除外解除を書いても、その PR の計測には効かない。ヘルパーとテストは計測対象にすることが決まり（docs/agents/skill-helpers.md）なので、計測対象でないスキルにヘルパーを足す場合は、除外解除だけを先行する別の PR でマージしてから、ヘルパーの PR を出す。除外解除なしにヘルパーを足さない。
- 参照しているファイル・スキル・コマンドが実在すること。改訂したスキル名でリポジトリ内を検索し、古い前提の参照が残っていないこと。
- 他のスキルや AGENTS.md と矛盾する記述が無いこと（該当箇所を検索して読み比べる）。
- 変えた文言を固定している既存テストが残っていないこと（手順 5 の探し方で `scripts/tests/` を検索し、見つかったものは同じ PR で直したうえで `mise run script-test` が通る）。手順 5 以外の改訂でも、既存の文言を変えたなら同じく調べる。
- 変更行数が pr-size の数え方に収まること。収まらない場合は独断で分割せず、分割案を提示して停止し、指揮役の承認を受ける（implement-issue の停止条件と command-team の分割承認の手順に従う）。

### 7. 出して、記録する

- 変更は通常の流れに乗せる: Issue は write-issue、PR は write-pull-request と implement-issue の手順に従う。このスキル自体はマージしない。
- PR 本文に根拠の対応表を書く: 変更ごとに、根拠の一次記録、変更の内容、期待する変化（手順の「決まり」参照）。
- 引き渡しの記録は PR を出す時点で行う: 実装者メモに、候補の出どころの作業ログへの参照・対象の改善点・期待する変化を残す（実装担当はマージまで待機しない）。implement-issue の実装者メモ（5 項目と「使ったスキル」）とは別の記録で、5〜10 行の上限にも数えない。同じ round の「使ったスキル」の行の後に、次の見出しで足す。この記録が、指揮役が効果測定（command-team 手順 4）で引き継ぐ材料になる。

  ```markdown
  ### improve-skills 手順 7 の引き渡し記録

  - 候補の出どころ: <作業ログのパスと節（例: `docs/worklogs/issue-<N>.md` round 1「改善案」）。複数あれば全部>
  - 対象の改善点: <対象スキルと、直した不足の種類（手順の欠落／文言が効いていない／前提の陳腐化／矛盾／重複／肥大）>
  - 期待する変化: <どの種類の指摘・手戻りが、どの担当で減るはずか>
  ```

  変更が複数あるときは、上の 3 行の代わりに PR 本文と同じ「変更 ↔ 根拠 ↔ 期待する変化」の表を置いてよい。
- 「反映済み」の印付けと効果測定への引き継ぎは、指揮役がマージの時点で行う（印を付ける対象は、その候補を出した作業ログの改善点の表）。「見送り」の決定は指揮役または人間が行い、作業した側は提案までとする。候補の出どころに改善点の表が無い場合は、PR 本文と実装者メモへの記録で代える。

## やってはいけない

- 外部スキルの本体や skills-lock.json を手で書き換えること。
- 根拠を確かめずにスキルを全面書き直しすること。
- 効果測定に渡さず「直した」で終えること。
- 1 つの PR に、根拠の異なる複数のスキル改訂を混ぜること。
