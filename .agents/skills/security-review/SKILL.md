# Security Review

レビュー担当（Codex でも Claude でもよい）が、`review-pr` のレビューに重ねて行うセキュリティ観点の検査。結果は `review-pr` の投稿 1 件の中に書く。発動条件は `review-pr` の「2. 検査する」にある。

## 決まり

`review-pr` の「決まり」をすべてそのまま守る。PR のコードは読むだけで、実行も head の取り出しもしない。差分は `scripts/agent-gh review pr diff`、PR 側のファイルは GitHub API、main 側の履歴は `git log`・`git show`・`git blame`・`git grep`（どれも読み取り）で読む。手法の中で、実行しないと確かめられないこと（試験の実行、PoC、動的解析）は「未確認」と書いて、読んで分かる範囲で判断する。

所見は、根拠（`<file>:<line>`、必要ならコミット）と、具体的な攻撃の筋書き（誰が、どの入力で、何を得るか）が揃ったものだけを書く。筋書きの途中が読みだけでは確かめきれない懸念は、捨てずに「未確認」に回し、どこが確かめられなかったかを書く。

このレビューの役目は、通常のレビューが見落とす穴を探すことにある。所見 0 は「探したが無かった」ときの結論で、手順 2〜5 の完了の基準を満たしたあとでだけ書ける。

## 手順

### 1. ファイルごとに危険度を決める

PR の変更ファイルを 1 つずつ、次の表で HIGH / MEDIUM / LOW に分ける。行数ではなく、何に触れているかで決める。「リファクタリングだけ」でも、安全のための検査を動かしていれば HIGH にする。

| 危険度 | 当てはまるもの |
|---|---|
| HIGH | 認証・認可、トークン・鍵・暗号、`unsafe`、sandbox・egress・gateway、テナント分離（RLS）、監査、外部入力を受ける経路（HTTP の経路・ハンドラ、ファイルパス、SQL、プロセス起動）、検査器・フィルタ・許可リストそのもの、`.github/workflows/`、`scripts/agent-gh`、エージェントへの指示（`AGENTS.md`、`.agents/skills/`、`docs/agents/`）、検査の削除（`deny.toml` の許可・例外の追加を含む） |
| MEDIUM | 状態の変更、新しい公開API、外部への送信、設定の既定値、依存の追加・更新（`Cargo.toml`・`Cargo.lock`） |
| LOW | コメント、テスト、表示、ログの文言 |

完了の基準: 変更ファイルが 1 つ残らずどれかに分かれている。

### 2. main 側の安全の型を集める

HIGH のファイルが扱うのと同じ種類の処理を、main 側ではどう安全に書いているかを `git grep` で探す。たとえば、利用者の特定（セッション・ヘッダー）、ファイルパスの組み立て、SQL とテナントの指定、ログに出す値の仮名化、秘密の読み込み、検査器の照合のしかた。見つけた型（関数名・`<file>:<line>`）を控えておく。

差分がこの型を使わずに同じことをしている箇所は、それだけで穴の候補になる。例: main に 1 パス成分を検査する関数があるのに、新しい経路が利用者の値をそのまま `Path::join` している。ログは仮名化の型を通すのに、新しい行が `eprintln!` で生の ID を出している。

完了の基準: HIGH のファイルごとに、対応する main 側の型を挙げたか、「main に同じ種類の処理が無い」と書けている。

### 3. 入口から危険な処理までをたどる

差分が足した・変えた入口を挙げる。入口は、攻撃者が値を入れられる場所のこと: HTTP の経路・クエリ・ヘッダー・本文、Cookie、CLI の引数、環境変数・設定ファイル、IdP や外部 API の応答、チャンネルの発言や Bot の出力、Issue・PR の本文やコメント（エージェントへの指示に届くもの）。

入口ごとに、その値が届く危険な処理までを `<file>:<line>` でたどる。危険な処理は、ファイルの読み書き、SQL、プロセスの起動、認証・認可の判定、テナントの選択、秘密の取り扱い、ログ・外部への送信、エージェントへの指示文、メモリの確保（大きさを外から決められるもの）。途中にある検査（型、検証、許可リスト、フレームワークの保証）を書き留め、その検査を外す・すり抜ける入力が無いかを考える。

検査器・フィルタ・許可リストそのものが差分にあるときは、通してはいけないのに通ってしまう入力を自分で 3 つ以上作り、コードを読んで判定をたどる。区切り文字や全角文字、大文字小文字、空白や改行の入れ方、別の書き方（`-XPOST`・`--method=`、値の位置とキーの位置）を変えるのが効く。

完了の基準: 差分のすべての入口について、届く危険な処理と途中の検査を書けている。HIGH のファイルが入口を持たないときは、そう書けている。

### 4. 観点の一覧を当てる

差分に関係する観点だけを当てる。関係しない観点は飛ばしてよいが、飛ばした理由は書かない。差分に `.rs` のファイルがあるときは、`references/rust.md` を読み、そこにある Rust の観点も当てる（どの節を当てるかは同じファイルの冒頭の表で決める）。

#### HIGH のファイルの 4 点

HIGH のファイルすべてについて、次の 4 点を確かめる。

- **消えた検査**: 差分で消えた行のうち、検査・制限・エラー処理に当たるものを `git log -L` や `git blame`（main 側）で、入ったときのコミットまでたどる。`fix`・`security`・CVE を含むコミットで入った行が、代わりなしに消えていれば所見。
- **影響範囲**: 変わった関数・型を `git grep` で呼び出し元まで数える。呼び出し元が多い、または外部入力から届く経路があるものほど重く扱う。呼び出し元がまだ無い新しい部品（後の Issue で組み込む前提のもの）は、組み込まれた後の経路で判断する。
- **試験**: 変わった検査に対応する試験が、同じ PR で追加・更新されているか。検査を変えたのに試験が変わっていなければ所見。試験が「通ってはいけない入力が通る」ことを固定していないかも見る。
- **既定値**: 下の「安全でない既定値」に当てはまる書き方がないか。

#### 安全でない既定値（fail-open）

候補を見つけたら、本当にその値で動くかをたどってから所見にする。

- 秘密の代わりの値: 環境変数や設定が無いときに、固定の鍵・パスワード・トークンで動き続ける（`unwrap_or("dev")` の類）。値が無ければ止まる書き方なら問題ない。
- 既定で開く切り替え: 認証・検証・暗号化・テナント制限を「設定が無ければ（空なら）無効」にしている。
- 固定の資格情報: 初期ユーザー、試験用の鍵が製品の経路に残る。
- 弱い暗号: パスワードや改ざん検知に MD5・SHA-1・固定の IV・乱数でない値を使う。
- 広すぎる許可: CORS `*`、全員に読める権限、ワイルドカードの許可リスト、引数を見ずに通すサブコマンド。
- だれでも書ける場所: `/tmp` などの共有ディレクトリを既定の置き場所にする。
- デバッグの漏れ: スタックトレースや内部のエラー文を利用者への応答に返す。

#### 認証・認可・セッション

- 状態を変える経路（削除、失効、権限の変更）が、要求の本文やクエリの ID ではなく、認証済みのセッションから本人を決めているか。
- 取り消しや失効のあとに、取り消し前に始めた手続き（ログインの途中、保留中の要求）で新しいセッションが作れないか。
- start と finish に分かれた手続きで、start の時点の確認を finish でやり直しているか（名前の重複、資格情報の存在）。
- OAuth・OIDC の `state` や nonce が、開始したブラウザに結び付いているか。

#### 依存

`Cargo.toml`・`Cargo.lock`・`deny.toml` が変わったときに当てる。RustSec の照合は CI の static ジョブ（`verify-static` タスクの `cargo deny check`）が行うので、レビュー担当は道具が判断できないところを見る。`review-pr` の「観点として読むスキル」で読む `rust-supply-chain` のうち、ここで使うのは「Reading an advisory properly」と「Unmaintained is a finding」の考え方。`cargo tree --invert` の代わりに、`Cargo.lock` でその crate に依存する package をたどる。同じファイルの `docs/agents/rust.md` と `/setup-rust-ci` への参照は、このリポジトリに無いので無効とする。

- 新しい依存が、外部入力を受ける経路（HTTP、parse、暗号、認証）で使われるか。使われるなら、その crate の既知の advisory と保守の状態を `deny.toml` の例外・CI の結果と合わせて見る。
- `deny.toml` に、advisory の無視、許可するライセンス・取得元（git・別の registry）の追加、ban の解除が足されていないか。足されていれば、理由と期限が書かれているか。理由の無い緩和は所見。
- 取得元が crates.io 以外（`git =`、`path =`、`[patch]`）になる依存が増えていないか。

#### AI エージェントを動かす GitHub Actions

`.github/workflows/` が変わったときに当てる。

- 攻撃者が書ける入力（Issue・PR の本文やタイトル、コメント、ブランチ名、CI のログ、`workflow_dispatch` の入力）が、AI への指示文に届くか。`${{ github.event.* }}` を指示文に直接入れる、`env:` を経由して入れる、指示文の中で `gh issue view` などで取りに行かせる、のどれも同じ扱い。
- `pull_request_target` や `issue_comment` で起動し、PR の head を取り出して実行していないか。
- AI の出力を `eval`・`$(...)`・`run:` でそのまま実行していないか。
- AI に渡す権限が広すぎないか（全コマンドの許可、sandbox の無効化、だれでも起動できる許可リスト）。権限の広さは、上の入力の経路と組み合わさったときに重く扱う。
- `permissions:` が必要最小か。秘密がフォークからの PR に渡らないか。

#### Pelway 固有の観点

HIGH のファイルがあるときは毎回当てる。

- **GitHub App の使い分け**: エージェントの GitHub 操作が `scripts/agent-gh <dev|review>` を通っているか。素の `gh` を使う箇所が、AGENTS.md の例外（hatai が判断する例外 PR（skill `command-team` の「マージ」の 3 つ）への人間の `gh pr merge --admin` と、`hatai` が書く目印コメント）より広がっていないか。App の権限やトークンの取り扱い（`scripts/agent-gh` の中）を広げていないか。
- **指示の混入（prompt injection）**: Issue・PR の本文やコメントの文が、実装担当やレビュー担当への指示として扱われる経路が増えていないか。目印コメントを作成者（`hatai`）で確かめずに信じる箇所、本文中の「〜せよ」に従わせる手順の書き方、外部から取った文書を指示として読み込ませる箇所を探す。広い実行権限（`full-access`、`bypass`、sandbox の無効化）と、この経路が組み合わさる手順は重く扱う。
- **レビュー担当のネットワーク制限**: レビュー担当が GitHub 以外へ通信できる経路、PR のコードを実行させる経路、head を取り出させる経路、GitHub に書き込める経路（読み取りのはずの操作が書き込みのメソッドを通す）が新しく開いていないか（スキルの手順の変更、sandbox の設定、`scripts/agent-gh review` の挙動）。
- **秘密と個人の情報の露出**: トークン・鍵・接続文字列・生の利用者 ID・開発機のホスト名が、ログ、`docs/worklogs/`、PR・Issue のコメント、試験の期待値、エラー文に出ていないか。ログは仮名化の型を通っているか。
- **手元の道具の書き込み先**: `scripts/` の下で引数として ref・パスを受け取る道具は、引数を信頼できない入力として扱っているか。削除・作成・上書きの先が一時ディレクトリか作業ツリーの中に収まることを、実体パス（symlink を解決したパス）で確かめているかを見る。経路の途中（`<ref>` 側のディレクトリ、重ねる先の親）にある symlink をたどって外に書く筋書きも候補にする。「引数を渡すのが実装担当自身であること」は、この観点の所見を退ける理由にしない（手順 5 の「値が攻撃者の手に届かない」にも当てない）。

完了の基準: 差分に関係する観点を、一つ残らず「問題なし」「所見」「未確認」のどれかにしている。

### 5. 候補を確かめる

手順 2〜4 で出た候補を 1 つずつ、次の 4 つに答えて確かめる。

- **入口**: 攻撃者はだれか（未認証の利用者、ループバックに届く同じホストのプロセス、別テナントの member、Issue にコメントできる人、乗っ取られた Bot など）。その人が実際にその入口に値を入れられるか。
- **経路**: 入口から危険な処理までの各段を `<file>:<line>` で言えるか。
- **防御**: 途中の検査やフレームワークの保証が、その入力を止めないか。止めるなら棄却する。
- **影響**: 攻撃者が何を得るか（読めるデータ、奪える操作、止められる機能）。

4 つとも答えられたものを所見にする。経路か防御が読みだけで確かめきれないものは「未確認」に書く。次のものは棄却してよい: 値が攻撃者の手に届かない（定数、サーバーが決める値）、手前の検査で確実に止まる、試験のコードだけにある。「今は呼び出し元が無い」は棄却の理由にしない（手順 4 の影響範囲）。

完了の基準: 候補がすべて「所見」「未確認」「棄却」のどれかになっている。

### 6. 判定に入れる

本当の欠陥と判断した所見は、`review-pr` の「3. 指摘を 2 種類に分ける」の must-fix（正しさ・セキュリティの欠陥）に数える。直したほうがよいが欠陥ではないもの（多層防御、将来の経路への備え）は nit にする。

### 7. 投稿に書く

`review-pr` の本文の `## 検査（PR のチェック）` の前に、次の節を足す。must-fix・nit に数えた所見は、それぞれの節にも書く。最後の `Reviewer:` の行は `review-pr` のとおりに書く。

```
## security-review
- 発動: <high-risk: 当てはまった条件 | sampling: security=yes>
- HIGH: <ファイルの一覧。なければ「なし」>
- 所見: <件数>（must-fix <件数>、nit <件数>）
- <file>:<line> [<観点>] <筋書き: 誰が・どの入口に・どの入力で・何を得るか>。<直し方>
- 確かめたこと: <入口ごとに、届く危険な処理と途中の検査。比べた main 側の型。HIGH のファイルの 4 点>
- 未確認: <実行しないと確かめられなかったこと。なければ「なし」>
```
