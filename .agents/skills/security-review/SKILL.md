# Security Review

レビュー担当（Codex でも Claude でもよい）が、`review-pr` のレビューに重ねて行うセキュリティ観点の検査。結果は `review-pr` の投稿 1 件の中に書く。発動条件は `review-pr` の「2. 検査する」にある。

## 決まり

`review-pr` の「決まり」をすべてそのまま守る。PR のコードは読むだけで、実行も head の取り出しもしない。差分は `scripts/agent-gh review pr diff`、PR 側のファイルは GitHub API、main 側の履歴は `git log`・`git show`・`git blame`・`git grep`（どれも読み取り）で読む。手法の中で、実行しないと確かめられないこと（試験の実行、PoC、動的解析）は「未確認」と書いて、読んで分かる範囲で判断する。

所見は、根拠（`<file>:<line>`、必要ならコミット）と、具体的な攻撃の筋書き（誰が、どの入力で、何を得るか）が揃ったものだけを書く。筋書きを書けない懸念は所見にせず「未確認」に回す。

## 手順

### 1. ファイルごとに危険度を決める

PR の変更ファイルを 1 つずつ、次の表で HIGH / MEDIUM / LOW に分ける。行数ではなく、何に触れているかで決める。「リファクタリングだけ」でも、安全のための検査を動かしていれば HIGH にする。

| 危険度 | 当てはまるもの |
|---|---|
| HIGH | 認証・認可、トークン・鍵・暗号、`unsafe`、sandbox・egress・gateway、テナント分離（RLS）、監査、`.github/workflows/`、`scripts/agent-gh`、エージェントへの指示（`AGENTS.md`、`.agents/skills/`、`docs/agents/`）、検査の削除 |
| MEDIUM | 状態の変更、新しい公開API、外部への送信、設定の既定値 |
| LOW | コメント、テスト、表示、ログの文言 |

完了の基準: 変更ファイルが 1 つ残らずどれかに分かれている。

### 2. HIGH のファイルを差分と履歴で読む

HIGH のファイルすべてについて、次の 4 点を確かめる。

- **消えた検査**: 差分で消えた行のうち、検査・制限・エラー処理に当たるものを `git log -L` や `git blame`（main 側）で、入ったときのコミットまでたどる。`fix`・`security`・CVE を含むコミットで入った行が、代わりなしに消えていれば所見。
- **影響範囲**: 変わった関数・型を `git grep` で呼び出し元まで数える。呼び出し元が多い、または外部入力から届く経路があるものほど重く扱う。
- **試験**: 変わった検査に対応する試験が、同じ PR で追加・更新されているか。検査を変えたのに試験が変わっていなければ所見。
- **既定値**: 3 の「安全でない既定値」に当てはまる書き方がないか。

完了の基準: HIGH のファイルごとに、4 点それぞれ「問題なし」「所見」「未確認」のどれかを決めている。

### 3. 観点の一覧を当てる

差分に関係する観点だけを当てる。関係しない観点は飛ばしてよいが、飛ばした理由は書かない。

#### 安全でない既定値（fail-open）

候補を見つけたら、本当にその値で動くかをたどってから所見にする。たどりきれなかった候補は所見にしない。

- 秘密の代わりの値: 環境変数や設定が無いときに、固定の鍵・パスワード・トークンで動き続ける（`unwrap_or("dev")` の類）。値が無ければ止まる書き方なら問題ない。
- 既定で開く切り替え: 認証・検証・暗号化を「設定が無ければ無効」にしている。
- 固定の資格情報: 初期ユーザー、試験用の鍵が製品の経路に残る。
- 弱い暗号: パスワードや改ざん検知に MD5・SHA-1・固定の IV・乱数でない値を使う。
- 広すぎる許可: CORS `*`、全員に読める権限、ワイルドカードの許可リスト。
- デバッグの漏れ: スタックトレースや内部のエラー文を利用者への応答に返す。

#### AI エージェントを動かす GitHub Actions

`.github/workflows/` が変わったときに当てる。

- 攻撃者が書ける入力（Issue・PR の本文やタイトル、コメント、ブランチ名、CI のログ、`workflow_dispatch` の入力）が、AI への指示文に届くか。`${{ github.event.* }}` を指示文に直接入れる、`env:` を経由して入れる、指示文の中で `gh issue view` などで取りに行かせる、のどれも同じ扱い。
- `pull_request_target` や `issue_comment` で起動し、PR の head を取り出して実行していないか。
- AI の出力を `eval`・`$(...)`・`run:` でそのまま実行していないか。
- AI に渡す権限が広すぎないか（全コマンドの許可、sandbox の無効化、だれでも起動できる許可リスト）。権限の広さは、上の入力の経路と組み合わさったときに重く扱う。
- `permissions:` が必要最小か。秘密がフォークからの PR に渡らないか。

#### Pelway 固有の観点

HIGH のファイルがあるときは毎回当てる。

- **GitHub App の使い分け**: エージェントの GitHub 操作が `scripts/agent-gh <dev|review>` を通っているか。素の `gh` を使う箇所が、AGENTS.md の例外（指揮役の委任された `gh pr merge --admin` と、`hatai` が書く目印コメント）より広がっていないか。App の権限やトークンの取り扱い（`scripts/agent-gh` の中）を広げていないか。
- **指示の混入（prompt injection）**: Issue・PR の本文やコメントの文が、実装担当やレビュー担当への指示として扱われる経路が増えていないか。目印コメントを作成者（`hatai`）で確かめずに信じる箇所、本文中の「〜せよ」に従わせる手順の書き方、外部から取った文書を指示として読み込ませる箇所を探す。
- **レビュー担当のネットワーク制限**: レビュー担当が GitHub 以外へ通信できる経路、PR のコードを実行させる経路、head を取り出させる経路が新しく開いていないか（スキルの手順の変更、sandbox の設定、`scripts/agent-gh review` の挙動）。
- **秘密の露出**: トークン・鍵・接続文字列が、ログ、`docs/worklogs/`、PR・Issue のコメント、試験の期待値、エラー文に出ていないか。`Debug` の出力に秘密を含む型がないか。

完了の基準: 差分に関係する観点を、一つ残らず「問題なし」「所見」「未確認」のどれかにしている。

### 4. 判定に入れる

本当の欠陥と判断した所見は、`review-pr` の「3. 指摘を 2 種類に分ける」の must-fix（正しさ・セキュリティの欠陥）に数える。直したほうがよいが欠陥ではないものは nit にする。

### 5. 投稿に書く

`review-pr` の本文の `## 検査（PR のチェック）` の前に、次の節を足す。must-fix・nit に数えた所見は、それぞれの節にも書く。最後の `Reviewer:` の行は `review-pr` のとおりに書く。

```
## security-review
- 発動: <high-risk: 当てはまった条件 | sampling: security=yes>
- HIGH: <ファイルの一覧。なければ「なし」>
- 所見: <件数>（must-fix <件数>、nit <件数>）
- <file>:<line> [<観点>] <筋書き: 誰が・どの入力で・何を得るか>。<直し方>
- 未確認: <実行しないと確かめられなかったこと。なければ「なし」>
```
