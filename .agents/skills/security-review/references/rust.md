# Rust の観点

`security-review` の手順 4 から、差分に `.rs` のファイルがあるときに読む。Rust の型と借用の検査が保証するのは安全なコードのメモリ安全とデータ競合の無さまでで、認可の誤り、panic による停止、`unsafe` の中身、論理の誤りは保証しない。

## どの節を当てるか

差分（追加・変更した行と、その関数）に次のものが現れた節だけを当てる。「すべての Rust の差分」の節は毎回当てる。

| 節 | 当てる条件 |
|---|---|
| 外部入力と panic | すべての Rust の差分 |
| 秘密を持つ型 | すべての Rust の差分 |
| 数値の変換 | `as`、`usize`・`u32` などの算術、長さ・個数・時刻の計算 |
| ファイルとパス | `std::fs`、`Path`・`PathBuf`、`join`、`File::open`、`tokio::fs` |
| HTTP の経路とハンドラ | axum の `Router`・extractor、`pelway-http` の `route`・`handle_*`、Cookie・ヘッダーの読み取り |
| SQL とテナント分離 | `sqlx`、`query!`・`query`、`format!` で組む SQL、`set_config`、`SET ROLE`、migration |
| 非同期と並行 | `async`、`tokio`、`Mutex`・`RwLock`、`spawn`、`select!`、atomic |
| unsafe と FFI | `unsafe`、`extern`、`#[repr(C)]`、`transmute`、生ポインタ、`MaybeUninit`、`set_len` |
| 暗号 | 鍵、nonce、MAC、ハッシュ、乱数、`aes`・`chacha`・`ring`・`rand` |

完了の基準: 表の各節について、当てたか当てなかったかが決まっていて、当てた節の項目をすべて「問題なし」「所見」「未確認」のどれかにしている。

## 外部入力と panic

サーバーの要求 1 件が panic すると、そのスレッドやタスク、場合によってはプロセスが止まる。攻撃者が送れる値で panic に届くなら、停止を起こせる所見になる。

- 入口から届く値に対する `unwrap`・`expect`、添字（`v[i]`・`&s[a..b]`）、`str` のバイト位置での切り出し（文字の境界でないと panic）。
- 再帰で処理する入力（入れ子の JSON、深い構造）に深さの上限があるか。
- 読み込む大きさ（本文、ファイル、`read_to_string`、`Vec::with_capacity(n)`）を外から決められないか。上限が無いと、メモリを使い切らせられる。`/dev/zero` のような終わらない入力も含めて考える。
- 保留中の状態（ログインや登録の途中、pending の表）が、未認証の要求で増え続けて消えないか。

## 秘密を持つ型

- 鍵・トークン・パスワード・`client_secret` を持つ構造体が `#[derive(Debug)]` していないか。していれば `{:?}` やエラーの経路でログに出る。手書きの `Debug` で伏せるか、秘密用の型で包む。
- `Display`・`Serialize` で秘密を外に出していないか。エラー型に秘密や本文を入れていないか。
- 秘密やトークン、MAC の比較が `==` になっていないか。時間差で値を推測される比較は、定数時間の比較にする。
- ログに出す値が、`pelway-http` の `logger.id` のような仮名化の型を通っているか。`eprintln!`・`println!`・`tracing` で生の ID・本文・パスを出していないか。

## 数値の変換

- `as` による切り捨て・符号の反転（`u64 as u32`、`i64 as usize`）で、長さや上限の検査をすり抜けないか。`try_from` で失敗を扱っているか。
- 外から決められる値どうしの足し算・掛け算が、release ビルドで黙って桁あふれしないか（`checked_*`・`saturating_*`）。
- 時刻や期限の比較が、桁あふれや時計の戻りで常に真（期限切れにならない）にならないか。

## ファイルとパス

- 利用者の値を `Path::join` に渡していないか。`join` は絶対パスを渡されると前を捨てて置き換わり、`..` も解決しない。パスの組み立ての前に、値が 1 つのパス成分である（空でない、`.`・`..` でない、`/`・`\`・NUL を含まない）ことを確かめる。main に同じ検査の型があれば、それを使っているか。
- URL デコード（`%2F`・`%2E`）の後で検査しているか。デコードの前に検査すると、`..%2F` がすり抜ける。
- シンボリックリンクをたどって置き場所の外に出ないか。確かめてから開くまでの間に差し替えられないか。
- 置き場所の既定値が、だれでも書ける場所（`/tmp`）になっていないか。

## HTTP の経路とハンドラ

- 新しい経路が、既存の経路と同じ認証・認可の型を通っているか。axum なら、認証を extractor や layer で強制しているか、ハンドラが `Option` で受けて素通りさせていないか。
- だれの操作かを、要求の本文・クエリ・ヘッダーの自己申告ではなく、認証済みのセッションから決めているか。既存の経路が自己申告で済ませている場合（デモの仮の経路など）は、新しい経路が返すもの・変えるものの重さで判断する（読み取りより、中身を返す・消す・権限を変えるほうが重い）。
- 他人のもの（別の member、別のテナント、別のチャンネル）を ID の指定だけで読めないか、変えられないか。
- 応答に内部のエラー文、パス、スタックトレースを返していないか。
- Cookie の `HttpOnly`・`Secure`・`SameSite` と、状態を変える `GET` が無いか。

## SQL とテナント分離

migration（`crates/*/migrations/`）が変わるときは、`review-pr` の「観点として読むスキル」で読む `supabase-postgres-best-practices` のうち `references/security-privileges.md` と `references/security-rls-basics.md` を repo のパスで読み、最小権限・`SECURITY DEFINER`・RLS の有効化の観点を当てる。どちらも Supabase 向けに書かれているので、`auth.uid()` や `authenticated` ロールの例は、Pelway の書き方（`set_config` で渡すテナント、`pelway_app` などのロール）に読み替える。

- SQL を `format!` や文字列の連結で組んでいないか。値はバインド変数で渡す。識別子を組むなら、定数か許可リストからだけにする。
- テナントの指定（`set_config('app.workspace_id', ...)` など）が、トランザクションの中でだけ効く形（`is_local = true`）か。接続プールで次の要求に持ち越されないか。
- テナントの ID を、要求の値ではなく認証済みの文脈から取っているか。
- RLS の表に `ENABLE` と `FORCE ROW LEVEL SECURITY`、ポリシーに `USING` と `WITH CHECK` の両方があるか。設定が無い・空のときに、どの行にも一致しない（fail-closed）か。
- アプリのロールが `BYPASSRLS` や所有者の権限を持たないか。管理用の経路（RLS を通らない接続）が、監査の付いた専用の入口に閉じているか。

## 非同期と並行

- `Mutex` の guard を持ったまま `.await` していないか。async の中で重いブロッキング処理（ファイル、暗号、`std::thread::sleep`）をしていないか。止まると、ほかの要求も止まる。
- 「確かめてから使う」の 2 段が、別々にロックを取っていないか（確かめた後に状態が変わる）。認可の確認と操作は、同じロックか同じトランザクションの中で行う。
- `select!` や途中で落とされる future で、半分だけ終わった状態（片方の表だけ更新）が残らないか。
- ロックの毒（poison）を `unwrap` して、1 件の panic を全要求の停止に広げていないか。

## unsafe と FFI

`review-pr` の「観点として読むスキル」で読む `unsafe-checker` のうち、`checklists/review-unsafe.md` を repo のパスで読み、その項目（ポインタの有効性、別名、初期化、Send・Sync、FFI の境界）を `unsafe` のブロックごとに当てる。個々の規則の詳しい説明が要るときは同じスキルの `rules/` の該当ファイルを読む。

- `unsafe` のブロックごとに `// SAFETY:` の説明があり、その前提を呼び出し元が本当に満たしているか。安全な関数の引数だけで前提を破れるなら、その関数は健全でない（所見）。
- `set_len`・`MaybeUninit`・`from_raw_parts` で、初期化していない値や範囲外を読まないか。長さと容量の計算が外から決められないか。
- `transmute`、`#[repr(C)]` の詰め物、`unsafe impl Send`・`Sync` の根拠。
- FFI の境界で panic が外に抜けないか。`CString` の寿命より長くポインタを使わないか。

## 暗号

- nonce を使い回さないか（固定値、カウンタの巻き戻り、同じ鍵での乱数の衝突の確率）。
- 乱数が暗号用の生成器（`OsRng`・`getrandom`）か。
- 認証付き暗号（AEAD）の検証に失敗したときに、復号した途中の値を使っていないか。エラーの種類で中身を推測させていないか。
- 鍵の取り違え（テナント間で同じ鍵、用途の違う鍵の流用）が無いか。鍵の識別子と暗号文の結び付けを検証しているか。
