# Write Issue

AI 開発チームに渡す Issue のタイトルと本文を書く・直す手順。`write-pull-request` と対になる。
実装担当は Issue の本文だけを読んで作業し、レビュー担当は受け入れ条件と対象外だけを基準にする。本文に無いことは、だれも確かめない。

## 使うとき

- AI 開発チームに渡す Issue を新しく立てるとき（指揮役・人間・エージェントのどれでも）
- Issue を分割するとき
- 実装担当から差し戻された Issue の本文を直すとき
- `ready-for-agent` を付ける前に、本文を確かめるとき

## 決まり（毎回守る）

- 本文の見出しは下の「本文の構成」の 8 つをこの順で全部書く。書くことが無い見出しも消さず「なし」と書く。
- 本文の構成の正本はこのスキル。`.github/ISSUE_TEMPLATE/agent-task.yml` はその写しなので、見出しを変えるときは両方を同じ PR で直す。
- Issue の正本は本文。決まったこと・直したことはコメントで済ませず、本文に書き直す。コメントは経緯と、目印（`<!-- split-plan -->`、`<!-- pr-size-exception -->`）だけに使う。
- AI 開発チームのエージェントは `scripts/agent-gh dev issue create` で立てる。Web のフォームを通らない起票でも、このスキルの形にそろえる。
- 起票しただけでは `ready-for-agent` を付けない。手順 6 のゲートを通ってから付ける（付けるのは人間。指揮役は人間に委任されたときだけ）。

## 手順

### 1. 調べる（Prior art first）

書く前に、次を調べる。調べたものは「関連情報」にリンクで残す。

```bash
scripts/agent-gh dev issue list --state all --search "<キーワード>" --json number,title,state
scripts/agent-gh dev pr list --state all --search "<キーワード>" --json number,title,state
git grep -n "<対象の型・関数・ファイル名>"
ls docs/adr docs/research
```

- 同じ目的の Issue・PR が既にあれば、新しく立てずにそちらを直す。
- 関連する ADR、`docs/research/` の調査、仕様（`docs/technical/`）の該当節、対象のコードの今の状態を読む。
- リポジトリ外の成果物（素案・調査文書など）を参照するときは、取得可能な URL か、判断に足る抜粋の引用を本文に残す。名前だけの参照は書かない（実装担当が内容に到達できなくなるため）。
- 慣れない機能なら、AGENTS.md の「Prior art first」に従い、方式を人間に選んでもらってから「採用する方式」に書く。

### 2. タイトルを書く

対象と変化が 1 行で分かる日本語にする（T3 のスレッド名と同じ考え方）。「<対象>：<何をどう変えるか>」の形をすすめる。

- 良い例: 「LLMゲートウェイ：rig-coreでOpenAI互換APIにつなぎ、BYOKで測れるようにする」
- 悪い例: 「LLM対応」（何が変わるか分からない）、「#92 の続き」（番号だけ）、「pgBackRest r2」（工程名だけ）

### 3. 本文を書く

#### 本文の構成

| 見出し | 書くこと | 書かないこと |
|---|---|---|
| 目的 | 何のために、何を変えるか。2〜3 文 | やり方の細部 |
| 背景・前提 | この Issue が要る理由、前提になる決定（ADR、Issue の番号） | 経緯の物語。決定の中身の写し（リンクで足りる） |
| 受け入れ条件 | 下の「受け入れ条件の書き方」のとおり | 実装の手順 |
| 対象外 | この Issue では触らないこと。分けた先の Issue 番号 | 「その他すべて」のような範囲の無い書き方 |
| 関連情報 | 手順 1 で調べた ADR・調査・仕様・コード・Issue・PR へのリンク（リポジトリ外の成果物は URL か判断に足る抜粋）。バグ・インシデントの調査（skill `investigate-bug`）起点の起票では、報告のパス（`docs/worklogs/bugs/<slug>/report.md`）と調査スレッドのリンクの両方 | 調べていないもの、名前だけの参照 |
| 未決事項 | 決まっていないことと、だれが・いつ決めるか。無ければ「なし」 | 本文のほかの見出しに散らした未決 |
| 規模の見積もり | 見込みの追加行数と、その内訳。800 行を超えるなら分割案 | 根拠の無い数字 |
| 採用する方式 | Prior art first で人間が選んだ方式と、選んだ理由へのリンク。慣れた機能なら「なし」 | まだ選ばれていない方式 |

本文は heredoc で渡す。

```bash
scripts/agent-gh dev issue create --title "..." --body-file - <<'EOF'
### 目的
...
EOF
```

#### 受け入れ条件の書き方（このスキルの核）

- 1 行に 1 条件。テストかコマンドか手順で、満たしたかどうかを判定できる形にする。
- 条件ごとに、行末の「→」の後に確かめ方（テスト名、コマンド、確認の手順）を書く。
- 到達点の状態を 1 行に含める: 成果物の出来だけでなく、どこまで行ったら完了かを書く（例: 「Draft PR の存在をもって完了とする」「マージまで行う」）。書かないと、PR への手当ての指示が到達点の性質（Draft のままか、マージまでか）を落とす。
- 測れない言葉（「いい感じに」「適切に」「十分に」「きれいに」「なるべく」）を使わない。数値・状態・出力で書く。
- 1 行に複数の条件を詰めない（「〜し、〜し、〜する」になったら行を分ける）。
- 実装の手順を受け入れ条件として書かない（「〜関数を作る」「〜をリファクタリングする」は手順。満たすべき振る舞いで書く）。どうしても手順を指定するなら「採用する方式」に書く。
- 作業環境で確かめられない条件（実機、GPU、外部のアカウント）は、人手の Issue に分けて「対象外」に番号を書く。

良い例（#95 の書き直し後の条件に確かめ方を添えた形）:

```
- モックサーバーが 5xx を返したとき、要求が 1 回しか送られない → `cargo test -p pelway-llm retry_never_on_5xx`
- `Debug` の出力とログにトークンが出ない → `cargo test -p pelway-llm token_not_in_debug`
- JSON スキーマに合わない応答に「応答が不正」のエラーを返す → `cargo test -p pelway-llm schema_violation_is_invalid`
- 試験が外部ネットワークに出ない → `mise run verify` がネットワークを切った環境で通る
```

悪い例:

```
- pgBackRest で復旧できるバックアップを最大 14 日に保てるか確かめる
    （確かめた結果「保てない」でも満たすのか分からない。確かめ方も無い。#101 の旧本文）
- LLM の接続をいい感じに作る（測れない）
- rig-core を入れて trait を作り、試験を書き、README も更新する（4 条件を 1 行に詰め、しかも手順）
- ListView が速いこと（何件で何秒か無い）
```

直した例（上の #101 の 1 行目）:

```
- 件数指定の設定で、日次バックアップが毎日成功するとき、15 日目の expire の後に 14 日を超えたフルバックアップが残らない → `scripts/pgbackrest-verify/verify.sh` の retention 段階が PASS
- 日次バックアップが欠けた日があるときに 14 日を超えた世代が残るかを、実測の結果として報告書に書く → `docs/research/<報告書>.md` の該当節
```

### 4. 規模を見積もり、分ける

- 1 Issue = 1 PR。PR の差分は追加 800 行・削除 2000 行まで（`mise run pr-size`。base 側の `.gitattributes` で `linguist-generated` を付けたファイルは数えない）。
- 見積もりは、変えるファイルごとの追加行数を足す。試験は実装と同じくらいの行数を見込む。
- 800 行を超えそうなら、起票の時点で分ける。分け方は、追加行の境目（型と契約／HTTP／試験の土台など）で、それぞれ単独でレビューできる単位にする。
  - 子の Issue をそれぞれこのスキルで立て、その子に割り当てた範囲の受け入れ条件だけを書く。親の Issue の「対象外」に子の番号を書く。
  - 着手後に実装担当が超過で止まったときは、指揮役が親の Issue に `<!-- split-plan -->` のコメントで PR ごとの範囲と受け入れ条件を表にする（skill `command-team` の「分割を認めるとき」）。表の受け入れ条件も、この手順 3 の書き方に従う。

### 5. 未決事項を集める

- 決まっていないことは「未決事項」にだけ書く。目的・受け入れ条件の中に「（未定）」「要検討」を散らさない。
- 未決事項がある Issue に `ready-for-agent` を付けるのは、次のどちらかを済ませた後だけ。
  - 未決を解消して、本文に反映する
  - 未決ごとに、だれに何の判断を仰ぐか（例: 「hatai が A と B から選ぶ。選ぶまで実装担当は〜の部分に着手しない」）を書き、実装担当がその部分を避けて進められる形にする

### 6. ゲート（`ready-for-agent` を付ける前）

次を全部満たすときだけ `ready-for-agent` を付ける。1 つでも欠けたらラベルを付けず、自分で補うか、起票者に返す（返すときは何が欠けているかを具体的にコメントする）。

- [ ] タイトルが手順 2 の形
- [ ] 8 つの見出しが全部ある
- [ ] 受け入れ条件が 1 行 1 条件で、全部に確かめ方が付いている
- [ ] 受け入れ条件に測れない言葉・詰め込み・実装の手順が無い
- [ ] 受け入れ条件に到達点の状態が書かれている（Draft PR の存在をもって完了とする／マージまで行う、など）
- [ ] 未決事項が「未決事項」に集まっていて、手順 5 のどちらかを済ませている
- [ ] 規模が 800 行以内の見込みか、分割済み
- [ ] 慣れない機能なら「採用する方式」が埋まっている

### 7. 差し戻されたら

実装担当（skill `implement-issue`）が「受け入れ条件が無い・確かめられない」などで止まったら:

1. 実装担当のコメントで指摘された不足を読む。
2. コメントで答えるのではなく、Issue の本文を手順 3〜5 に従って書き直す。
3. 手順 6 のゲートを通し、`needs-human` を外して `ready-for-agent` を付け直す。
4. 本文を書き直したことを、1 行のコメントで残す（例: 「受け入れ条件 2・3 に確かめ方を足した」）。

## 誠実さのルール

- 調べていないものを「関連情報」に書かない。
- 決まっていないことを、決まったように書かない。
- 規模の見積もりに根拠（ファイルごとの内訳）を付ける。
