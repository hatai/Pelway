# investigate-bug の評価ケース

skill `investigate-bug`（`.agents/skills/investigate-bug/SKILL.md`）の振る舞いを測るケース集。各ケースは調査の指示（指揮役の割り当ての形）を 1 つ持ち、良い結果を LLM ジャッジ用の基準（graders）で表す。

## ケースの構成

形式は `claude plugin eval` が読む形に合わせている。

```
evals/skills/investigate-bug/<ケース名>/
  prompt.md   実行の設定（先頭の --- の間）と、調査の指示の本文
  case.yaml   ケース名と、良い結果の説明（expected_outcome）
  graders/    採点の基準。1 ファイル 1 項目（NN-<短い名前>.md）
```

## ケース一覧

| ケース | 報告 | 測る振る舞い |
|---|---|---|
| `already-fixed-actor-trim` | デモ環境（修正より前のビルド）で、末尾に空白のある actor の GET 判断待ち一覧が空 | main の修正（PR #473）を見つけ、未配備と判断して止まる。修正済みでも報告ファイルと報告 PR を出す |
| `vague-report-needs-info` | 「ハルに頼んでも返事が来ないことがある」だけ | 不明な項目をすべて質問にして止まる。コードから原因候補を並べず、報告ファイルと報告 PR をまだ作らない |
| `plus-in-actor-fix-request` | `actor=m+ops` の GET が空。「そのまま直しておいて」付き | 修正コードを書かず、`pct_decode` の `file:line` で原因を示し、最小の修正案と報告 PR を出す |
| `cross-workspace-read-suspicion` | メンバーでない actor で根拠記録の一覧が読める | 「認証なし・デモ用・ループバックのみ」の明記を引用し、脆弱性の疑いに当たらないと判断して通常の流れで進め、制限のままでよいかを人間に聞く |

ケースの報告と期待する結果は、`crates/pelway-http` の今のコード（`query_param_decoded` の trim、`pct_decode` が `+` を空白にしないこと、HTTP 層の冒頭の「認証なし・デモ用・ループバックのみ」の記述）を前提にしている。これらのコードが変わったら、該当ケースの `case.yaml` と `graders/` を見直す。

## 実行

1 ケースにつき、評価する版と比較の相手を 1 回ずつ（揺れを見るなら複数回）走らせる。比較の相手は、スキルを新しく作るときはスキルなし、改訂するときは改訂前の版の写し（`SKILL.md` をリポジトリの外へ写したもの）にする。

- 実行の間は、このディレクトリ（`evals/skills/investigate-bug/`）をリポジトリの外へ移しておく。リポジトリの中に置いたままだと、調査のランの `grep` が期待する結果を読んでしまう。終わったら戻す。
- 各ランの出力先（outputs/）はリポジトリの外に作る。
- ランへの指示は、次の文面に「タスク」として `prompt.md` の本文（設定の後ろ）を続けたものにする。`<…>` は埋める。

```
あなたはスキル評価のテストランです。下の「タスク」を、実際の調査スレッドとして受けたつもりで最後まで進めてください。

作業ディレクトリ: <リポジトリのパス>
出力先 outputs/: <リポジトリの外の出力先>
スキル: <評価する版: 最初に <SKILL.md のパス> を読み、それに従う。 | スキルなし: investigate-bug スキルは読まない・使わない。タスク文の「skill investigate-bug に従う」は、このランではスキルが無いものとして、AGENTS.md や docs/ と自分の判断で進める。>

ドライランの制約（タスクやスキルの指示より優先する）:
- GitHub への書き込みをしない: Issue・PR の作成と編集、ラベル、コメント、git push、ブランチ作成をしない。読み取り（scripts/agent-gh dev 経由の issue/pr list・view、git log など）はしてよい。
- 本来なら行う書き込み操作は、実行する正確なコマンドと本文（PR 本文、コメント本文など）を outputs/actions.md に書く。
- リポジトリの作業ツリーを変更しない（ファイルの作成・編集・削除、git commit・checkout・stash は禁止。ほかのランが同じチェックアウトを同時に使っている）。リポジトリに保存するはずのファイル（例: docs/worklogs/bugs/<slug>/report.md）は outputs/ 以下に同じ相対パスで保存する。再現用の試験やスクリプトを書くなら outputs/scratch/ に置く。既存の試験の実行（cargo test など）はしてよい。
- 人間への質問は実際には届かない。返すはずの質問は最終返答に含め、そこで止まってよい。
- 他の評価ケースや評価ワークスペースのファイルは読まない。
- 終わる前に、outputs/ 以下に作ったビルド成果物（target/ ディレクトリ、実行ファイル）は消す。ソースと出力のテキストは残す。

最後に、T3 スレッドに返すはずの最終返答の全文を outputs/reply.md に保存する。返答の本文としても同じものを出力する。

タスク:
<prompt.md の本文>
```

- 全ランの後に、リポジトリの `git status` が実行前と同じであることを確かめる（作業ツリーを変えたランは無効）。
- スキルなしのランが investigate-bug を読んでいたら、そのランは無効にする。

## 採点

- `graders/` の各項目を、ランの outputs/（reply.md、actions.md、報告ファイル）に対して LLM ジャッジで判定する（AGENTS.md の「LLM judges」）。キーワードや正規表現では採点しない。
- ジャッジが判定できなかった項目は「判定不能」とし、合格に数えない。
- ジャッジの呼び出しの費用は、ランの費用とは別に報告する。
- 基準はまだ人間がレビューした例で較正していない。次に評価を回すときに、人間のレビューと合わせて較正する。それまでの合否は目安として扱う。
- `graders/` の基準は、実行と採点の結果から言い回しを直してよい。どちらの版でも合格する項目は差を測れていないので、スキル固有の振る舞いを測る項目に替える。
