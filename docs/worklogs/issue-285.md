# Issue #285 の作業ログ

## 実装者メモ（round 1）

1. 詰まった箇所: 手順 4（テスト実行）: ensure が `flock 9` で取ったロックの fd を、setsid で起きた見張りが引き継ぎ、ロックが見張りの寿命まで解放されず 2 回目の ensure が永久待ちになった。起動側に `9>&-` を付けて直した。
2. 曖昧だった文: 「`systemd --user` が使える環境では、ensure が unit 経由で起動し、プロセスを kill しても ensure を呼ばなくても自動で再起動される」（Issue #285 の「受け入れ条件」）。unit 外ですでに動いている見張りを、unit に移し替えるのかそのまま採用するのかが書かれていない。
3. 仮定と解釈: 動作中の見張りは起動元を問わずそのまま採用する解釈を選んだ（止めて unit に移す案は、kill で巡回の空白を作り、Issue の目的と逆になるため採らなかった）。二重起動の防止だけを ensure の責任とした。
4. 足りなかった情報・検証手段: Issue の関連情報に挙がる `docs/worklogs/2026-11-14-conductor-substitute.md` が main に無く、事故の実際の再現条件は Issue 本文の記述だけを頼りにした。
5. 改善案: `.agents/skills/implement-issue/SKILL.md` の手順 4 に「実プロセスの起動・停止や systemd のような環境依存の副作用は、`unshare` の名前空間やモックで隔離して確かめる」を足すと、この種の受け入れ条件でもローカルの再現可能な検証が書きやすい。

## 実装者メモ（round 2）

1. レビュー指摘: round 1（Codex、request-changes、must-fix 1 件）で「すでに動いている見張りを無条件に採用すると、直接起動や別 unit のプロセスをそのまま採用してしまい、`Restart=always` の管理外のプロセスが死んだとき監視が空白になる。systemd 経路では unit の所有を保証するか、受け入れ条件・設計合意の文面を変えよ」と指摘された。
2. 解釈の訂正: round 1 で採った「起動元を問わず採用」は却下。設計意図（誤った起動を構造的に排除する）に立ち返り、「正しい形でない見張りは正しい形に置き換える」へ直した。置き換え時に一瞬の空白が生じるが、unit があれば `Restart=always` が即座に立て直す形なら空白は `RestartSec=5` 以内で、手動起動の見張りが親シェルの終了で道連れ死するリスクより小さい。
3. 対応: systemd 経路では unit ファイルの更新・`daemon-reload` を必ず先に行い、`systemctl --user show -p MainPID` で unit のプロセスを取得し、それでもその子でもない見張り（`foreign_pids`）を kill してから `start` する。unit が active であれば起動済みとして終了する。直接起動経路では、セッションを切り離していない見張り（`fragile_pids`、リーダーの一時的な子は除外）を kill し、セッションリーダー（`leader_pids`）が 1 つ残れば採用、2 つ以上なら後からのものを落とす。
4. 検証: 名前空間テストに「unit 外で動く見張りは unit に置き換えられる」「セッション非切り離しの見張りは切り離した形に置き換えられる」「リーダーが 2 つなら 1 つにする」の 3 系統を追加。実環境でも unit 外の見張りを起きてから ensure を実行し、unit の MainPID が生き残り foreign が死ぬこと、unit のプロセスを kill すると ensure を呼ばずに新しい pid で自動復旧することを確かめた。
5. 詰まった箇所: テスト側の sysbin に `tail` が無く `tail -n +2` が黙って失敗し、複数リーダーの後続を落とせない不具合をテストが検出した。sysbin に `tail` を足して解消。
