# 起票スキル write-issue を作る

## 経緯

- Issue の本文がざっくりしすぎていて、実装担当とレビュー担当の判断がぶれる問題があった（hatai の要望）。
- `.github/ISSUE_TEMPLATE/agent-task.yml`（目的・受け入れ条件・対象外・規模が必須）は既にあったが、Web のフォームを通る起票にしか効かず、`scripts/agent-gh dev issue create`（API）での起票は素通りしていた。
- 実際に、形のそろわない Issue が混ざっていた。#101 は「背景／やること」の形で、確かめられる受け入れ条件・対象外・規模が無く、レビューで 4 回の修正の指示（14 日の上限を「確かめる」の解釈、未検証の運用での断定など）を経てエスカレーションになった。#98 は Windows・macOS の実機が要る項目が受け入れ条件に混ざり、split-plan で人手の Issue（#138）に分けた。

## 判断

- 本文の構成の正本をスキル（`.agents/skills/write-issue/SKILL.md`）に置き、フォームはその写しにした。見出しを変えるときは両方を同じ PR で直す。フォームに「背景・前提」「関連情報」「未決事項」を足し、「規模の見積もり」は内訳を書けるよう選択式から自由記述にした。
- `config.yml` を `blank_issues_enabled: false` にし、Web からフォームを通らない Issue を作れなくした。API での起票はフォームが効かないので、スキルの「決まり」と、command-team・agent-team.md・AGENTS.md からの参照で縛る。
- 受け入れ条件は 1 行 1 条件で、条件ごとに確かめ方（テスト名・コマンド・手順）を付ける形にした。良い例は #95 の書き直し後の条件、悪い例は #101 の旧本文から取った。
- implement-issue の「止まる条件」の受け入れ条件の行を、「受け入れ条件が無い・確かめられない Issue には着手せず、不足を具体的に指摘して差し戻す」に強めた。差し戻された本文は起票者がスキルの手順 7 で直す（正本は本文）。
- 進行中の Issue（#95、#97、#100）は遡って書き直さない。未着手の Issue（#133、#138、#149、#150、#151 など）は、`ready-for-agent` を付ける前に write-issue の手順 6 のゲートを通す。
