# Issue #714 の作業ログ

## 実装者メモ（round 1）

1. 詰まった箇所: `state.json` への `cur` の保存が、issue 一覧と PR 一覧の両方の取得成功・未打ち切りを条件にするブロックの中にしかない。SLOTS 行は PR 一覧の成否に関わらず出したいので、判定をゲートの外に置き、署名の保存は SLOTS ブロック内で行う形にした（ゲートが通れば後段でもう一度保存されるので、二重保存の影響は無い）。「HEARTBEAT の行のたび」の判定は、HEARTBEAT を出す箇所で `hb` フラグとして確定させ、後段の SLOTS 判定に使い回した（出したかどうかを `heartbeat_at` の再比較で後から確かめると、更新後の値と比べてしまい出した巡回を判定できない）。
2. 曖昧だった文: 「巡回ごとに、実装と調査に使っている枠の数を agent-team.toml と照合して出す」と「出すのは、使用数が前回の巡回から変わったときと HEARTBEAT の行のたび」の関係。毎巡回「照合」は行い、「出す」のは条件のときだけと解釈した（watch.log が SLOTS 行で埋まるのを避ける意図と整合する）。
3. 仮定と解釈: 「使用数が前回の巡回から変わった」は、担当ごとの出力行を連結した署名を `state.json` に残して比較する形にした。agent-team.toml が無い・issue 一覧の取得に失敗・件数が打ち切られた巡回では署名を更新しない（前回の署名を残す）ため、復帰した巡回で使用数が同じなら出し直さない。`SLOTS error` の理由は `agent-team-config` の stderr の最初の非空行・160 字までとした。選ばなかった解釈: 巡回ごとに必ず出す（上記）、agent-team.toml が無いときに `SLOTS error` を出す（要件は「出さない」）、理由を `SLOTS error` だけにして中身を出さない（巡回記録だけでは原因を追えなくなるため、検証エラーの先頭行を載せた）。
4. 足りなかった情報・検証手段: Issue の担当の内訳は「`agent:devin` があれば devin、無ければ opencode」の対応表を conductor-watch 側に持つ形になった。agent-team.toml の `developers.hatai.use` に opencode・devin 以外の実装担当が加わったとき、その担当の枠には（Issue のラベルで識別できる内訳が無い限り）何も数えられないが、行は `0/<上限>` で出る。Issue #714 は「Issue の所有者は区別せず hatai の表だけを読む」と明記しているので現行構成ではこの解釈で足りる。
5. 改善案: `agent-team-config` に「Issue のラベルから枠の担当（slots のキー）を引く」問い合わせを足すと、実装担当を増やすときに conductor-watch 側の対応表（`agent:devin` → devin、それ以外 → opencode）を直さずに済む。ラベル命名（`agent:<担当>`）と slots のキーの対応を toml 側に寄せられる。
