## 改訂と根拠

一次記録はランの出力（reply.md）と最終報告。引用は原文のまま。

1. 修正済み・未配備のときも報告ファイルと報告 PR を出す（手順 2）。改訂前の手順 2 の「そこで止まる」と、手順 5・AGENTS.md の「報告 PR は起票の可否にかかわらず出す」が食い違っていた。
   ```
   skill の手順 2 に「そこで止まる」とあるので、報告ファイル（`docs/worklogs/bugs/<slug>/report.md`）も報告の Draft PR も作っていない。
   ```
   出典: 2 回目 `already-fixed-actor-trim` 改訂前の版の reply.md。1 回目の同じ版は逆に報告 PR を出しており、版の中で振る舞いが割れていた。
2. 調べる対象が決まらない報告では、手順 2 の検索だけをして質問で止まる（手順 1）。改訂前の版とスキルなしは、回答を待たずにコードを読んで候補を並べた。
   ```
   ## 4. 回答を待たずに進めた読み取り調査（原因の確定ではない）
   ```
   出典: 2 回目 `vague-report-needs-info` 改訂前の版の reply.md。スキルなし（1 回目）は 290 秒かけて候補 7 つの報告を書いた。改訂後の 3 ランはいずれも 94〜176 秒で質問を返して止まった。
3. 6 項目のうち不明なものはすべて質問に入れる（手順 1）。改訂後の 3 回目の 1 ランが頻度を聞かなかった（採点の根拠: 「No frequency question: Q5 asks what differed between success/failure, not how often it happens」）。この 1 行は実行で確かめていない。
4. 脆弱性の疑いの判断を、3 種類の結果（他人のデータの読み書き、認証・認可の迂回、秘密の漏えい）につながる原因に限り、明記された制限で報告の環境がその範囲内なら疑いに当たらないとした（手順 4）。迷ったら疑いとして止める。改訂前の版は同じケースで止めた回と止めなかった回に割れた。
   ```
   脆弱性の疑いとして止める分岐には当たらないと判断し、報告ファイルの保存と報告 PR の手順に進みました。
   ```
   出典: 1 回目 `cross-workspace-read-suspicion` 改訂前の版の reply.md。2 回目の同じ版は「脆弱性の疑いがあるため、skill investigate-bug の手順 4 に従って通常の流れ（報告ファイルの保存、Draft PR、起票）を止めました。」と止めた。
5. Issue の無い報告（部屋のメッセージ）では、`needs-info`・`needs-human` の代わりに質問をスレッドの返答に書く（決まり、手順 4、`docs/agents/command-team-details.md`、`docs/agents/grokbot-runbook.md`）。
   ```
   `docs/agents/grokbot-runbook.md` は、調査が脆弱性の疑いで止まったら「報告の対象の Issue に `needs-human` を付ける」としています。今回のように部屋のメッセージから始まって Issue が無い報告で、どこに `needs-human` を付けるかは書かれていません。
   ```
   出典: 1 回目 `cross-workspace-read-suspicion` スキルなしの reply.md。同じ指摘が 1 回目 `vague-report-needs-info` のスキルなしにもある。
6. 報告 PR の `Implementer:` の行を「対象」節の最後に置くと明記した（手順 5）。2 回目の 2 ランが最終報告で、置き場所が書かれておらず PR テンプレートにも欄が無いと指摘した（「The investigate-bug skill says to put an `Implementer:` line in the PR body, but `.github/pull_request_template.md` has no such field.」）。

## 評価の運用で分かったこと

- 評価ケースをリポジトリの中（スキルのディレクトリ）に置いたまま回すと、調査のランの `grep` が期待する結果を読んだ（1 回目 `plus-in-actor-fix-request` の両ランが最終報告で自己申告。スキルなしは reply.md にも書いた）。2 回目以降は実行の間だけリポジトリの外へ移した。README の手順に入れた。
- 再現用のクレートを outputs/ に作ったランが、ビルド成果物で 1GB を超える `target/` を残した。ドライランの制約に後片付けを足した。

## 期待する変化

- 修正済み・未配備の調査でも報告 PR が出て、報告が main に残る。
- 情報不足の報告で、検証できない原因候補を並べた報告が出なくなり、質問が早く返る。
- デモ層の明記された制限に当たる報告で、調査が止まるか進むかが揺れなくなる。
