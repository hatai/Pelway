# 指揮役のコンテキスト管理

指揮役のスレッドは長命で、稼働が長くなるほどコンテキストが圧迫され、判断根拠や割り当ての細部が落ちて巡回の質が下がる。状態の正本が GitHub Issues と Projects ボード、待ち状態が patrol-state、割り当てと判断が巡回記録（`docs/worklogs/`）にあるため、圧縮の前後の手順を決めれば安全に圧縮できる。この文書がその手順の正本（skill `command-team` の「コンテキスト管理」から条件つきで参照する）。

リスクは 3 つに分けて扱う: A 未外部化（記録されていない判断を保持したまま圧縮して失う）、B 復元漏れ（外部化されていても復元で読み漏れる・手順を踏み外す）、C 状態の陳腐化（記録後に外部状態が変わり、古い前提で再開する。結果不明の操作の二重実行を含む）。外部化は A への対策にすぎず、それだけで安全は保証されない。

圧縮の仕組み（明示的な圧縮の可否・使用率の取得方法・自動圧縮の有無と検知）は、指揮役を動かすプロバイダ（opencode・Devin CLI・Codex・Claude）ごとに異なる。プロバイダごとの検証結果は `docs/dev-environment.md` の「指揮役スレッドのコンテキスト圧縮の検証」を参照する。この文書の手順（2 経路・外部化チェック・復元検証・照合）はどのプロバイダでも同じ形で適用し、プロバイダごとの差分はトリガーの判定（使用率か代理指標か）と予期しない圧縮の取扱いに現れる。

## 経路と区切り

圧縮は 2 経路に分ける。

- **計画的圧縮**: 区切りでのみ実施し、事前の外部化チェックと事後の復元検証を必須とする
- **予期しない圧縮**: 環境の自動圧縮の途中発動。前提欠落の自己検知もこの経路で扱う（下の「予期しない圧縮」）

**区切りの定義**: 指揮役の操作が完結し、未記録の判断がなく、進行中・待機中の全案件の記録が完了した時点（例: PR のマージと報告が完了し、次の Issue に着手する前）。結果不明の自発行操作が残っている間は計画的圧縮を延期する。

## トリガー（暫定の観測基準）

- 使用率が取得できる環境では使用率 70% 以上（代理指標は使わない）。使用率が取得できるかはプロバイダごとに異なる（検証記録は `docs/dev-environment.md` の「指揮役スレッドのコンテキスト圧縮の検証」）
- 取得できない環境では代理指標: 起算点から完了 Issue 5 件以上、または巡回 75 回以上
- 前提欠落の自己検知（思い出せない状態があること）は数値条件より優先する

起算点と集計定義:

- 起算点は、結果が「発生確認済み」の前回圧縮の直後とする
- 完了の数え方は runbook の「ステータスの導出規則」の完了条件と同じ（実装 Issue は主 PR のマージ、調査 Issue は報告 PR のマージ）
- 巡回は開始時点で 1 回と数える

打ち切り:

- 圧縮後も使用率 70% を下回らない場合はその区切りで再圧縮しない（次の区切りで改めて判定する）
- 圧縮操作が 2 回連続で失敗したら繰り返さず、交代または人間確認へ進む

数値は暫定で、導入後の観測で見直す（下の「観測と見直し」）。

## 操作発行時の記録（常時ルール）

結果を伴う操作（マージ、ラベル、コメント、スレッドへの指示・起動、ステータス変更）は、発行前に種類・対象・照合識別子を巡回記録に残し、結果確定後に追記する。この記録が結果不明の操作の照合の土台になる。事前に識別子を確保できない操作は実行先での照合方法を併せて残す（例: スレッドの起動なら割り当て ID とスレッドの link、コメントなら対象 Issue・PR と内容の先頭）。

## 圧縮前の外部化チェック（チェックリスト）

計画的圧縮の直前に、次のすべてを確認する。1 つでも残っていれば圧縮しない。

1. 割り当てと次アクション: 巡回記録（割り当ての記録の表）が現状と一致し、各案件の次アクションが書かれている
2. patrol-state の 4 項目（誰待ち・待ち始めた時刻・次の担当・次回確認時刻、Issue #255・#307）が全対象で埋まっている
3. 未記録の判断: セッションの文脈だけに置いている判断が無い。すべて巡回記録か Issue/PR のコメントに書かれている
4. ボード Status の確認: 全カードの Status が導出値に補正済みであること。確認方法は、Issue #290 の正本化後は runbook の「ステータスの導出規則」を参照し、正本化前は agent-team.md の既存の決まりに基づく暫定確認に限る
5. 識別子つきの「復元検証待ち」記録を巡回記録に事前に作る（圧縮前の状態の要点と、復元で照合すべき識別子を書く）
6. 圧縮未実施のとき（トリガーを満たさない、延期した）は、検証待ち記録を「見送り」として閉じ、見送りの理由（使用率・代理指標の値）を追記する

## 復元検証

入口は 3 つ: 圧縮直後、巡回開始時、異常検知時（前提と実状態の食い違いに気づいたとき）。入口のいずれかで、正本の読み直しと、情報種別ごとの照合先からの再構成を行う。

| 情報種別 | 照合先 |
|---|---|
| 状態=GitHub | Issue のラベル・状態、PR の Draft・レビュー・チェック、ボード Status |
| 担当スレッド=巡回記録と実行先 | 割り当ての記録と `t3 thread list` |
| 判断=巡回記録 | 判断の記録と Issue/PR のコメント |
| 待ち=patrol-state | patrol-state.json の必須項目 |

GitHub 内部で食い違いがあれば既存規則（runbook の整合チェックと「ステータスの導出規則」）で解消し、解消不能なら依存操作を保留する。

復元検証の終了は 2 つに区別する。

- **完了**: すべての情報種別で照合が済み、矛盾が無い
- **部分復旧**: 照合できなかった項目がある。未解決事項・停止対象（その間進めない操作）・停止の解除条件を記録し、毎巡回の開始時に継続照合する。解除条件が揃ったら完了にする

## 結果不明の操作の照合

操作発行時の記録（常時ルール）を使い、実行先ごとに結果を照合する。スレッドへの指示はスレッドの履歴と GitHub の実状態、マージ・ラベル・コメントは GitHub の実状態、スレッドの起動は割り当て ID とスレッド履歴で照合する。

照合手段がない操作は結果不明のまま保留し、依存する後続操作を止める。再実行しない（二重実行のリスクが残るため）。

## 圧縮の結果の区分

圧縮の結果は次の 3 つに区分する。

- **発生確認済み**: 圧縮が走ったことを記録（セッションのトランスクリプト等）で確認できた
- **未実施・失敗**: 計画的圧縮を見送った、または圧縮操作が失敗した
- **発生不明**: 実行した（または自動圧縮の疑いがある）が、確認できなかった

起算点の更新と圧縮成功回数の計上は「発生確認済み」の場合だけ行う。

## 予期しない圧縮

環境の自動圧縮を検知したら、通常操作を止めて検証待ち記録を作り、復元検証へ進む（runbook の巡回開始手順も、未完了の復元検証待ち記録があれば復元検証から始める）。

自動圧縮の有無と検知方法はプロバイダごとに異なる（検証記録は `docs/dev-environment.md` の「指揮役スレッドのコンテキスト圧縮の検証」）。自動圧縮が無いプロバイダではこの経路は発生せず、自動圧縮があってもエージェント会話内で検知できないプロバイダでは、検知手段を持つ環境側（フック・ログ・DB 等、検証記録参照）を併用できない限り発生を検知できない。検知方法が未検証の環境では、巡回開始時の状態再取得に加え、重要操作（マージ、割り当て、ステータス変更）の直前に正本・巡回記録・実行先の状態を照合する。この照合を実施できない環境は有効化対象にしない。

## 恒久交代

圧縮で改善しない場合（再圧縮を重ねても使用率が下がらない、圧縮操作の失敗が続く）の手段として、新指揮役スレッドへの恒久交代がある。手順 5（代行）は一時代行（正本の指揮役へ戻す前提）であり、恒久交代には操作権限の移譲点・確認失敗時の不移転・同時稼働の禁止の明示が不足するため、この節が恒久交代の正本。

1. 旧指揮役は、案件を進行させる操作を止める（スレッドの起動・指示、マージ、ラベル、コメント、ステータス変更のすべて）
2. 新指揮役スレッドを立てる（skill `command-team` の手順 5（代行）の開始のチェックと同じ条件）。1 より先に立てて待たせてよい（操作権限は 4 で移る。下の「始め方」はこの順）
3. 新指揮役が引き継ぎ確認を行う（GitHub の実状態、patrol-state、巡回記録、実行中スレッドの照合。runbook の「引き継ぎの発動条件と順序」と同じ順序）
4. 引き継ぎ確認の完了時点で操作権限が移る。確認が完了しない場合は権限を移さず、旧側の復旧または人間確認に進む
5. 旧・新の同時稼働の禁止: 権限移行後、旧指揮役はいかなる操作も行わない（見張り `conductor-watch` の停止を含め、停止の操作は引き継ぎ確認の中で新旧どちらか一方だけが行う）

始め方: hatai がホストの端末で、必ず本体 checkout の `scripts/conductor-rebuild --from '<旧指揮役のスレッド ID>'`（または本体 checkout で `mise run conductor-rebuild -- --from '<旧指揮役のスレッド ID>'`）を実行する。worktree の版は sandbox の中から書き換えられるので実行しない（スクリプトは worktree から起動されると止まるが、これは書き換えられていない版を誤って起動したときの止め具で、書き換えへの守りにはならない）。旧指揮役のスレッド ID は、hatai がホスト側の T3 の画面か `t3 thread list --json` の `threadId` で確かめ、単一引用符で囲んで渡す。provider・model・effort を替えるときは `--provider`・`--model`・`--effort`（省略すると provider と model は旧指揮役と同じで、effort は渡さず、渡さないことを表示する）。スクリプトは次の順で進め、どこかで失敗したら、その先は行わずに止まる。
1. 新指揮役を、main から作った専用の worktree（`t3 thread start --worktree main`）で立て、何もせずに待たせる決まった文を送る（`--to '<新指揮役のスレッド ID>'` を渡したときは立てずに、そのスレッドを使う）
2. 新指揮役の権限（`runtimeMode`）が旧指揮役と同じで、`full-access` でないことを `t3 thread show` で確かめる。`t3 thread start` には権限のフラグが無く、本体のプロジェクトの既定は `full-access` のことがあるため。合わなければ、旧指揮役には何も送らず、宛先も変えずに止まる。hatai が T3 の画面で新指揮役の権限を旧指揮役と同じに直し、表示された `--to` 付きのコマンドで実行し直す
3. 決まった停止の文を旧指揮役に送り、終わるまで待つ
4. 新指揮役に引き継ぎの指示を送る
5. agent-watch の起こしの宛先を、インストールした `~/.local/bin/pelway-agent-watch --register` で新指揮役に替える（入っていなければ、最初に何もせずに止まる）

新指揮役を worktree で立てる理由（hatai の判断。Issue #564 のコメント）: 本体 checkout で立てると、そのスレッドの sandbox の書き込み範囲が本体 checkout（作業ツリーと共有 git dir の `index`・`refs/`）になり、hatai がホストで実行するスクリプト・`mise.toml`・cargo の入力・pitchfork の定義を指揮役が書き換えられる。worktree で立てれば、本体 checkout は sandbox から書けないままになる。今の指揮役が本体 checkout で動いているときは、そのスレッドが本体 checkout を書けるので、交代の前に hatai が本体 checkout に変更が無いことを確かめる。

新指揮役は、恒久交代の手順 4（引き継ぎ確認の完了で操作権限が移る）の後に、旧指揮役のスレッドを `t3_thread_organize`（`action: settle`）で settle し、巡回の scheduled task を作り直す（runbook の「指揮役の定期巡回（スケジュール起床）」。`t3` CLI には settle が無いため、スクリプトでは行わない）。

交代も含め、その環境で検証済みの手段だけを使う（段階導入）。

## 導入条件

環境（指揮役を動かすプロバイダを含む）ごとに、次の 4 つが検証済みであること: 「圧縮操作の実行方法」「圧縮の検知方法」「使用率の取得方法（取得できる場合）」「交代手順」。検証はプロバイダ単位で行い、記録は `docs/dev-environment.md` の「指揮役スレッドのコンテキスト圧縮の検証」に置く。検証が古くなったとき（プロバイダの更新で圧縮の仕組みが変わりうるとき）も同じ場所に記録し直す。

未検証の環境では本仕組みを有効化しない。圧縮も交代も実行せず、外部化チェックだけを行って操作を止め、人間に確認する。

## 観測と見直し

トリガー発生・実施・延期・異常検知・交代の各イベントを、発動理由・取得できた使用率・代理指標の値・照合結果・採った対応とともに巡回記録に残す。

暫定数値（使用率 70%、完了 Issue 5 件、巡回 75 回、打ち切りの連続 2 回）の見直しは、環境ごとに圧縮成功 10 回または導入 1 か月のどちらか早い方になった時点で、人間が判断する。
