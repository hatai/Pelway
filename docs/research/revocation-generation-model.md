# 承認と資格の失効が再取り込みで復活しない世代管理の検討

## 結論（推奨）

- 世代（対象ごとの単調な版数）で失効を表す方式を**採用する**ことを推奨する。
- 記録形式は「対象（subject）の行が持つ単調な `generation` 列」と「参照側が作成時に刻む `(workspace_id, subject_kind, subject_id, generation)`」の組を推奨する。全社共有の時計（Buzz の `protectionClock` 相当）は採らず、世代は対象の識別子ごとに独立して進める。
- 再付与の形は subject_kind ごとに決める（記録形式の節の表）。いずれの形でも、失効済みの世代を参照する承認・資格・委任は復活しない。
- 採否の最終判断は Issue #198 の未決事項として hatai が行う。この文書は検討と推奨であり、実装・既存 ADR の改訂は行わない。

## 前提と調べた範囲

- 「復活しない」とは、失効・削除・期限切れにした権限が、同じ鍵・同じ内容・同じ主体の再取り込み・再付与で、失効前の継続として扱われないこと。再付与そのものを禁じる意味ではない。
- 出発点は Buzz（block/buzz-app）の `docs/agent-protection.md` の `protectionClock`（Issue #198 の「採用する方式」より）。Pelway 側の根拠は ADR-0001・0002・0007・0009 と `docs/technical/v0.7/body/` の 03・04・10・11・12、および認証試作 `crates/pelway-auth`。

## Buzz の方式（出発点）

Buzz は version 4 の保存形式で、全所属行と単調な `protectionClock` を同じ場所に置く。

- ポリシー変更と所属の確定はその時計から世代を割り当てる。
- 所属の参加は身元の世代を写す。既定値だけの書き込み・削除・最後の身元の忘却は時計を維持する（戻らない）。
- 同じ公開鍵を再取り込みしても以前の世代は復活しない。
- 保存は compare-and-swap の版で行い、古い写しは仕事を拒否して再読込する。古いハンドルは取り消す。
- Codex は保護の `stateKey` をスレッドに記録し、同じ鍵の下でだけ再開する。ポリシー変更や保護の切替で新しいスレッドになる。

要点は、失効も変更も「戻らない時計から新しい世代を割る」ことで、復活を状態の巻き戻し禁止として定義し直している点にある。

## Pelway に既にある世代・版の機構

Pelway には世代に相当する機構が対象ごとに点在する。名前と粒度が揃っておらず、「復活しない」ことを 1 つの約束として説明する層がない。

- grant の失効 `epoch`：停止は epoch を増やし、broker token と新 dispatch を拒否（10、04、11）。
- 通信根拠の `epoch`：`communication_basis_records` が `basis_version`（内容の版）と `epoch`（有効性の世代）を分けて持ち、撤回は epoch を進める（12）。
- `context_authorizations` が `basis_refs/epochs` を記録し、実行点ごとに照合する（12）。
- 承認の版：snapshot は不変、決定は `approval_version_id` に結び付き、予約は `unique(workspace, approval_version_id)`。内容変更は再承認（03、04、ADR-0002、ADR-0009）。
- run の `fence`：リースを取るたびに増やし、古い token の更新・新 dispatch を拒否（03）。
- 取消の順序：`cancel_accepted_at` の commit と開始受理を一意に順序化（03）。
- 開始資格：発行から 5 秒・一回消費・重複要求や再起動で再発行しない（03、04）。

## 「復活しない」の定義

失効は、以後の利用・開始・照合を拒否する方向の状態遷移。再付与は、失効した対象と同じ実体（同じ人・同じ鍵・同じ型・同じ連携）への権限の付け直し。「復活」とは、再付与によって失効前の継続関係（旧世代に結び付いた承認・資格・セッション・委任・記憶・進行中の予約）が再び有効になること。防ぐ姿は、再付与が新しい世代として始まり、旧世代を刻んだ参照だけは通用しない、という形。

## 対象ごとの失効と再付与の意味論

### 承認（承認カード・型の決裁）

- 失効：期限切れ・取消・対象内容（本文・宛先・添付・account・scope）の変更で、その版からの予約・開始資格の発行・型一致の自動実行を止める。承認は不変 snapshot への決定なので、内容が変われば別の snapshot であり、失効済み版は以後の根拠に使えない。
- 再付与：同じ内容への再承認は新しい承認版（新 `approval_version_id`）として記録する。旧版の復活ではなく監査上も別の決定。型は版管理済みで、変更・停止後の再有効化も新版の再決裁（ADR-0009）。
- 「復活しない」の保証：失効済み版への予約・資格発行を常に拒否し、版番号を再利用しない（削除→再作成で版が初期値に戻らない）。担当交代で承認を保つかの残課題（03）は「新版への付け直し」側に倒すと世代と整合する。

### 資格（passkey・IdP・セッション・broker token・連携 credential・BYOK 鍵）

- 失効：認証試作（`pelway-auth`）はセッションの行削除で、credential 取消が member の全セッションを消す。broker token は短命かつ scope 限定で、実効の失効点は grant epoch の照合（開始受理と同じ transaction 内の検査、03 の手順 7）。
- 再付与：同じ公開鍵・同じ credential の再登録・再取り込みは新しい資格の世代とし、旧世代に紐づくセッション・grant 由来の権限・未消化の承認を引き継がない（Buzz の「同じ公開鍵の再取り込みで以前の世代は復活しない」の翻案）。
- 「復活しない」の保証：資格の世代をセッション・broker token・credential ref に刻み、世代の一致しないものを拒否。バックアップ復旧で古い資格行が戻っても、復旧範囲の外に独立して置いた失効台帳（記録形式の節）の status 再適用と世代照合で使えない（12 の「復旧した古い同意・ACL・資格情報で自動再開しない」に対応）。

### ポリシー（core_domestic_policy・integration grant・PlacementPolicy・会社ルール・Bot の許可 policy・型・通信利用の根拠版）

- 失効：ポリシーの変更・撤回は新しい版（世代）とし、旧版に結び付いた承認・`context_authorization`・grant の有効化は新版で通用しない。PlacementPolicy の版変更は影響する grant を再同意まで停止（11）。同意撤回は目的・scope の epoch を進め、以後の入力・検索・再利用・公開・外部提供を拒否（12）。
- 再付与：「元に戻す」は旧版の復活ではなく新版として記録する。監査・snapshot・`context_authorizations` が版・epoch を記録するため、同じ版番号の再発行は「どの内容を承認・同意したか」を曖昧にする。
- 「復活しない」の保証：版の単調性（同じ版番号を二度発行しない）。内容の版（何を決めたか）と有効性の世代（いつまで有効か）の扱いは記録形式の節。

### AI の所属（AI Bot のメンバー所属と委任）

- 失効：メンバーの削除・Bot の停止で、所属に結び付いた委任・チャンネル権限・進行中の委任範囲を失わせる。実行中の run は lease/fence で runner を切る。記憶参照（source・根拠・期限付き）は所属とは別の保持条件で残る。
- 再付与：同名・同役割の Bot の再作成・再招待は新しい所属世代とする（Buzz の「参加は身元の世代を写す」の翻案）。旧所属に結び付いた未消化の承認・委任・セッション・checkpoint・進行中 task は引き継がない。
- 「復活しない」の保証：委任・承認依頼・task 担当・記憶参照は所属の世代を刻み、世代の切れた所属からの権限行使を拒否。member 識別子を再利用しなければ、復活と新規を機械的に区別できる。

## 世代方式の採否

**採用を推奨する。**

- 機構が既に存在する。epoch・fence・版・`cancel_accepted_at` の順序付けは、いずれも「古い世代を拒否する」世代機構の部分実装。統一の語彙と記録形式に載せ替える費用は小さい。
- 「復活しない」を一つの機構で説明できる。対象ごとに tombstone や状態列を増やす方式（世代を採らない案）では、「同じ識別子の再付与が旧世代を復活させない」ことを別の制約で書く必要があり、監査の版・epoch 照合と整合しにくい。
- 検査点が決まっている。開始受理・承認確定・broker 発行・根拠照合は、すべて「記録時の世代と現在の世代を同じ lock/transaction で比較する」形に統一できる（03 の手順 7 が雛形）。

世代を採らない代替は、失効を各行の状態列（active/revoked）だけで表し、再付与で新行を作る運用。行の削除と再作成で識別子・版が再利用されると監査の参照が曖昧になり、「旧世代として扱われない」ことを機械的に保証しにくい。

## 記録形式の推奨

- **世代の単位**：対象（subject）ごとの単調な版数 `generation`。対象の識別子は `(workspace_id, subject_kind, subject_id)`。subject_kind は approval・credential・grant・policy・membership 等。Buzz のような全店舗共有の時計は採らない。Pelway の照合は対象の識別子全体と世代の組、すなわち `(workspace_id, subject_kind, subject_id, generation)`（以下 `(subject, generation)` と略記）の単位で閉じ、対象をまたぐ順序は監査の `prev_hash` 鎖と `stream_pos` が既に担う。参照・照合を `subject_id` と世代の 2 項だけで行うと、別 workspace や別 subject_kind に同じ `subject_id` と世代を持つ行があったときに別対象の参照を一致と誤認するため、照合には必ず識別子の 3 項をすべて含める（`subject_id` を全 workspace・全 subject_kind で一意にする前提は置かない）。
- **同一行内の変更は 1 系列**：同一対象行への有効化・内容変更・失効は `generation` を 1 進める。12 の `basis_version` と `epoch` の併記は「内容の版」と「有効性の世代」を別列にした例で、同じ関係を版の写し（世代 n のときの内容）で表すこともできる。内容の同定に版を残す現行の設計を維持するなら併記でよい。
- **対象行**：`generation` を持つ。新規作成は 1 から、同一行への変更・失効は同じ transaction で `generation + 1`。
- **`subject_id` の再利用禁止**：`subject_id` は `(workspace_id, subject_kind)` の中で、削除・tombstone の消去・DB の復旧をまたいで再利用しない（例: ランダムな UUID。DB の復旧で巻き戻る採番は使わない）。復旧で採番が巻き戻ると、消えた行の id が別の主体の新しい行に再発行され、DB の外に残った旧参照（セッション・broker token 等）が新しい行に一致する穴になる。
- **再付与の形は subject_kind ごとに決める**：

  | subject_kind | 再付与の形 |
  |---|---|
  | approval | 新行（新 `approval_version_id`）。同じ内容への再承認は別の決定として記録する（承認の節、ADR-0002） |
  | credential | 新行（新 id）。同じ公開鍵・同じ credential の再登録・再取り込みも新行とする |
  | grant | 新行（新 id）。連携の再同意・再有効化は新しい grant として記録する |
  | policy | 同一行で `generation + 1`（新版）。「元に戻す」は旧版の復活ではなく同一系列の新版とする（ポリシーの節） |
  | membership | 新行（新 member id）。同名・同役割の再招待・再作成は新しい所属とする（AI の所属の節） |

- **照合は自然キーでなく識別子の組で**：参照は `(workspace_id, subject_kind, subject_id, generation)` の組で照合する。再付与が新行なら `subject_id` が異なり、旧世代を刻んだ参照は一致しない。公開鍵・型名・メンバー名などの自然キーでは照合しない。同じ公開鍵の再取り込みが旧行を復活させない根拠は、世代の値ではなく `subject_id` の違い（新行は 1 から始まるため世代の値が偶然一致することがあり、世代の値の比較だけでは復活を弾けない）。
- **新行で再付与する subject_kind の旧行**：`status` と最終 `generation` を残す tombstone とし、削除で消さない。
- **参照側**：承認・`dispatch_attempts`・`context_authorizations`・委任・セッション・記憶参照は、参照する対象の `(workspace_id, subject_kind, subject_id, generation)` を作成時に刻む。検査点では現在の世代と比較し、不一致を既定拒否する。既存の「検査時epoch/version/fence/hash」（04 の `dispatch_attempts`）はこの形の先駆け。
- **単調性の保証**：同一 `(workspace_id, subject_kind, subject_id)` で `generation` を戻さない。更新は条件付き（`generation = expected` の compare-and-swap）にし、古い写しからの書き込みを競合として拒否する（Buzz の compare-and-swap と同じ）。
- **失効台帳**：失効・制限の記録は対象行とは別に、追記型の失効台帳に残す。記録は `(workspace_id, subject_kind, subject_id, generation, status)` とし、同じ行で版を進める種別（policy）は最終版の内容への参照も持つ。台帳は対象行を含む DB の復旧範囲の外に独立して保管する（同じ DB 内の tombstone 行の集合では、バックアップ復旧で台帳ごと巻き戻るため保証にならない）。
- **復旧・再開**：復旧時は認可と外部 dispatch を既定停止したまま、台帳の status を再適用する。復旧した行の世代が台帳より古い対象は、`generation` を台帳の値を超える新しい世代へ進める（台帳の値に揃えるのではなく超える。世代の値を揃えるだけでは、status が有効のまま戻ったり、復旧前に刻まれた参照が復旧した古い内容の行に偶然一致したりする穴になる）。照合できない対象は停止のままにする（12 の復旧手順「認可と外部 dispatch を既定停止・独立保全した削除・制限・撤回の記録を再適用・現 ACL と根拠を再確認」に対応。10 の「独立制限記録を復旧前に再適用」と 04 の dispatch 検査にも対応）。
- **監査との関係**：`audit_events` の policy 版・snapshot 参照は `(subject, generation)` で揃える。世代の単位を揃えると ADR-0007 のチェックポイントで世代照合の欠落も検出できる。

## 競合と開始済み外部操作

世代照合が保証するのは「失効以後の新規利用・開始・照合の拒否」までである。開始済みの外部操作の巻き戻しは保証しない。08（D11）の区分に合わせる。

- 予約前の失効：検査点（開始受理・承認確定・broker 発行・根拠照合）で現在世代と記録世代を同じ transaction で比較し、不一致を拒否する。世代機構がそのまま防ぐ。
- 予約後・開始前の失効：予約と開始受理が別の時点で行われるため、開始受理時に再度世代を照合する。失効済み世代の開始資格は発行・受理しない。
- 外部開始後の失効：外部操作の取り消しは保証しない。停止要求は送るが結果は「別の追跡」として扱い、外部停止の確認は grant の停止確認記録（10）と同じ仕組みで別途保持する。12 の「開始後の外部結果は不明・取消を保証しない」に対応する。

実行中の run は fence・lease で runner を切り、未送出の dispatch を止める。送出済みの外部効果は世代では消せないため、「復活しない」の約束は開始点までと明確に区切る。

## ADR への改訂案（実施は対象外）

- ADR-0002 系：承認版の単調性（版番号の再利用禁止）と、承認者変更は新版への再決裁であることを明示する。
- ADR-0009 系：型の版管理を世代の語彙に揃え、内容の版と有効性の世代の関係を明記する。
- 04・12 系：`epoch`・`fence`・`version` を世代の語彙に統一するか、世代を上位語とする対応表を書く。

## 残る未決
