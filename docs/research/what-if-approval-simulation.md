# 承認ポリシーと型のwhat-ifシミュレーションの検討

## 結論（推奨）

- **作ることを推奨する**。ただし管理画面は作らず、型の決裁の判断材料を出す最小構成（機械的検査のみの過去再現レポート）から始める。採否の最終判断は Issue #195 の未決事項として hatai が行う。この文書は検討と推奨であり、実装・既存 ADR の改訂は行わない。
- 最小構成の要素は「型の草案と過去の実行記録の期間を入力に、機械的検査だけを再現し、自動通過（上限）・都度承認へ落下・拒否相当の3分類の件数と内訳を出す」こと。番人（モデル審査）の再現は含めない。
- OpenBot の what-if（単発の仮想操作に対する各制御の判定表示）は、Pelway の課題である「型の決裁」にはそのまま使えない。Pelway で必要なのは、過去の実行記録をまとめて再判定する集計である。

## 前提と調べた範囲

- 「what-if」とは、承認ポリシーや型の設定を決裁・有効化する前に、その設定で過去の実行がどう扱われたかを試算して見せる機能を指す。
- 出発点は CopilotKit/OpenBot の管理画面 `/admin/what-if`（Issue #195 の「採用する方式」より。公開リポジトリの `shared/what-if.ts`、`app/src/routes/_authed/admin/what-if.tsx` で確認）。
- Pelway 側の根拠は [ADR 0002](../adr/0002-designated-approver-and-expiry.md)（指定承認者・期限）、[ADR 0004](../adr/0004-declared-action-tiers.md)（操作の4段階）、[ADR 0007](../adr/0007-signed-audit-checkpoints.md)（監査チェックポイントと#187の輸出形式の補足）、[ADR 0009](../adr/0009-hybrid-approval-with-preapproved-types.md)（ハイブリッド承認・型の事前決裁）、および v0.7 技術仕様の [03 Bot実行](../technical/v0.7/body/03-ai-bot-runtime.md)と[04 データモデル](../technical/v0.7/body/04-data-api-realtime.md)。

## OpenBot の what-if（出発点）

OpenBot の what-if は、管理者が仮想の1操作（どのBotが・誰の権限で・どの起点で・どのツールや画面操作を）を組み立てると、製品が実際に使う判定器を本番と同じ順序で走らせ、制御層（grant、app_allowlist、capabilities、network、boundaries、safety、approvals）ごとに判定（allows / refuses / asks / hands_off / trial）と根拠となったルールを1行ずつ表示する。境界（boundaries）を試験モード（trial: 拒否として記録しつつ通す）で効かせる前に試せるのが目的である。また「Why did this happen?」として、監査行に記録された結果と今日の判定を並べて見せる。

要点は2つある。

- 判定に本物の判定器を使う。試算用の模倣ロジックを別に作らないため、設定と試算が乖離しない。
- 1操作ずつの前方シミュレーションである。過去の実行記録を期間でまとめて再判定し、件数の内訳を出す集計（replay）は OpenBot の what-if にはない。

## Pelway の what-if が答える問い

ADR 0009 の型の決裁者（ADR 0002 と同じ規則で指定された承認者）は、型の決裁カードに対して「この型で先月の送信を流したら何件が自動で通っていたか」を見て決めたい。同じ都度承認の繰り返しから型を提案する学習（ADR 0009。提案のみ、有効化は型への決裁）が出てきたときも、提案された型で過去を流すとどうなったかが判断材料になる。つまり Pelway の what-if は、OpenBot のようにこれから設定する制御の挙動を確かめる道具ではなく、**型の草案で過去の実行記録を再判定して集計する道具**である。

## 対象・入力・出力

### 対象

what-if で差し替えて試す設定は3つである。

| 対象 | 試すこと | 根拠 |
|---|---|---|
| 型 | テンプレート・宛先範囲・金額上限・データ範囲の組（版管理される草案版）に一致するか | ADR 0009 |
| 段階設定 | その操作の4段階（読み取り、取り消せる内部の書き込み、外部、取り消せない操作）の扱い。取り消せない操作は型による自動実行の対象外なので、試算でも都度承認側に残す | ADR 0004、ADR 0009 |
| 承認ポリシー | 型の決裁者・期限（切れたら自動実行を止める）と、一致判定の順序（機械的検査が先、次に番人） | ADR 0002、ADR 0009 |

### 入力

- 型の定義（未決裁の草案版でよい。決裁前の試算が目的）。
- 過去の実行記録の期間（開始日・終了日）。期間内の社外に出た操作（承認を得て実行されたもの、拒否されたもの、型で自動実行されたもの）が再判定の対象になる。

### 出力（3分類の件数と内訳）

| 分類 | 意味 | 内訳 |
|---|---|---|
| 自動通過（上限） | 型に一致し、機械的検査（宛先ドメイン、金額、添付の有無、初めての宛先か）に合格する件数。番人を含めないため上限である | 検査項目ごとの合格数 |
| 都度承認へ落下 | 自動実行できず都度承認に落ちる件数（fail-closed） | 型不一致、宛先範囲外、金額超過、添付あり、初めての宛先、取り消せない操作、期限切れ・停止中 |
| 拒否相当（危険信号） | 期間内に人が承認を拒否した操作のうち、この型だと自動通過してしまう件数 | 拒否された操作の内訳 |

拒否相当を独立した分類にする理由は、過去に人が「送らない」と判断した内容まで通す型は、件数がどれだけ多くても決裁されるべきではないからである。自動通過の内訳と合わせて、決裁者が最初に見るべき数である。

### 番人（モデル審査）を含める場合の注意

ADR 0009 の一致判定は機械的検査の後に番人（意味的逸脱のモデル審査）を置く。過去分に番人を回す再現は、(a) 過去の全件にモデル審査の費用がかかる、(b) モデル審査は非決定性があり同じ入力に同じ結果を返さないため決裁材料としての再現性が弱い、の2つから最小構成には含めない。機械的検査のみの試算は自動通過の上限を与え、番人はそれを減らす方向にだけ働くため、上限を示すことで決裁の判断材料として十分使える。番人を含めた試算の要否は残る未決とする。

## 監査ログ（ADR 0007・#187 の輸出形式）との関係

- **輸出された監査ログだけでは試算を再現できない。** ADR 0007 の補足（#187）が定める JSONL 輸出は `audit_events` 行の写しで、メッセージ本文・ツール引数・秘密を記録しない。機械的検査の入力になる宛先ドメイン、金額の抽出元の本文、添付の有無はこの「記録しない項目」に当たるため、輸出先だけで再判定は組み立てられない。
- **試算の入力は DB の実行記録から取る。** [04 のデータモデル](../technical/v0.7/body/04-data-api-realtime.md)の `action_snapshots`（action_kind・操作・宛先・本文・添付hash・account・scope・policy版。snapshotは不変）、`external_actions`（logical operation と固定payload）、`dispatch_attempts`（承認・試行履歴）が再判定の入力になる。snapshot が不変なため、期間を遡る再現性がある。金額は本文からの抽出になるため、型の金額上限と同じ抽出規則を試算でも使う必要がある（判定器を共有する理由は下記）。
- **監査ログの役割は照合。** `audit_events` は操作と結果（どう扱われたか）と policy版を記録し、ADR 0009により自動実行の全件に根拠となった型の版を結び付ける。what-if の「過去にどう扱われたか」側（現状の都度承認・拒否・既存の型での自動実行の実績）は監査ログから揃えられ、試算結果との突き合わせ（OpenBot の「Why did this happen?」に相当）に使える。
- **期間の上限は実行記録の保持による。** 監査ログの保持は既定365日（ADR 0007 補足）。what-if で試算できる期間は `action_snapshots` 等の実行記録の保持期間に依存し、両者は別の保存単位である。試算可能期間の上限をどこに揃えるかは残る未決とする。
- **what-if の実行自体の記録。** 試算は社外に出ない読み取りであり、ADR 0004 の段階では読み取り相当である。試算で外部副作用は起きないため監査記録は必須でないが、決裁の根拠としてどの型草案・どの期間の試算を見たかを型の決裁カードに残すか（試算結果の要旨の添付）は実装 Issue で決める。

## 推奨（作る／作らないと最小構成）

**作ることを推奨する。** 理由は次の4つである。

1. 型の決裁は自動実行の範囲を決める影響の大きい判断で、ADR 0009 が決裁の質を前提にしている（期限、即時停止、日次ダイジェストは事後統制であり、決裁前の見通しを与えない）。
2. 入力データが既にある。`action_snapshots` は現行の都次承認の記録として既に蓄積され、試算のために新しい記録を足さない。
3. 機械的検査は決定的なので、過去分の再現が正確にできる。試算には本物の判定器（機械的検査の実装）をそのまま使い、模倣ロジックを作らない（OpenBot と同じ原則）。設定と試算が乖離しない。
4. 学習による昇格提案（ADR 0009）の判断材料になる。提案が出ても決裁者の確かめ手段が無ければ提案の価値が下がる。

**最小構成**は次のとおりである。

- 管理画面は作らない（Issue #195 の対象外）。CLI（検証コマンド）として、型の草案（JSON 等のデータ）と期間を引数に受け取る。
- `action_snapshots` / `external_actions` / `dispatch_attempts` に対して機械的検査（ADR 0009 の検査項目）を本物の実装で再現し、3分類の件数と内訳を標準出力にレポートする。
- 番人の再現は含めず、自動通過は上限として示す。拒否相当（人が拒否した操作が型で通るか）を出す。
- 実装は ADR 0009 の実装 Issue の一部、または後続 Issue とする（この文書は検討まで）。

**作らない場合**に失われるものは、決裁者が「過去の実績に対する見通し」を決裁前に得る手段である。日次ダイジェストは有効化後の事後確認であり、決裁前の試算を代替しない。この費用（クエリと集計の実装）は小さいため、作らない理由を見出せない。

**OpenBot 方式（単発の仮想操作に対する判定表示 UI）を採らない理由**は、Pelway の課題が型の決裁であり、単発操作の判定結果は都度承認カード（snapshot と承認の集合）が既に示しているためである。設定変更の前に1操作ずつ確かめる必要性が生じたとき（例: 段階設定の確定作業）に、UI の有無は別途判断する。

## 残る未決

- 要否の最終判断（Issue #195 の未決事項、hatai）。
- 番人（モデル審査）を含めた試算を決裁材料に使うか（費用と非決定性の取り扱い）。
- 試算結果の要旨を型の決裁カードに添付する形式と、試算実行自体の監査記録の要否。
- 試算可能期間の上限（実行記録の保持期間を監査ログの365日に揃えるか）。
