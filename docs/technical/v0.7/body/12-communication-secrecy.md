# 12 通信秘密・目的別根拠・可視範囲・運営アクセス

J-S01〜07の推奨は暫定採用済み。この章は当該方針を具体化する参照仕様であり、法的適合・実装済み対策の認証ではない。未決の正本は[08 U01〜07](08-decisions-open.md)。§番号は本章内の番号で、旧追補の§2〜9との追跡を維持する。

<a id="ch12-s02"></a>
## 2. 判定する対象と責任

通信の秘密の対象分類は本文だけにしない。通信相手、日時、channelやthreadの関係、配送情報、通信の存在を示す件数、検索候補、監査情報も、個別の通信との関係に応じて対象とする。識別子やhashだけでも、他の情報と結び付けば秘密を明らかにする場合がある。

`actor`は既存のhuman、bot、external_agent、external_toolを維持する。Botの参加は技術上の権限設定であり、必要な人や法人の同意を作らない。会社管理者は会社方針と委譲権限を設定する。運営者は適用する根拠と実行制御を確認する。操作を承認する社員は当該操作の権限を持つ。三者の責任を一つの「利用者責任」で置換しない。会社による連携有効化、権限者の個別操作承認、通信当事者の同意等を含む利用・提供の法的根拠は別に記録する。管理者権限やデータの閲覧権限だけで、代理権や外部提供権限があるとは扱わない。Botの自動全履歴読取や常時要約を追加せず、v0.6のメンション起動を維持する。

広告、モデルの学習・fine-tuning、会社横断の分析、別taskの人格メモリへの転用は初期不許可とする。要約・メモリへの同意を、モデル重みへの学習許可と読み替えない。委託先にも同じ目的制限を適用する。

通常の配送等は、必要な正当業務行為等を根拠とする場合と、同意を根拠とする場合を分ける。「会社が便利と判断」「国内処理」「閲覧権限あり」「管理者が有効化」だけを通信秘密の法的根拠として登録しない。正当業務行為の根拠には、目的の正当性、必要性、手段の相当性と取扱範囲を記録する。

<a id="ch12-s03"></a>
## 3. 目的と根拠の表

各目的は本文とmetadataの分類、対象scope、取扱主体、説明版、保持方針を持つ。同意を使う場合は、必要な通信当事者又は具体的に委任された代理の同意が対象scopeを覆うことを確認する。本人を特定する記録と、同意の有効性・代理権を確認する記録は分け、単なるチェック済みフラグだけで充足としない。外部guestや取引先の通信を会社管理者一人の同意で覆ったとみなさない。

| 目的ID | 目的と対象 | 根拠の登録と初期制限 | 説明版・撤回時の扱い |
|---|---|---|---|
| P01 | 指定参加者への本文・添付の保存、配送、本人の履歴閲覧 | サービス提供に必要な正当業務行為等の範囲を確認。依頼された保存・配送を超えるAI分析へ流用しない | 基本サービスの説明版を保持。退会、削除請求、契約終了と任意AI同意の撤回を分ける |
| P02 | 配送障害、不正アクセス、課金、苦情等に必要なmetadata処理 | 必要最小限の業務上の根拠を定義。行動分析、広告、営業用閲覧への流用は禁止 | 目的、項目、保持、閲覧者を説明。保存の必要性を失えば消去。個別保全は別記録 |
| P03 | 依頼された国内AIの読取、要約、下書き | 対象の会話・履歴・添付、出力先、国内取扱主体を具体化した有効な同意等。未登録は無効 | 国内AI説明版を参照。撤回対象の以後の入力・再利用・出力を停止し、実行中は§5で扱う |
| P04 | Botの永続メモリ、将来の検索・RAG | P03と区別して将来再利用の範囲と期間を説明。単なる一回の要約承認から永続記憶を推定しない。RAGは初版必須外 | メモリ利用の説明版を保持。撤回で対象メモリとindexを検索対象から除外し、削除・隔離を処理する |
| P05 | 他のchannelや人への要約・引用・成果物公開 | sourceの全可視範囲内なら現在の権限と目的を再検査。範囲を広げる開示は別の権限と法的根拠が必要 | 出力先を説明scopeに含める。元の根拠失効後の新規公開を停止する。公開済みコピーの回収は保証しない |
| P06 | 外部AI、業務APIへの本文・metadata提供 | 会社のgrant、個別snapshot承認、通信秘密の提供根拠を別々に確認。個人データにはAPPI上の委託・外国移転等も確認 | 受領者、目的、対象、保持、再利用、国外情報等の説明版を参照。変更と撤回は影響する範囲だけ再判定 |
| P07 | 認証と能力確認 | 接続に必要な項目と宛先だけに限定。業務内容を含む確認要求はP06へ分類 | 接続説明版を保持。資格情報取消で通常の利用を停止。限定照会権限は別に明示 |
| P08 | supportの内容調査、本文を伴わない事故対応 | 内容調査は§7の具体的依頼、必要な根拠、実行者とは別人の適切な顧客側承認、最大60分の一時権限を要する。緊急本文アクセスは初期非提供。事故対応は本文を見ない隔離・停止と必要最小の診断に限定 | 目的・範囲・期限・承認と対応証拠を保持し、事故対応の審査と通知可否を記録 |

P03、P04、P06を根拠なしに有効とする初期設定は認めない。P01とP02の必要処理まで、任意AIの同意と抱き合わせにして拒否不能の同意を作らない。

<a id="ch12-s04"></a>
### 3.1 同意の取得と版の変更

利用開始時又は参加時に、機能ごとの対象情報、主体、目的、方法、対象履歴、保持、撤回方法を具体的に示し、その範囲の事前同意を取得できる設計とする。個別操作承認は、既存の製品安全契約として別に維持する。

必要当事者の範囲や代理権は§10 J-S01で確認する。事前同意が有効な範囲の処理について、全メッセージごとに全員の再クリックは求めない。反対に、明示した範囲を超えるAI利用や外部提供を、会社管理者の一括同意で追加しない。

新規参加者が同意しても、過去の通信当事者の根拠や過去履歴の閲覧権限が自動で増えることはない。必要な当事者の根拠が欠ける会話はAI入力から除外する。混在するデータから安全に分離できなければ処理全体を拒否する。

説明文の版、目的の版、権限の版は区別する。宛先、取扱主体、利用目的、データ分類、保持、公開範囲を実質的に拡張する変更は、影響するscopeを保留して必要な再同意を得る。表記修正だけで全件再同意にしない。変更が実質的かの判定と理由を保存する。新目的への同意を後から取得して、過去の無根拠な利用を適法化したと扱わない。

参加時の説明は、根拠確認済みの通常配送等と任意AIに分ける。前者は必要処理の説明、後者は目的ごとに短い説明と初期オフの選択を置く。任意AIを断っても通常利用できることを明示し、全目的を一括選択するボタンを置かない。通常処理に別途同意が必要な場合は、必要処理と表示するだけで取得済みとせず、確認した根拠に応じて扱う。

同意時点の推奨候補は、channel参加時に自分の発言をAIに読ませる範囲を選び、本人の依頼で機能を使う時点ではその依頼に必要な同意等を確認する組み合わせである。呼出者一人の初回同意で他の参加者の発言を覆わない。参加時の説明を超える過去履歴やguestの代理同意も推定しない。正式な同意主体・代理権・取得時点はJ-S01で確認する。

入力を一部除外して処理できる場合、出力を会話全体の検討結果と見せない。出力先が除外元の存在を知る権限も持つときは、同意不足による除外なら出力の先頭に06のnotice-ai-input-excluded「一部の発言を除外して処理しました（利用の同意を確認できない範囲）」を出す。誰が同意していないかは名指ししない。件数等は元channelの現閲覧権限と業務上の必要性を検査した相手だけに返し、個別の同意状態・理由は権限のある本人又は管理担当に限定する。存在自体を知らせられない出力先では、発言の存在や同意状況を示さず06のnotice-consented-scope-only「許可された範囲だけを参照しました」とするか、漏えいを避けられなければ出力を保留する。件数をchannel内全員に見せるか依頼者に限るかはJ-S02に残す。

撤回は初期設定又は明示した窓口で受け付け、対象目的・scope、受付時刻、反映状態を確認できる形にする。取得より不当に難しい手順にしない。復帰には当該scopeの新しい有効な根拠を記録し、旧runを自動再開しない。

### 3.2 最小データ契約

既存の`integrations/grants`の同意版と失効epoch、`action_snapshots/approvals`、`audit_events`を利用する。ただし、連携設定の同意と通信当事者の根拠を同じ列で代用しない。次の名称は論理上の保存単位であり、確定DDLや新サービスの指定ではない。

| 保存単位 | 最小項目・制約 |
|---|---|
| `communication_use_policies` | `workspace_id, purpose_id, version, data_classes, source_scope, processors, allowed_outputs, explanation_version, retention_policy_ref`。変更前の版は証拠参照として残す |
| `communication_basis_records` | `workspace_id, basis_id, basis_version, basis_type, purpose_id, scope, party_coverage_ref, grantor_ref, representative_authority_ref, explanation_version, evidence_ref, collected_at, effective_at, expires_at, withdrawn_at, withdrawal_method_ref, status, epoch`。必要な当事者と代理権の確認方法を保持。人物情報や本文の不要な複製を避ける |
| `context_authorizations` | `task/run/snapshot_ref, purpose_id, source_manifest_ref, source_acl_versions, basis_refs/epochs, decision, reason, checked_at`。承認時の証拠であり、将来の無条件な通行許可にしない |
| 派生物の属性 | artifact、memory、index、checkpointに`source_refs, access_scope_ref, purpose_ids, basis_refs, retention_policy_ref, expires_at, restricted_at, deletion_state`を関連付ける。元との関係が不明なら公開・再利用しない |
| 運営アクセスと削除記録 | `support_access_grant`に目的、対象、担当、根拠、承認者、期限。削除・制限記録に対象ID、種類、発効順序、保全理由、処理結果を保持。本文を削除記録へ複写しない |

根拠の有効性は`active`等の状態、期間、scope、目的、必要当事者の充足で決める。`pending`、欠落、不明、期限切れ、撤回済みは同意根拠として使わない。同意不要の処理は、確認済みの別の根拠を登録する。失効を避けるために実行中だけ根拠の種類を付け替えない。

### 3.3 初期機能の根拠確定用表

下表は実データ利用前に埋める確定用の台帳である。実在の同意者、取得担当、委任、法的根拠が既に確認された記録ではない。具体的な通信当事者は送受信と契約の事実から法務が確認し、会社代表、管理者、呼出者又はchannelメンバー全員のどれかへ一律に置き換えない。候補の根拠名だけを登録して有効化しない。

| 初期に対象とする機能 | 必要な通信当事者の確定 | 同意取得者・根拠確認担当 | 代理権の確認方法 | 使う根拠と確定状態 |
|---|---|---|---|---|
| P01/P02 通常保存・配送と必要metadata | 対象通信の送受信主体・法人と個人の関係を特定。未確定 | 取得又は確認を行う運営/顧客の権限者を記名する。未指定 | 代理取得をする場合だけ、委任者、委任内容、対象目的、履歴、期間を証拠参照で確認 | サービスに必要な正当業務行為等の範囲を個別確認。追加AIへの流用は不可。未確定 |
| P03 国内AIの読取・要約・下書き | 入力に含む発言・履歴・添付の当事者と対象範囲を特定。未確定 | 参加時等の範囲別説明を届け、本人又は確認済み代理から取得する担当を記名。未指定 | 会社による委任で覆える範囲と社員・guest等の個別範囲を分け、委任証拠を確認 | 具体的な事前同意等を使えるか事実に当てはめる。呼出者の承認だけでは不足。未確定、対象AI利用は無効 |
| P05 成果物公開・既存の引継ぎ | sourceと出力先の当事者・現閲覧権限を特定。未確定 | 元の根拠との整合と拡張時の説明を確認する担当を記名。未指定 | 元の委任に新受領者・目的が含まれるか確認。不足する代理権は推定しない | source内でも目的と現在の根拠を再検査。公開範囲拡張の根拠は別確認。未確定の公開は無効 |
| P06/P07 選択外部連携と認証 | 認証通信と操作データを分け、通信当事者、提供主体、受領者を特定。未確定 | 連携条件の確認担当、必要な同意の取得担当、操作承認者を別に記名。未指定 | 会社の連携許可だけで提供代理権を作らず、委任scopeの証拠を確認 | 通信秘密の利用・提供根拠とAPPIの適用根拠を別確定。未確定の業務データ提供は無効 |

P04の永続メモリ・検索を初期提供へ加える場合は、目的・期間・必要当事者を分けた行を追加してから有効化する。将来のRAGやwikiを今回の必須機能へ戻さない。通常の内容調査P08は§7の別記録を使い、緊急本文アクセスは非提供のままとする。J-S01/J-S06は自由選択できる製品設定ではなく、必要な法務確認が済むまで機能又は不足scopeを無効に保つ条件である。

## 4. 可視範囲の継承表

認可はserverで強制する。UIで隠すだけにしない。会社境界の複合FK、全取得経路のchannel認可、失効時tombstoneは[v0.6/04:7,31,58–66](../sources/v0.6/fixed/pelway-technical-docs/04-data-api-realtime.md)を継承する。

| 対象 | 採用時の可視範囲と継承規則 |
|---|---|
| 通常・非公開channel | 明示されたchannelメンバーと役割だけ。参加前履歴を含む対象期間は会社方針で明示。方針未設定の過去履歴は返さない |
| DM | 限定参加者channelとして扱う。会社管理者を自動的な閲覧者にしない。参加者追加は通常の権限変更として明示し、過去履歴を自動開示しない |
| thread | 親channelの可視範囲を継承し、広げない。thread固有の非公開機能は初期対象外。対応していないACL例外を黙って親公開へ落とさない |
| guest | 招待先channel、許可期間、許可された履歴範囲だけ。全社名簿、他channel、全社検索を自動付与しない。退出・期限切れで現在のアクセスを拒否 |
| 添付・作業画像・成果物 | 元message又はtaskのsource scopeを継承。storage keyやURLを知るだけでは取得不可。取得時にも現権限を検査。画像も同じ保持と削除を適用 |
| 要約・引用・下書き | source参照を保持。複数sourceを使う出力は、原則として全sourceへの現在の閲覧権限を持つ相手だけに公開。広い共有は別の開示根拠と承認がある場合だけ |
| メモリ・checkpoint・引継ぎ | taskとsourceの権限・目的を保持。他Botのvolumeや人格メモリ全体へ統合しない。新担当にも現在の権限と根拠を検査 |
| 検索・embedding・RAG | indexの作成前と検索結果の返却前に検査。本文、snippet、タイトル、件数、候補語から無権限sourceの存在を漏らさない。検索できてもAI利用の根拠は別に必要 |
| 通知・監査・履歴一覧 | 本文以外の相手・日時・channel名も同じ分類で扱う。非参加者の通知、検索候補、全社一覧へ秘密を出さない。運用目的の監査参照は§7で別に制限 |
| client cache・書出し | 現在の閲覧範囲だけを保存。logout、退出、権限取消で削除要求を適用。未管理端末の機密cacheは無効。コピー後の完全回収は保証しない |

複数のsourceの一部だけが許可される場合、許可部分だけの再生成は可能な範囲に限定する。禁止sourceの要約、存在、件数が混ざった結果をそのまま返さない。安全に分離できるか不明なら対象出力を保留する。

元の権限が変わった場合、保存時のACLだけで許可し続けない。出力を狭めたり安全に再生成できない場合は、出力を保留する。モデルに「秘密を出さないで」と指示するだけでは代用しない。

<a id="ch12-s08"></a>
## 5. 取消、撤回、削除の扱い

三つの操作を区別して記録する。取消受付、未開始抑止、外部への停止要求、実停止確認、送出・受領・副作用の結果は別の事実である。取消受付や停止要求の記録だけで「止まっている」「取り消しました」と表示しない。

| 受付の種類 | 効果 |
|---|---|
| task又はoperationの通常取消 | 対象の未開始処理を抑止する。開始済み操作は取消方針v0.3の競合と停止非保証を別に表示。法的根拠全体の撤回とはみなさない |
| integration grant取消 | 通常の新submit、更新、broker利用を止める。既存operationの停止・照会だけを残す場合は別の限定権限。全面取消を別accountで迂回しない |
| 通信利用の同意撤回・法的根拠失効 | 対象目的とscopeのepochを更新し、以後の入力、検索、再利用、公開、外部提供を拒否する。内部開始記録だけを送信許可にしない。別根拠で必要な保存・事故対応が残る場合は、その根拠と限定範囲を示す |

撤回を受けた国内AI runは停止可能な処理を止める。既に推論へ渡った情報を「渡していない」と扱わない。返ってきた結果は現在の根拠を再検査し、根拠を失った公開・メモリ書込み・外部送信を止める。作業用の入力、出力、cacheを削除又は利用停止し、処理結果を記録する。 対象には、利用している国内推論serverのprompt cache・slot保存、要約やメモリ作成用に一時fileへ書き出した入力、embedding indexを含める。llama.cpp等を使う場合も同じ分類を適用する。今回これらの製品や機能の新規導入は要求しない。撤回時にも§8.2のsource参照による影響範囲列挙を行い、除外前の発言から作った要約・メモリ・checkpointを経由する迂回再利用を止める。

同意撤回は、適法に保存している元の配送記録を全て直ちに削除する要求と同義ではない。削除請求、契約上の保持、法令上の保全は別に判定する。停止可能な処理の失効反映と、物理削除の完了を別に表示する。 「以後の利用を停止しました」は抑止の確認時だけ、「削除処理中」は物理削除の確認前に表示する。削除完了は§8.2で確認できた対象に限定する。

取消判定と実送出の競合、開始直前の中断、後日の復旧は既存S1に関係する。本章はゼロ競合を証明済みとしない。少なくとも現在の失効が判明した経路は新規実行せず、未開始要求を止める。直前再検査と短い開始資格、停止・照会の具体方式は13のX01〜06と整合させる。法的根拠がなくなった後も一律に送信できる免責条項は置かない。

「開始受理」は、承認された個別操作の権限等を確認し、送信開始を内部で受け付けた記録で、実送出や外部受付の証拠ではない。キュー投入、task全体、大量の事前資格発行を開始受理にしない。暫定採用した取消P方針でも、開始受理済みの操作がまだ物理送出前であり、取消受付後に送られる競合があり得ることを利用前と操作承認時に説明する。取消受付を遅らせて開始を先取りする設計は採らない。

法的根拠失効が判明した後に、通常取消の非保証を理由として可能な抑止を放置しない。停止・照会は許可された範囲で行い、全面取消を別accountや再認証で迂回しない。照会不能なら理由と利用者による確認方法を示す。法定の事故報告・本人通知の判定は§7.1の事故判断担当が通常の対応枠や照合結果を待たずに行う。通知・請求の法的効力と製品のcommit時点が常に一致するとは断定せず、残る法的当てはめは08のU03で確認する。

## 6. 実行点ごとの認可差分と既定拒否

共通判定は`workspace → actor/委任 → sourceの現ACL → purpose → 有効な根拠と必要当事者 → 出力先/宛先 → 保持条件`の順に評価する。外部操作には既存grant、snapshot、承認、account、epoch、fenceも必要。権限があることと法的根拠があることの両方を満たす。

| 実行点 | 追加検査と拒否時の動作 |
|---|---|
| serverの取得・context作成 | 許可されたsourceのID・版・履歴範囲を確定。会社全体のDBをrunnerへ渡さない。必要な当事者、目的、根拠を満たせないsourceを除外。分離不能なら処理保留 |
| runnerの国内AI入力 | 実際の入力manifestとcontext認可証跡を照合し、現ACLと根拠epochを再確認。失効・変更・不一致ならモデルを呼ばない。Botメンバーシップや国内hostを根拠の代用にしない |
| 検索・メモリ読取 | 依頼者とBot双方の現scopeで絞る。利用目的、根拠、期限、source制限を検査。候補や件数にも同じ制限を適用 |
| メモリ・index書込 | 将来再利用の許可、source参照、ACL、期限が揃う場合だけ保存。P03だけの一回処理をP04の永続記憶にしない |
| 出力公開・引継ぎ | 表示直前にsourceと受領者の現権限、目的と根拠を再確認。非同期生成中に失効した結果は保留。別channelへ投稿して制限を迂回しない |
| egress gateway | 固定payloadとaccount、宛先、操作、source scope、通信秘密の提供根拠版・epochを照合。APPI条件が必要ならその確認も要求。既存03の予約・開始判定のtransactionに検査値を結び付ける |
| 外部callback・成果物取込 | 既存の署名と保存済み帰属対応を検査。受信だけで次のrunや公開を始めない。撤回後の到着物は隔離し、必要な最小照合以外へ再利用しない |
| support・backup復旧 | §7の一時権限、§8の保持と削除・制限記録を検査。復旧した古い同意、ACL、資格情報で自動再開しない |

以下のいずれかに該当する場合、当該AI利用、追加利用、公開又は提供を既定拒否する。

- 会社、source、依頼者、Bot、委任元又は受領者の帰属・現権限が不明。
- 必要な通信当事者、代理権、目的別の根拠又はその証拠が不足。
- 説明版の範囲を超える変更、撤回、期限切れ、epoch不一致がある。
- source、派生物、実入力、公開先の対応を確定できない。
- 保持期限、削除責任、必要な受領者条件が未設定のまま永続保存・外部提供しようとする。海外又は所在未確認という事実だけをこの不足と同一視せず、必要な根拠・説明の充足を個別判定する。
- 認可台帳に接続できず、現時点の許可を確認できない。

拒否は理由コードと対象操作だけを権限ある人へ返す。非権限者へchannel名、参加者、内容、件数を理由文で漏らさない。根拠のない操作を、空の成功結果や「停止確認済み」に置き換えない。通常の配送等の必要処理は登録された別根拠で判定し、任意AIの同意不足だけで無関係な配送を止めない。

<a id="ch12-s10"></a>
### 6.1 提供先・委託先の確認記録

既存の`describe_data_boundary`の説明版と、提供先ごとの確認記録を結ぶ。実装時に別の管理画面や外部サービスを必須とせず、構造化された設定と証跡参照で始める。

| 確認区分 | 保持する内容と検査 |
|---|---|
| 操作の許可 | 会社の有効化、依頼者・Bot・taskの権限、account、snapshotと個別承認。通信当事者の根拠とは別の参照 |
| 通信秘密の提供根拠 | 対象本文・metadata、source scope、受領者、目的、必要当事者、根拠版、説明版、epoch。APPI上の委託や同意だけで代用しない |
| 個人データの根拠 | 提供主体、委託・再委託・第三者・非取扱いの事実分類、27条側の根拠、外国移転があれば28条の適用根拠と、そのルートに応じた説明・措置。非個人データでも通信秘密の検査を省略しない |
| 受領者と条件 | 法人、処理・保存・保守の主体と地域、内容・metadataの閲覧者、再委託先、目的、保持、学習・広告等の独自利用、再提供、停止・削除、事故通知、確認日・版・担当・証拠ref |
| 継続監督 | 委託には必要な監督を適用。APPIの相当措置ルートは受領者が扱う間の継続確認等を別に管理し、連携解除だけで終了しない。同意ルートへ同じ義務を機械的に重ねないが、他の該当義務は残る |

外国未特定時の代替説明はAPPI上の説明方法の例外であり、通信秘密の同意範囲や提供先確認を省略する根拠ではない。受領者、目的、取扱条件まで白紙の状態では有効化しない。

本体の委託・再委託では国内保守アクセス、目的外の再利用禁止、再委託管理、事故連絡、消去確認を契約と運用で満たす。所在の実態を確認するまでは国内保証済みと表示しない。選択した外部連携は受領者の利用条件を説明し、許されない独自利用がある場合は当該データを送らない。送信後も停止・削除・結果照会と事故対応の未完事項を追跡する。

## 7. 運営者、support、鍵保持者のアクセス

会社管理者、通常support、事故対応者、DB管理者、鍵保持者を役割として区別する。初期は既存serverの認可と国内の管理アカウントで表現し、外部の権限管理サービスを必須にしない。担当者の守秘義務、訓練、異動・退職時の即時権限失効、アクセスの定期点検を運用条件にする。

| 場面 | 条件と記録 |
|---|---|
| 通常support | 本文・添付・DMを既定で閲覧不可。許可された診断metadataだけを利用。顧客の調査依頼でも他の通信当事者の情報を無条件に開示しない |
| 内容を伴う調査 | 目的、workspace、resource、担当、必要性、根拠、顧客側承認者と期限を一時権限へ固定。最大60分、延長は新承認、書出しは別権限。顧客側の適切な承認者と実行者を分け、自己承認しない。権限の確保は08 U02/U03で確認 |
| 緊急本文アクセス | 初期は非提供。緊急を理由に本文/DMを閲覧せず、本文を見ない隔離・停止と必要最小の診断だけに限定する |
| DB、host、backupの管理 | 個人別の管理認証と必要な権限だけを使う。共有rootアカウントでの恒常調査を認めない。直接DB操作・backup読取も一時権限と監査の対象。アプリのACLを迂回できる主体は運用上の信頼対象として開示する |
| 鍵保持 | host credential storeと国内brokerの境界を維持。鍵をBot、LLM、sandbox、ログへ出さない。連携の認証tokenと保存時暗号鍵は別の管理対象とする。復号可能な役割、鍵の保管・更新・失効・復旧手順を定める。鍵へのアクセスとデータアクセスの権限を分離できる範囲を明示 |

監査には担当、目的、根拠、対象ID、承認、時刻、操作、結果を残す。本文や資格情報を監査へ複写しない。通常調査は事前監査が保存できなければ拒否する。緊急時の記録も残せない経路を無記録の例外にしない。

初期は緊急本文アクセスを提供しない。単独運営では本文を読まない隔離・停止・必要な診断metadataで対処する。通常調査は当事者を覆う根拠、適切な顧客側の別人による承認、一時権限を必要とする。担当と実稼働の確保は08 U02、法的当てはめはU03へ集約する。

保存時暗号化、端末からserverへの通信保護、service identityの方式は[v0.6/08:80–83,117](../sources/v0.6/fixed/pelway-technical-docs/08-decisions-open.md)の未決を解消してから共同利用へ進む。E2EEは一律に必須としない。serverと国内runnerが平文を扱う信頼モデルを明示する。TLS、保存時暗号化、hash chainは、host管理者や鍵保持者が絶対に読めない証明ではない。別権限で保護する監査と定期的なアクセス点検を組み合わせる。

### 7.1 事故対応の担当と報告経路

実データの試験導入前に、事故判断担当、連絡窓口、不在時の代替担当と対応時間を記名して確定する。現時点は未指定であり、24時間有人対応の提供を約束しない。検知者から事故判断担当へ集約し、封じ込めと証拠保全、該当性判定、顧客・当事者・当局への連絡を担当が追跡する。

通信の秘密の漏えいについての総務省等への報告と、個人データの漏えい等についてのPPCへの報告・本人通知は別々に該当性を判定する。顧客への連絡だけで双方を完了としない。事故認知時刻、判断担当、対象事実、適用期限とその根拠、通知先、判断・連絡の履歴を記録する。通常サポート枠や取消・照合の確認待ちを理由に初動を遅らせない。具体的な報告要否・適用期限は事案と適用規定に沿って確認し、未確認の一律日数をここで作らない。

## 8. 保存、削除、バックアップ

<a id="ch12-s14"></a>
### 8.1 採用した保持方針

区分・起算点・例外・検証/見直し条件は[13 §2〜8](13-operational-defaults.md)を適用する。本文/添付/成果物は365日、メモリはsource期限内で最長365日、索引はsourceに従い独立TTLなし、生prompt/response/KVは永続0、backupの復旧対象は作成から最大14日。メモリ30日・180日ごとの全件確認やbackup30日の旧候補を現行値として残さない。

法定記録は作成方法別の1年/3年・各起算点を適用し、同意証拠の終了後365日より長い該当期限を優先する。R12/R13/R16は通常AI利用から隔離する。30日保全点検を期限延長や法定記録消去の理由にしない。公開要約は別のP05等の有効根拠と元source制限を満たす必要があり、記憶の撤回だけで元の適法な配送記録まで必ず消すとはしない。

<a id="ch12-s15"></a>
### 8.2 削除と復旧の順序

1. serverは現在の削除・制限を確定し、対象の読取、検索、再利用、公開を先に止める。
2. source参照を使い、message、添付、要約、メモリ、index、画像、checkpoint、一時fileの影響範囲を列挙する。削除、再生成、限定保全を区別する。
3. オンラインの物理削除24時間以内は選定済みの内部目標であり、実測前の対外保証にしない。失敗は担当へ上げ、利用停止を解除しない。削除確認前に完了と表示しない。
4. clientへtombstoneを配信する。オフライン端末の残存は別に表示し、次回同期で削除を先に適用する。通信できない端末の即時消去は保証しない。保持期限を端末で強制できない構成では機密cacheを有効にしない。
5. backupは期限内の限定残存として管理する。法的保全に切り替える場合は理由、対象、別の期限、閲覧条件を記録する。
6. 復旧時は認可と外部dispatchを既定停止する。復旧DBと独立して保全した削除・制限・撤回記録を先に再適用し、現ACLと根拠を再確認する。適用範囲を列挙できなければ対象scopeのAI、検索、公開、外部送信を再開しない。

削除の表示は対象別の確認状態に結び付ける。「削除完了（オンライン・索引・メモリ・端末で確認済み）」は列挙した全対象の削除証拠が揃った場合だけ使う。未同期端末があればこの一括文言を出さず、オンライン等の確認済み範囲と「未同期の端末に残っている可能性があります」を分ける。対象外の分類は省略し、確認できない対象を確認済みとしない。backupが残る場合は、採用済み保持期限と復旧時の削除再適用を詳細へ示す。backupの14日は復旧対象の上限、世代の物理消去24時間は内部目標であることを区別し、全backupまで消えたとは称さない。

独立記録の具体方式は国内の限定権限による別保存とし、復元するDBの古いsnapshotだけに依存しない。新しい外部サービスや国外backupを必須にしない。現在のDB・volume整合復旧と二重送信防止に、この削除・権限制限の再反映を追加する。採用時は定期処理と失敗通知で削除・失効・復旧後の再適用を追跡する。今回その実装や実行は行わない。

| S10 | grantと操作承認は有効だが通信秘密の提供根拠が不足 | egressで拒否。逆に根拠だけ有効でも操作承認を省略しない |
| S11 | 固定payload、account、宛先、source、根拠epochを変更 | snapshot一致又は現在の認可検査で拒否。追加promptは新承認へ |
| S12 | 外国情報未特定でも法定の代替説明等と必要な根拠が成立 | 所在不明だけを理由に一律拒否しない。ただし通信秘密の同意範囲、受領者・目的・取扱条件の確認が別に揃わなければ拒否。本体policyを緩和せず承認payloadだけ扱う |
| S13 | 根拠失効が最終検査前に確定、又は通常取消後に新規要求 | 未開始要求を拒否。最終検査後の競合はP方針の暫定採用とS1の方式・検証未完を分けて記録し、ゼロ競合合格と偽らない |
| S14 | 外部応答断、取消後成果到着、全面資格情報取消 | 結果不明を保持、自動再送なし。到着物は公開しない。限定照会不能を明示 |
| S15 | 通常support、期限切れ一時権限、管理者のDM閲覧 | 根拠と範囲がなければ拒否。延長や書出しを暗黙に許可しない |
| S16 | 緊急本文アクセスを要求、又は監査保存に失敗 | 緊急本文アクセスを拒否。通常調査の根拠・別人の適切な顧客側承認・最大60分の範囲を検査し、無記録の調査を拒否 |
| S17 | log、通知、作業画像、crash記録を確認 | prompt全文・秘密値・無許可の相手や本文なし。外部exporterやcrash自動送信なし |
| S18 | 各保持期限、削除、個別保全、物理削除失敗 | 期限と保全理由どおり処理。先に利用停止し、失敗を完了にしない。オンライン等とbackup残存を区別。未同期端末がある場合に端末を含む一括の削除完了を表示しない |
| S19 | 削除・撤回前のbackupを復元 | 再適用前はAI、検索、公開、外部dispatchを停止。削除済み内容や旧同意・ACLを復活させない |
| S20 | 台帳障害、source不明、鍵権限不足、service identity不一致 | 既定拒否。LLM、直接DB、別account、旧cacheで迂回しない |

証拠は版、構成、fixture、操作主体、source scope、期待値、実結果、拒否理由、発生順序、監査参照を残す。試験用でも実在の通信や秘密をfixtureに使わない。「許可外の出力0」は定義したfixture内の結果であり、あらゆる障害の数学的保証ではない。

<a id="ch12-s18"></a>
### 10.1 契約と責任の設計境界

本体運営は国内の法人向けホスト型チャットを基本仮定とし、通信媒介/管理主体・設備に沿って届出等を確認する。B2B/閉域だけで通信秘密や届出の適用除外としない。ソフト配布だけの場合とは分ける。自然人の私用契約は消費者契約法の追加審査が必要で、「社員が仕事に使う」だけで事業者と判定しない。

停止結果の非保証とPelwayの権限検査/安全管理/合理的抑止/報告義務を分ける。故意・重大な過失には免責・賠償上限を適用しない方針を安全側の契約提案とするが、金額・損害範囲・第三者請求/外部料金補償は未決U03で確認する。B2Bの全責任制限が一律無効という法的結論にはしない。通常過失の扱いも全面免責を自動採用しない。

濱田さんの企画上のP採用は既存顧客契約の変更合意ではない。既存契約があるなら保証変更の明示合意等を別に確認する。法的通知の到達と製品取消commitは同一と断定しない。対外意思表示/申込み等の代理行為は単なる情報検索と分けて確認する。

<a id="ch12-s19"></a>
### 10.2 個人データ・外国移転の事実分類

以下は日本法確認§5を継承する当てはめの分岐で、連携ごとの該当性はU03/U04に残す。

| 事実関係 | 必要な整理 |
|---|---|
| 国内の真の委託/再委託（目的達成に必要な範囲） | 27条5項1号の第三者非該当。一般の第三者提供同意は不要でも23・25条等の安全管理・必要な監督。独自目的の学習・広告等を勝手に委託扱いしない |
| 外国の取扱事業者へ本人同意ルート | 28条1・2項、規則17条2項。事前に外国名、制度、受領者の保護措置等を本人へ示し、外国第三者提供を認める同意。**国外委託も、27条5項だけで28条の条件を免れない** |
| 外国の受領者が相当措置を継続する体制を整備 | 28条1項の特別の外国移転同意は不要になり得るが、27条側の同意/委託等の根拠は別に必要。28条3項・規則18条の継続確認、本人への求めに応じた情報提供等。契約/DPA締結だけで運用確認を省略しない |
| PPC指定の同等水準国（現行案内はEU/英国） | 28条の外国の除外。ただし27条、目的制限、安全管理等は残る。単なる「十分そうな国」を自社判断で追加しない |
| 27条1項各号の法令等の例外 | 条文の要件に合う場合のみ。一般の業務上便利・顧客が承認しただけではこの例外にならない |
| クラウド事業者が個人データを取り扱わない | 契約上の非取扱いと適切なアクセス制御等の実態を確認。PPC FAQ7-53・12-3上、第三者提供にも委託にも当たらない場合がある。ただし23条の安全管理、外国の制度等の把握、32条の公表等は残る。promptを解析する外部AIを「学習なし」「保存なし」「TLSあり」だけで非取扱い扱いしない |
| 利用者の選択した提供を裁量なく仲介するだけ | PPC通則3-6-1の注記に沿い、提供主体が利用者側となる場合がある。Pelway/Botが送付先・範囲を自律決定し加工/再利用する構成まで機械的に同じ扱いにしない |

**外国名等が未特定の場合：** 規則17条3項・外国移転ガイドライン5-3-1は、同意時に外国を特定できない場合、未特定の事実と理由、候補国等の本人に参考となる代替情報を示す方式を認める。17条4項・5-3-2は受領者措置の情報を提供できない場合の事実・理由の説明を定める。「海外かも/自己責任」のみで足りるという意味ではない。他の義務や同意の実質が満たせるなら、不明という一点だけの一律禁止は不要。

**相当措置ルートの継続義務：** 外国移転ガイドライン6・6-1、規則18条。相当措置の実施状況とそれに影響する外国制度を定期的に確認（公式解釈は年1回程度以上等）。支障があれば必要かつ適切な措置、継続実施の確保が困難なら提供停止。提供先がデータを扱う間は継続し、連携解除だけで終えない。**有効な本人同意ルートで提供した場合に、この28条3項義務が当然に重ね掛けされるわけではない**（同ガイドライン6）。それでも23・25条等の該当義務は別に残る。

**通常運用で残すもの：** 受領法人/アカウント、データと目的、外部処理/保存/保守地域、同意又は相当措置等の根拠、委託/再委託関係、再利用・保持・削除・事故通知、アクセス制御、確認日/版/担当。29・30条の提供/受領記録は該当性に応じて作成保存する（委託等の除外、外国同意ルートの扱いを区別）。監査のために本文や秘密を無制限複製しない。

**事故と本人請求：** 26条・施行規則7～10条の報告対象等に該当すれば漏えいのおそれ段階を含む事故対応、PPC等への報告・本人通知を検討。委託元への所定の通知による受託者の報告免除はあるが「顧客責任」と書くだけでは足りない。35条の利用/提供停止請求等は要件・代替措置・通知の規定に従う。全件削除を保証する必要も、通常の取消非保証で拒絶する権利も一律には導けない。
