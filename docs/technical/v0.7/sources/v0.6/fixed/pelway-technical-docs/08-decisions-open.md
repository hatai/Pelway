## 外部レビューで明確化した実装前の判断

- 単一host/合成データの検証構成から、LAN/TLS/端末認証へ拡げる際の範囲と認証方式。今はLAN公開を設計/実装しない。
- CLI専用連携区画と認証主体/資格情報方式。host直実行やcoreの出口緩和で代用しない。
- 連携取消後の既存operationの停止/照会だけの限定権限。全面取消なら自動確認不能で人が証拠確認する。
- server側DB/添付/backupの保存時暗号化・鍵管理と、整合backup/復旧手順。現時点で暗号化済みではない。
- controllerの高権限リスクと3 runtime系統の工数。Windowsの初期試験はPodman一つを第一候補、Engineは代替とする案。
- 同一operation再承認時の提供元keyの保持期限/照会証拠と再試行資格。人の推測だけでunknownを消し新keyで再送しない。

これらは実装着手前の選択/実機検証待ちで、文書の修正完了や計画案への賛成で解消した扱いにしない。

### S1提案からそのまま採らない点

- 開始受理の記録や内部キュー投入は、外部要求を実際に送出した証拠ではない。product-s1.mdの「要求前に受理されたものを既に外部要求が出た側に分類する」という案は、そのまま採用しない。過去の受理済み要求も、送出前に遅延していた可能性を含めて制御/証明が必要。
- 開始資格の期限切れだけでは取消完了にも未送信の証拠にもしない。接続単位の独立記録で接続なしと読めるだけでは、keep-aliveや既存接続の再利用で要求が出ていない証明にはならない。要求単位の独立した送出記録により過去の送出なしを確定でき、かつ旧主体/検査済み待機処理の後発送出を拒否できる条件が成立する場合だけ、未送信の候補とする。送出前の検査記録だけを、実送出なしの証拠にはしない。具体的な証拠要件と判定方式は未決。
- 提供元でtokenを失効させることは、提供元で受理/副作用を拒否する候補であって、Pelwayから1byteも送出しないことと同じ保証ではない。提供元の即時失効だけでBの適合を証明したと扱わない。「どの方式でも不可能」といった一般命題も今回の検証済み事実にはしない。
- 連携の取消完了（将来の送出能力がないこと）と、既に送った操作の結果確定は別。取消完了を確認できても、元操作の送信中/結果不明や試行記録を消さず、タスク成功/停止の証明に代用しない。送出能力の取消完了は外部run停止の証拠ではない。止まっているへ移すには03の状態表（作業中から止まっている）およびA5に従い、対象の外部runの終了/停止を別の証拠で確認する必要がある。送信中/結果不明は該当の結果規則を維持する。
