# 07 性能・メモリ・入力品質の評価計画

測定は未実施。機材も未確認。以下の負荷・目標値は企画統合の試験仮定であり、既存見積もりや性能保証ではない。

## 比較の順番

Slintとeguiを同条件で比較する。まず3OSのIME、文字選択、NVDA/VoiceOver/Orcaで最低限の操作が成立するかを調べる。合格候補だけを製品採用の性能比較へ進める。GPUIはWindows読み上げ等の阻害が解消するまで採用候補の比較から外す。技術担当が望む参考計測を追加する場合も、工数と承認を別に取り、合格候補と混ぜない。

## 負荷と記録

| 項目 | 試験案 |
|---|---|
| 基本負荷 | 架空の5万message。和文6割・英文4割、可変高さ、長文2万字、code/link/emoji、50channel |
| ストレス負荷 | 同条件で10万message。基本と分けて記録し、DB履歴全体と同時表示windowを区別 |
| 読み方 | 先頭からスクロール、中間で新規受信、過去message編集/削除、画像遅延読込、読み上げで画面外へ移動 |
| 操作 | 長文編集、変換確定、複数message選択、承認diff、切断・再接続、30分idle |
| 環境 | OS版、CPU、GPU、RAM/VRAM、driver、runtime版、framework固定版、font、倍率、viewport、display refresh、build最適化、電源設定を記録 |
| 繰返し | 各5回の中央値・範囲、p95 frame/input latency、失敗回数。cold/warm cacheは別 |

## 指標と合格基準案

ネイティブの初期メモリ目標は300MiB以下を仮置きする。対象はGUI＋client-coreのプロセス木で、コンテナ・DB・LLMは含まない。DB・推論を隠した「アプリ全体300MiB」とは呼ばない。Discordの数値を根拠にせず、機材と表示windowを固定した後にこの目標を見直す。目標を満たせなくても無断でWebViewへ変更しない。

| 指標 | 測定・評価 |
|---|---|
| GUIメモリ | Win private working set/commit、macOS footprint、Linux PSS/RSSを別々に記録。異なるOSの数値を同一尺度として順位付けしない |
| Webメモリ | renderer、WASM、workerの範囲を示し、他tab・ブラウザ共有分の扱いを記録 |
| 全体メモリ | GUI、server、runner、gateway、DB、sandbox、LLM、Linux VMの重複しない合計と各内訳。LLM有/無を別表 |
| 描画 | 60Hz条件でframe p95 16.7ms以下を仮目標。スクリーンリーダーon/off双方、文字200%拡大、高コントラストの各条件を分けて測る |
| IME入力 | 確定Enter誤送信0、文字欠落0、caretと候補位置の誤り0を必須機能条件とする |
| 履歴・コピー | 中間挿入で読んだ位置が飛ばない、画面外を含む選択の欠落0、読み上げとfocus対象が一致 |
| 起動・再接続 | 最初の操作可能表示まで、差分同期完了まで、WASM転送/展開サイズを測定。上限値は機材決定後に設定し、未決を0にしない |
| sandbox・推論 | 起動/停止/再開時間、tokens/s、first token、context長、peak RAM/VRAMをCPU/量子化別に記録 |
| 国内境界 | 10のD試験。全体通信を観測し、許可済み連携以外へ本体データが出ないか検証 |

ローカル推論品質は、架空の指示・日本語要約・tool引数・外部文章の攻撃例で評価する。モデル出力の正しさと、強制承認・権限制御の正しさは別に試す。モデルの安全な返事だけでゲート合格にしない。
