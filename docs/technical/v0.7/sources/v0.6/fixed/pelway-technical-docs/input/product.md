## 2. 同じチャンネルに人が複数、Botが複数いる場面

台本は今までのモックと同じ #案件B（人：田中・佐藤・濱田、AI：ハル・ユイ・リク）。名前はすべて架空です。

### 2.1 依頼と受け渡し
1. 佐藤が「@ハル B社への見積もりメールの下書きを作って」と書く。タスクが「依頼済み」で作られ、担当はハル、依頼者は佐藤になる。
2. ハルが受け取ると「作業中」になる。ハルは途中で「@ユイ 単価表を確認して」と頼む。これは子タスクとして作り、親のタスクの担当はハルのまま［提案］。BotからBotへ渡すときに人の確認を挟むかは［未決］（PRD §9）。初版では、Botが作った子タスクは外に出る操作を持てないことにする［提案］。
3. 値引きの判断が必要になり、ハルが「判断待ち（判断者：濱田、論点：値引き5%を認めるか）」にする。
4. 濱田が「Aで」と返す。A案の本文の版を決定として残し、「作業中」に戻る（R10）。

### 2.2 送信承認と実行
5. ハルがメールを作り、「送信承認待ち」にする。承認のレコードには、本文・宛先・添付のハッシュと冪等キーが入る（R6、R7）。
6. 濱田が「承認して送る」を押す。実行の直前に権限を確かめ（R9）、「送信中」になる。
7. 提供元から成功が返れば「送信済み・顧客回答待ち」になる。応答が途切れたら「結果不明」になり、濱田に確認を頼む（R8）。

### 2.3 同時に操作したとき［提案］
- 濱田と田中が同時に「承認して送る」を押した場合、状態の変更は版番号つきの条件付き更新で行い、先に通った1回だけを有効にする。後の操作には「すでに承認されています」と返す。
- ハルが下書きを直している最中に濱田が承認した場合、承認は承認した時点の版に対して行う。そのあとハルの修正が保存されたら、前の承認は使えなくなる（受け入れ条件B-1）。
- 同じタスクに同時に動けるBotは1つだけにする（タスクごとの実行の権利）。権利には期限を付け、Botが落ちたら期限切れで外す。外に出る操作の途中で外れた場合は「結果不明」として扱う。

### 2.4 担当交代（受け入れ条件A）
- 人から人：田中から佐藤へ代わったら、まだ決まっていない判断待ちの判断者を付け替え、前の判断者には「担当が変わった」と出す（A-2）。
- Botから別のBot：ハルからリクへ代わったら、ハルの作業ファイルと手順の記録へのリンクを引き継ぎ欄に出す（A-3）。作業ファイルをハルの環境に置いたままにするのか、共有の保存場所に移すのかは、技術の隔離の設計で決める［要確認］。
- どちらも、引き継ぎ欄に5つの項目をそろえる（A-1）。
- 送信承認待ちのまま担当が代わった場合、承認の内容は変わらないので、承認はそのまま使える［提案］。ただし実行の直前に新しい担当の権限で確かめ直す（R9）。

### 2.5 キャンセル［要確認：PRDにない］
PRD §5の図にはキャンセルがありません。技術文書では次の案で設計し、状態を足すかどうかは濱田さんの確認待ちとして記録してください。
- 案：10番目の状態として「取り消し」を足す。依頼済み、作業中、判断待ち、送信承認待ち、止まっている、結果不明からだけ取り消せる。
- 送信中は取り消せない。外部への呼び出しを途中で止めても、送れたかどうかが分からなくなるからです。結果が出てから扱います。
- 送信済み・顧客回答待ちのあとの「取り消し」は、送ったメールを取り消すことではありません。送った後の取り消しや訂正の扱いは［未決］（PRD §9）のままです。
- 取り消したとき、Botの実行中の手順は止める。Botが作った子タスクも取り消す。誰が取り消せるか（依頼者、担当、管理者）は［要確認］。

### 2.6 再開（受け入れ条件C）
- Botの実行環境が落ちても、手順のどこまで済んだかと、決定・承認の記録はPelwayの側に残す。Botの環境の中だけに置かない（C-1）。
- 再開すると、済んでいない手順から続ける。済んだ手順のうち、外に出る操作はやり直さない（C-2）。そのため、手順のログには「外に出る操作かどうか」と「冪等キー」を持たせる。
- LLMが止まったときや利用上限に届いたときは「止まっている」にし、理由を会話に1行で出す（C-4）。

## 4. ローカル構成でも省略してはいけない境界

ローカル構成は「1台のPCで動かす」という意味で、安全の仕組みを省いてよいという意味ではありません。
- **承認の確かめと送信の実行は、サーバーの側で行う。** デスクトップ版でもWeb版でも、画面から直接外部サービスを呼ばない。
- **Botの実行環境と秘密の情報を分ける。** Botの環境にAPIキーを渡さず、外に出る操作はサーバーの側の送信の仕組みを通す。
- **局所試作では外部へ送らない。** 送信先は疑似のもので、通信を遮断していることを確かめる手順を持つ（技術の短期入力のとおり）。
- **監査ログは書き換えられないようにする。** 1台の中でも、追記するだけの形にする。
- **ローカルのインフラとローカルのLLMは別の話。** 外部のLLMを使うかどうかは［未決］で、使う場合は合成データだけを送る。

## 8. 企画係さんの追加依頼への対応（22:21 日本時間）

**9つの状態とキャンセル。** 9つの状態は変えません。§2.5の「取り消し」は、濱田さんが認めるまで技術文書の確定仕様に入れない案です。認められるまで、技術文書ではキャンセルを「状態」ではなく「止まっている＋理由：取り消し依頼」として仮に扱う設計を推奨します。この形なら、あとで状態を足すことになっても移行しやすいからです。

## 10. AIネイティブ連携のプロダクト要件（22:2x 日本時間、Grok Botさん経由の追加要件）
前提：今回は拡張点と契約・データモデルまで。実サービス接続・登録・実装はしない。各サービスで公式に使える連携手段（今可能／制約あり／将来案・未確認）の確認はリサーチ担当さんと技術担当さんに任せ、ここでは書かない。既存計画とPRDは変えず、要件追加として記録する。

**R21 誰が動いたかを区別する。** 発言・操作・成果物の主体は「人」「Pelway内のBot」「外部エージェント（例：利用者のPCで動くコーディングエージェント）」「外部ツール（例：監視、文書）」の4種で、画面と監査ログで見分けられる。外部エージェントは「誰の依頼で、誰の権限で動いたか」を必ず持ち、それ自体は権限を持たない［提案］。

**R22 1つのタスクに複数の実行をぶら下げる。** タスク（人が見る仕事の単位）＞実行（外部へ渡した1回の仕事。再試行や引継ぎで増える）＞成果物（差分・ファイル・調査メモ・ログ抜粋）の関係にする。タスクの状態は9つのまま。外部の実行の状態は9状態に対応付けて表示し、新しい状態を増やさない［提案］。

| 外部の実行で起きたこと | タスクの表示 |
|---|---|
| 渡した・動いている | 作業中 |
| 人の判断が要る（差分の確認など） | 判断待ち |
| 外へ出る操作の承認が要る | 送信承認待ち（R2〜R5をそのまま適用） |
| 失敗した | 止まっている（理由付き） |
| 外部の結果が確認できない（再接続中だけでは該当しない） | 結果不明（自動で送り直さない） |
| 成果物が届き、人が確認した | 完了 |

**R23 外部から届いた内容は「指示」ではなく「資料」。** 外部エージェントの出力、監視アラート、文書、ログに書かれた指示で、Pelwayのタスク作成・送信・権限変更をしない。画面では「外部から届いた内容」と明示する［提案］。

**R24 ツールを足しても権限は広がらない。** 連携を足すと「できる操作の候補」が増えるだけで、使えるのは管理者が有効にし、Botの役割で許した範囲だけ。連携は初期状態で無効。※国内未確認の連携を使えなくする扱いは§11で撤回［提案］。

**R25 届く順番が乱れても同じ結果。** 外部からの進捗・成果物は重複・順不同・再接続後の再送がありうる前提で、同じ通知を2回受けても表示と監査ログが二重にならず、重複は除外して現在の状態を保つ。古い進捗が新しい状態を上書きしない［提案］。

### 10.1 将来の例（#案件B、架空名）

## 11. 最新の差分（22:25〜22:30 日本時間、濱田さんの修正をGrok Botさん経由で受けて）
§8の「ツール」、R24、T21のうち「国内未確認の連携は使えない」とした部分を、この節で上書きします。既存計画とPRDは変えません。

**責任の分け方。** 国内限定はPelway本体（AI処理、保存、ログ、バックアップ、依存OSSが既定で行う通信）にだけかける。利用者が選ぶ外部連携（コーディングエージェント、監視、文書などのツール）は、利用者の責任で使える。
- 外部連携は初期状態ではオフ。権限を持つ利用者か管理者が、連携ごとに明示して有効にする。
- 有効にする画面には、送り先、送るデータ、国外で処理・保存されうるか（分からなければ「未確認」）、責任が利用者側にあることを出す。国内かどうか分からないという理由だけで、有効にするボタンを消すことはしない。
- 有効にしても、通常の操作権限、外へ出る操作ごとの承認（R2〜R5）、監査ログ、秘密情報の管理は省かない。外部から届いた内容は資料として扱い（R23）、連携を足しても権限は広がらない（R24の前半）はそのまま。
- 本体の推論を、外部サービス経由で黙って国外へ切り替えることはしない（T14は維持）。
- 国外の端末と持ち出し（R20）、外部メール（R18）は今回の変更に含めない。外部メールを同じ扱いにするかは未決のまま。

**連携先は例であり、限定しない。** 4つのサービスは設計を確かめるための例で、対象の固定リストではない。プロダクト要件は「主体の種類」「タスク＞実行＞成果物」「承認」「有効化・取消」という共通の形で書き、サービス名に依存させない。§10.1の例も同じ扱い。

**将来のリージョン。** 今は日本だけ。保存先、AI処理先、ログとバックアップの置き場所、外部連携の送信方針を、それぞれ日本と直接書かず、1つの「データの置き場所の方針」に結び付けておく。将来、米国・EU・日本から選べるようにする余地を残すだけで、画面、移行機能、工数は足さない。リージョンを選ぶことはデータの置き場所の指定であって、法律への適合を保証するものではない。あとで変えるときの既存データとバックアップの移し方は将来の要検討で、自動移行は約束しない。
