# 07 性能・メモリ評価計画

**まだ何も測っていない**。ここの数字は目標（仮定）で、保証ではない。

## 1. 測ること
| 指標 | 測り方 |
|---|---|
| 常駐メモリ（起動直後、チャンネル10個表示後、10万件スクロール後、30分放置後） | Windows：タスクマネージャーの「メモリ（プライベートワーキングセット）」とETW。macOS：`footprint` コマンドかInstruments。Linux：`/proc/<pid>/smaps_rollup` のPSS |
| 起動から最初の表示まで | アプリ内の計時ログ |
| スクロールのフレーム時間 | GPUIのフレーム時間、p95 |
| 入力から表示まで（IMEの確定から） | 計時ログ |
| 再接続から最新になるまで | 切断を起こして計時 |
| バックエンドのメモリ（コンテナごと） | `docker stats` / `container stats` |

## 2. 条件をそろえる
- 合成データ：チャンネル50、メッセージ10万件（日本語6割・英語4割）、長文（2万字）を含む、画像なし版とあり版。
- 同じ機械・同じ解像度・同じ倍率で、ネイティブ版・Web版（Chrome/Safari）を比べる。
- 各5回測って中央値と範囲を出す。測った人・日時・版を残す。

## 3. 目標（仮定）
- ネイティブ版：10万件の履歴で常駐メモリ 300MB以下を**目標**にする。Discordの報道の数字は根拠にしない（02 §4）。
- スクロール p95 が16.7ms以下（60fps相当）。
- 目標に届かなくても方針（Rust・非WebView）は変えず、原因を記録して改善する。

## 4. 比べるもの
- 02の検証ゲートで、GPUIとSlintを同じ合成データで比べる。
- Electron系との比較をする場合は、同じデータで動くごく小さな試作どうしでのみ比べ、他社製品の数字とは比べない。
