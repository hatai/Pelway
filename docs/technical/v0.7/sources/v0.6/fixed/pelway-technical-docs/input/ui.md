## 2. 採用案（UI担当の判断。未確定）

**採用案はSlint、比べる相手はegui。** 実機の確認試験（§5）に合格し、ライセンスの判断（§1a）が済むまでは確定の採用にしない。

- **Slintを第一候補にする理由：** 5つの候補のうち、日本語入力・アクセシビリティ・リリースの安定性の3つがそろっているのはSlintだけだから。業務アプリに必要な入力欄・リスト・ダイアログといった部品も最初から持っている。
- **Slintの不確実性：** 1つ目は、大きいリストでaccessibility機能を使うと遅くなる課題（#3867）。何万件もの履歴を持つチャットにまともに当たるので、試験で最初に確かめる。2つ目はライセンスで、条件の詳細は§1aのとおり。支出が伴う商用ライセンスを選ぶなら別の承認が要る。
- **eguiを比べる相手にする理由：** ライセンスに条件がなく、AccessKitが常に入っていて、リリースも頻繁だから。弱いところは、Linuxのfcitx5での日本語入力に未解決の課題が複数あることと、毎フレーム画面を描き直す方式なので、長い履歴の部品を自前で作る手間が大きいこと。
- **初版で採らないもの：** icedは、アクセシビリティが未対応で、業務アプリの基準（WCAG 2.2 AA相当）を満たせないため。GPUIは、Windowsでスクリーンリーダーが使えないことと、Zed専用に作られていて、外のアプリから使ったときの安定性を保証していないため。どちらも状況が変われば再評価する。
- **技術担当さんの推奨と違った場合：** 差をそのまま残し、どちらの根拠かを書く。この表は機能が公式にあるかないかの比較なので、メモリ使用量と描画速度は技術担当さんの性能評価の計画に従う。

## 3. Web版と共有するもの、共有できないもの

- **共有できるもの：** 状態の定義と移り方（プロダクト担当の9状態）、画面の文言と日英の翻訳ファイル、表示の決まり（送信中に完了の色やチェック印を出さない、結果不明に再送ボタンを置かない、AIであることを示す表示、360 CSS pxは読むだけ）、色や余白といったデザインの値、APIとイベントの型。
- **共有できないもの：** 画面の部品そのもの。Web版はブラウザの部品（HTMLの要素）を使い、アクセシビリティはブラウザに任せる。ネイティブ版はSlintかeguiの部品で作り直す。SlintにはWeb向けの出力もあるが、Web版には使わない。理由は、ブラウザの読み上げや選択・コピー・日本語入力の仕組みを使えなくなるから。
- **両方で作る部品（工数は未見積もり。0時間とは扱わない）：** メッセージの一覧（仮想スクロール）、メッセージ入力欄（日本語入力・メンション候補）、承認の画面と状態の表示、判断待ちの一覧、Botの「作業を見る」画面（静止画と手順のログ）、通知、設定画面（言語切り替え）。
- **二重に作ることの負担を減らす決まり：** 文言・状態・表示の決まりを先に1か所にまとめ、両方の画面がそこから読む。文言をどちらかの画面に直接書かない。

## 3b. 承認できる最小の幅（既存仕様の不整合。今回は決めない）

長期v0.5では360 CSS pxの画面は読むだけ、PRD作業原稿では390pxのスマホ版で承認できる。この食い違いは既存仕様の不整合として記録する。以下はUI担当の推奨案で、決定ではない。360 CSS pxを読むだけにすることは維持する。
- 390 CSS px未満は読むだけにする。
- 390 CSS px以上で承認ボタンを出せるのは、承認する内容（宛先・本文・添付の一覧）を、省略や横スクロールなしに全部表示できるときだけにする。全部表示できないときは承認ボタンを出さず、「広い画面で確認してください」と表示する。
- 承認できる最小の幅をどうするかは濱田さんの確認待ちとし、長期・PRDの記述は変えない。

## 4. 日英の切り替え・組版・入力

- 翻訳は1つの形式で持つ。候補は[Fluent](https://projectfluent.org/)（Mozillaの翻訳形式。RustとJavaScriptの両方に実装がある）。採用は技術担当さんと決める。
- 画面の言語は、OSの言語を最初の値にして、設定から切り替えられるようにする。切り替えはアプリを再起動しなくても反映する。
- 日本語と英語が混ざった文の折り返し、行の高さ、日本語の禁則処理（行頭に句読点を置かない）を試験の項目に入れる。
- 日付と時刻は日本語版も英語版も表示形式を決めておく。タイムゾーンは表示する人の設定に従う。

## 7. 国内限定の要件（2026-11-08 追加。UIの範囲）

Grok Bot経由で濱田さんから追加された必須要件「AI周りとファイルの置き場所を日本国内に限定し、国外へデータを送らない」を、UIの範囲で当てはめたもの。既存文書は変えず、設計要件の追加として記録する。以下はどれも**未検証**で、適合を保証しない。

**UIから国外へ出うる経路（棚卸し。確認は実装前）**
- **Webフォント：** 外部の配信サービス（CDN）から読み込まない。フォントはアプリとWeb版に同梱し、自分のサーバーから配る。Noto Sans JPの配布形態ごとのライセンス確認は以前からの未決のまま。
- **画像・リンクのプレビュー：** メッセージ中のURLのプレビューや外部画像を、自動で取りに行かない。取りに行くと、相手のサーバー（国外かもしれない）に利用者の情報が渡る。初期は、プレビューなしでリンクの文字だけを表示する。
- **絵文字・アイコン：** 同梱する。外部から取りに行かない。
- **UIフレームワークの通信：** Slintとeguiが、利用状況の送信（テレメトリ）や更新の確認をするかどうかは**未確認**。実装前の確認試験で通信を監視して確かめる。
- **通知：** OSの中だけで出す通知（ローカル通知）に限る。プッシュ通知はAppleやGoogleなどのサーバーを経由するので、初期は使わない。
- **クラッシュ報告と更新確認：** UI側から自動で送らない。送る場合は送信先を国内の確認済みの経路に限り、利用者がオンにしたときだけにする（技術担当さんの設計に合わせる）。

**利用者の端末側にあり、Pelwayでは止められないもの（境界として明記）**
- 日本語入力のクラウド変換候補、ブラウザやOSの翻訳・スペルチェックの機能は、設定によって入力した文字を外部へ送る可能性がある。どの製品のどの設定がそうなのかは**未確認**。Pelwayの画面からは止められないので、利用企業の端末管理の範囲として導入時の説明に書く。
- 国外にある端末からのログイン、画面の撮影、ファイルのダウンロードによる持ち出しも、利用企業側の管理の範囲。Pelway側で何を制限できるか（たとえば接続元の制限）は技術担当さんの設計に任せる。

**画面の表示（文言の案。外観は変えない）**
- 国内限定モードがオンになっていることを、設定画面と管理者画面に常に表示する。Botの作業画面にも、「この作業は国内の確認済みの経路だけを使います」と出す。
- 送り先が確認されていない通信を止めたときは、Botの作業を「止まっている」状態にし、理由を「確認されていない送り先への通信を止めました」と表示する。自動でほかの送り先に切り替えない。
- 「国内に保存」と「国外へ送らない」は意味が違うので、画面の文言でも使い分ける。確かめていないことを「国内で完結」とは書かない。

**§5の確認試験への追加**
| 試験 | 合格の条件 |
|---|---|
| 通信の監視 | アプリとWeb版の起動、メッセージ送信、Botの作業、設定変更、エラー発生の各場面で、確認済みの送り先以外への通信が0件 |
| 通信遮断時の表示 | 外への通信をすべて止めても、画面が固まらずに「止まっている」と理由が表示される。自動で別の送り先を試さない |
| 同梱の確認 | フォント・絵文字・アイコンが、ネットにつながっていない状態でも正しく表示される |

**§7への追記（2026-11-08、企画係の依頼による）**
- **ライブラリの更新・診断・クラッシュ送信：** UIフレームワーク、フォント処理、画像処理などの依存ライブラリが、実行中に自分で更新を確かめたり、診断やクラッシュの情報を外へ送ったりしないかを確かめる。SlintとeguiのどちらもUI担当は未確認で、実装前の通信監視の試験（下の表）で確かめる。アプリ自体の自動更新は初期は入れず、更新は人が配布物を入れ替える形にする。ビルド時にライブラリを取ってくる通信（crates.ioなど）は、機密データを載せない構築時の通信として実行時と分けて記録する（技術担当さんの棚卸しに合わせる）。
- **表示とコピー：** 画面に出した内容やコピーした文字は、利用者の端末の中に残る。OSのクリップボードの同期（端末どうしでクリップボードを共有する機能）を使うと、端末の外へ出る可能性がある。どのOSのどの機能が国外のサーバーを通るかは未確認。Pelwayからは止められないので、利用企業の端末管理の範囲として書く。
- **保存：** 添付ファイルを端末に保存する操作は、保存先がOSのクラウド同期フォルダ（例：iCloud DriveやOneDriveの同期フォルダ）だと端末の外へ出る可能性がある。Pelwayは保存先を選ばせるだけで、同期の有無は判定しない。保存の前に「端末に保存すると、Pelwayの国内限定の範囲から外れます」と表示する案を出す（文言は決定ではない）。
- **国外の端末：** 国外にある端末からPelwayを開くと、表示した内容はその端末に届く。これは「国内に保存」とは両立しても「国外へ送らない」とは両立しない。接続元の制限をするかどうかは技術担当さんと濱田さんの判断で、UIは制限されたときの表示（理由と問い合わせ先）だけを受け持つ。

**§3aへの追記：見積もりの根拠**
幅の根拠は、部品ごとの「状態の数」と「§5の試験項目のうち当てはまる数」の2つだけで、過去の実績はない。Web版は、ブラウザに読み上げや選択・コピー・日本語入力が備わっている分を差し引いて軽く見ている。ネイティブ版は、それを自前で確かめる分を足している。通知の幅は、技術担当さんが通知の仕組みを選ぶまで根拠が足りないので、確定の幅ではなく参考値として扱い、合計にも参考値が含まれると読む。どの値も既存の短期・中期の計画には足さない。

**§7の修正（2026-11-08 22:2x、企画係とGrok Botの指示による。上の§7の記述より優先する）**
上の§7で「利用企業の端末管理の範囲」と書いた項目（クリップボード同期、クラウド同期フォルダへの保存、国外の端末、日本語入力のクラウド変換）は、濱田さんの「国外へ送らない」要件から除外する意味ではない。**国内限定に適合とはしない。製品だけでは防げない設計境界・未保証として残す。**そのうえで、国内限定の初期構成のUIは次のようにする案。
- **国外の端末からのアクセス：** 初期構成では無効。接続元が国内の確認済みの端末・経路だと確かめられないときは、内容を表示せず「この接続元からは表示できません」と出す（接続元を確かめる方法は技術担当の設計）。
- **端末への保存（添付のダウンロード）：** 初期構成では無効。画面の中で見るだけにする。
- **コピー：** 止めない（止めても画面の撮影や手入力で持ち出せるので、止めることで安全に見せない）。代わりに、OSのクリップボード同期で端末の外へ出うることを未保証の範囲として導入時の説明に書く。
- **外部へのメール（承認後の送信を含む）：** 国内限定モードでは、宛先と配送経路が国外へ出ないことを確かめられない限り、承認画面に送信ボタンを出さない。理由は「国内限定モードでは、この宛先には送れません」と表示する。既存PRDとの不整合として記録し、例外を設けるかは濱田さんの判断。
- **UIの文言：** どの画面でも「国内で完結」「国外へ送りません」と言い切らない。表示するのは「国内限定モード：オン」と、止めた操作とその理由だけ。

## 8. 外部エージェント・外部ツール連携の表示（2026-11-08 追加。差分のみ、外観は変えない）

前提：今回は将来の連携の見せ方を決めるだけで、実接続・登録・実装はしません。状態は product.md R1 の9つを使い、外部連携のための状態は足しません。取り消しは product.md の推奨と同じく「止まっている＋理由：取り消し依頼」として仮に扱います。サービスごとの「今可能／制約あり／未確認」と「利用者が判断するための情報」（送り先、送るデータ、処理・保存の場所、国外の可能性、未確認の点）は、市場担当と技術担当の区分をそのまま表示に使い、UI側では判定しません。Claude Code、Cursor、Datadog、Google Workspaceは例であり、対象をこの4つに限りません。画面は製品名ごとに作らず、共通の連携の定義（名前、能力、送り先、送るデータ、権限）から作ります。

**最新差分（2026-11-08 22:25 の責任分界）：** Pelway本体のAI処理・保存は国内限定のままです。利用者が選ぶ外部連携は本体の国内限定とは別にし、初期はオフ、権限のある利用者・管理者が国外処理の可能性を見たうえで明示的に有効にできるようにします。この節の初版にあった「国内確認が済んでいなければ有効化・承認のボタンを出さない」は撤回します。有効にしても、通常の操作権限、個別の承認、監査、秘密管理は省きません。外部メール、国外端末、データの持ち出しは今回の対象外で、§7の扱いのまま未決です。

| 項目 | 表示の決まり［提案］ | 理由 |
|---|---|---|
| 誰の作業か | 発言・作業の主体を「人」「Pelwayのbot（AI）」「外部エージェント（AI）」の3種類で区別する。外部エージェントには、サービス名・連携の名前・有効にした管理者を出す。アイコンの色だけで区別せず、文字のラベルを付ける | 色だけに頼らない（WCAG 1.4.1）。外部エージェントがPelwayのbotと見分けられないと、責任の所在がわからなくなる |
| 状態 | 外部での進み方（キューに入った、実行中、再接続中など）は、9状態のどれかと「理由1行」で出す。例：外部実行中は「作業中（Cursorで実行中）」。重複して届いたイベントは表示に反映せず、今の状態を保つ。再接続中というだけでは状態を変えず「結果不明」にもしない（理由に「再接続中」を添えるだけ）。「結果不明」は外に出る操作の結果が確認できない場合だけ（R8） | 画面ごとに外部サービスの状態名が混ざると、判断待ちの一覧が読めなくなる |
| 完了の条件 | 外部から「完了」が届いても、成果物の取り込みと必要な人の確認が終わるまでは「完了」にしない。順序が前後したイベントや重複したイベントで表示が戻ったり、2回出たりしないようにする（表示は run の最新の確定状態だけを使う） | 完了の表示を誤ると、人が確認を飛ばしてしまう |
| 進捗 | 進み具合は、外部から届いた事実（ステップ名、最終更新の時刻）だけを出す。推測でパーセントや残り時間は出さない。最終更新から一定時間（値は技術担当の設計に合わせる）を過ぎたら「更新が途絶えています」と出す | 根拠のない進捗の数字は、信用できない表示になる |
| 成果物・差分 | 成果物（ファイル、PR、差分、ログの要約）は「作業を見る」画面にまとめ、会話には1行の要約とそこへのリンクだけを出す。差分は追加と削除を記号と色の両方で示し、行番号を付ける | 会話を長いログで埋めない。差分も色だけに頼らない |
| 外部由来の内容 | 外部から届いた文章・ログ・文書の本文には「外部由来・未確認」の帯を付け、地の文と見分けられるようにする。本文中のリンク・コマンド・指示は、押せるボタンや承認の選択肢にしない（テキストとしては表示し、コピーはできる） | 外部文書の中の指示で操作や権限が広がるのを、画面側でも防ぐ |
| 失敗 | 失敗は「止まっている」にして、理由・どこで止まったか・次に人ができること（やり直す、引き継ぐ、取り消しを依頼する）を出す。外に出る操作の途中で切れた場合は「結果不明」にし、自動で送り直すボタンは出さない（R8と同じ） | 失敗を黙って消さない。外に出る操作の二重実行を防ぐ |
| 承認画面 | 外部連携を使う承認では、この操作で使う権限・前回から増える権限・送り先・送るデータを出す。送り先が国外で処理・保存される可能性があるか、または未確認なら「Pelwayの国内限定の外です（利用者が選んだ連携）」と承認ボタンの近くに文字で出す。承認ボタンは消さないが、この表示を省略しない | 承認する人が、権限の広がりと国外送信の可能性を見てから判断できるようにする。国内限定の範囲を誤解させない |
| 再開・引継ぎ | 再開・引継ぎ・取り消し依頼は、同じタスクの中の新しい run として履歴に並べ、前の run の結果と承認は書き換えない | 誰がいつ何を決めたかを後から追えるようにする |
| 管理者の有効化・取り消し | 連携は初期状態でオフ。有効にする画面では、送り先・送るデータ・処理と保存の場所（国外の可能性、未確認の点）・責任は利用者側にあることを出し、権限のある人が明示的に確認してから有効にする。有効中の連携には、一覧と会話の主体表示に「国内限定の外」の文字ラベルを常に付ける。管理者が連携を取り消したら、進行中だった作業は一覧から消さない。外部での実行停止が確認できるまでは「止まっている（理由：停止確認中）」と出し、停止済みには見せない。停止を確認できてから理由を「連携の取り消し」に変える | 取り消しで作業が見えなくなると、何が途中だったかわからなくなる |
| アクセシビリティ | 状態が変わったら、読み上げには「状態名と理由」を1回だけ伝える（重複イベントで何度も読み上げない）。キーボードだけで、成果物の確認・承認・再開・取り消し依頼ができること | 外部イベントは頻度が高く、そのまま読み上げると使えなくなる |

§3a の工数への影響：外部連携の表示は既存の「承認・状態表示」と「作業を見る」の部品の中で扱う前提です。追加の工数はまだ見積もっていません（連携を実装する段階で見積もる）。既存の計画には足しません。

§5 の試験への追加（連携を実装する段階で実施）：重複・順序違いのイベントを流しても表示が戻らない、2回読み上げない。外部由来の本文中のリンクやコマンドが押せる部品にならない。連携の取り消し後もタスクが一覧に残り、外部の停止を確認するまで「停止確認中」のまま。再接続だけでは状態が変わらない。有効にした外部連携が「国内限定の外」と表示され、本体の画面に「国内で完結」と出ない。

**将来のリージョン（表示側の境界だけ）：** 今は日本のみです。データの所在を示す文言（「国内限定」など）は画面に直書きせず、配置・データ所在の方針から表示します。将来、米国・EUなどを選べるようにする余地を残すためで、リージョンの設定画面は今回作りません。リージョンの表示は所在の表示であり、法令への適合を示すものではないので、「準拠」「適合」とは書きません。
