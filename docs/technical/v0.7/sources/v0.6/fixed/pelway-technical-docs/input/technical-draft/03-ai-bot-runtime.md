# 03 AI Botの実行・ツール連携・隔離・承認と監査

前提（既存を維持）：長期v0.5 §6の安全条件（実行直前の権限再検査、内容/宛先/添付/アカウント変更で承認無効、結果不明で停止、成功済み操作を再実行しない、VMへ管理者キーを持ち込まない、許可外の通信を遮断）。本書はそれを**ローカル構成でどう作るか**を書く。条件は変えない。

## 1. 人と複数Botが同じチャンネルで働く前提
- Botはメンバーの一種（`member.kind = bot`）。人と同じチャンネル権限の仕組みに乗り、AIであることは表示で常に分かる（UI担当の範囲）。
- 仕事の単位は**タスク**。メッセージ（メンション）から作られ、担当者は人でもBotでもよい。担当交代（人→Bot、Bot→人、Bot→Bot）は状態を保ったまま `assignee` を変える操作で、新しい担当は**前の承認を引き継がない**（承認は内容ハッシュと承認者に結び付く）。

## 2. タスクの状態（プロダクト入力 R1・R2 に合わせる。技術側では状態を足さない）

9状態を1つのRustの列挙型（`TaskState`）で定義し、API・イベント・Web・ネイティブ・翻訳キーはここから生成する。
`requested`（依頼済み）, `working`（作業中）, `awaiting_decision`（判断待ち：判断者と論点が必須）, `awaiting_send_approval`（送信承認待ち）, `sending`（送信中）, `sent_awaiting_reply`（送信済み・顧客回答待ち。完了ではない）, `outcome_unknown`（結果不明）, `stopped`（止まっている：理由つき）, `done`（完了）。

- 移り方はPRD §5の図どおりで、移り方ごとに「きっかけ」（人の操作／Botの報告／外部の結果／時間切れ）を記録する。
- **結果不明**：自動で送り直さない。照会できる提供元なら照会結果を人に見せるが、**状態は人が「送れていた／送れていない」を選んで変える**（R8）。
- **再開**：手順（`task_steps`）の済んだところの次から。済んだ外向き操作はやり直さない（C-2）。LLMが止まった・上限に届いたら `stopped`＋理由。
- **キャンセル**：PRDに状態がないため、確定までは `stopped`＋理由「取り消し依頼」で扱う（プロダクト §8）。`sending` 中は取り消さない。ランナーはツール呼び出しの前後で取り消し依頼を確かめて止まる。

## 3. 重複実行の防止
| 仕組み | 内容 |
|---|---|
| リース | `tasks.lease_owner`, `lease_until` を `SELECT … FOR UPDATE SKIP LOCKED` で取り、ハートビートで延長。期限切れでほかのランナーが引き継げる |
| フェンシングトークン | リース取得ごとに増える番号。古い番号のランナーからの書き込み・ツール要求はゲートウェイが拒否 |
| 冪等キー | **1つの承認につき1つ**（R7）。`approval_id` から作る。ゲートウェイは同じキーの2回目を実行せず、前の結果を返す |
| 結果不明 | 応答が途切れたら自動再送しない（短期・中期の試験：20回中20回とも結果不明・自動再送0）。照会できる場合も、状態の確定は人が行う（R8）。照会手段がない連携は外部更新に使わない |

## 4. 隔離（「Botごと常時VM」との比較）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A 常時VM（Botごと） | 公開文書の想定に近い | 作業場が残る、人の同僚に近い | ローカル構成で重い。常時稼働の費用。復元の検証が大きい |
| **B（推奨）タスクごとの使い捨てコンテナ＋Botごとの作業場ボリューム** | タスク開始時に作り、終了で捨てる。ファイルは作業場ボリュームに保存 | 軽い。毎回きれいな環境。ローカルで3OSとも動く | 長時間の常駐プロセス（ブラウザのログイン状態など）は残らない |
| C ホストのOSサンドボックス（Seatbelt / bwrap+seccomp / Windowsのサンドボックス） | OpenAI Codex CLIの方式 | コンテナ不要 | OSごとに3種類の実装。ホストを触る |

**推奨はB**。理由：ローカル構成の要件、3OSで同じLinuxコンテナで済む、既存の「VM停止後に状態を復元」の条件はステップ記録＋作業場ボリュームで満たす設計にできる。**既存要件との差分**：公開 technical.md の「AI社員ごとにVM」とは違うので08に差分として記録し、決めるのは濱田さん。コンテナはカーネルを共有するため、外部の文章による指示（プロンプトインジェクション）に対する隔離はVMより弱い。ローカル試作は合成データだけなので許容するが、本番での隔離強度（microVMやgVisorなど）は未決。

サンドボックスの既定：
- ネットワーク：既定で遮断。ゲートウェイ（MCP）だけ到達可能。
- ファイル：作業場ボリュームだけ書き込み可。ホストのホームはマウントしない。
- 権限：rootなし、capabilityを外す、CPU・メモリ・時間の上限。
- 秘密：入れない。ゲートウェイが代理で使う。

## 5. ツール連携（MCP）と秘密管理
- Botが使うツールはすべて **MCPサーバー**として、**ツールゲートウェイ**の後ろに置く。Botが直接外部APIを呼ばない。
- ゲートウェイが持つもの：ツールごとの許可（Bot×チャンネル×操作）、秘密（ローカルでは暗号化ファイルかOSのキーチェーン。ホストのGUIと共有しない）、読み取り/更新の区別、更新の承認要否。
- 読み取りツールの結果は、LLMには「外部の文章」として印を付けて渡し、その文章の指示では更新操作の承認を省けない。

## 6. 外部送信の承認と監査
1. Botが送信を要求 → ゲートウェイが宛先・本文・添付・送信アカウントを正規化してハッシュを作る。
2. チャンネルに承認依頼（承認できる人の条件はプロダクト担当の権限仕様に従う）。
3. 承認はハッシュに結び付ける。内容が1文字でも変われば無効で再承認。
4. 実行直前に権限を再検査（承認者・Bot・連携の権限が取り消されていないか）。
5. 冪等キー付きで1回だけ実行。結果を `success / failed / outcome_unknown` で記録。
6. 監査ログは追記専用（`audit_events`、前の行のハッシュを含めて改ざんを検知）。誰が・いつ・何を・どの版の内容に・承認したかを残す。

## 7. LLM（国内限定の追加要件で更新。詳細は 10-domestic-only.md）
| 区分 | 扱い |
|---|---|
| 試験 | **スタブLLM**（台本どおり返す）。安全試験の再現性のため |
| 実行の既定 | **国内設置ホスト上のローカル推論**（llama.cpp 系など。候補とライセンスは市場担当の調査待ち）。品質・速度・メモリ・容量は**未測定**で、機材も未確認 |
| 外部LLM（各社API） | **国内限定モードでは無効・未承認**。推論場所・保管場所・運用アクセス・再委託・サポート経路まで一次資料と契約で確認できるまで使わない。国内リージョンの指定だけでは適合とみなさない |
- ローカルインフラ（コンテナのDB・サーバー）とローカルLLM（推論）は別のもの。
- LLMゲートウェイ：許可した提供元だけを使う。**落ちても許可外へ自動で切り替えない**。予算上限で新しい呼び出しを止める。
