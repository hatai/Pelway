# Pelway技術設計 v0.2 差分レビュー（文書のみ）

## 1. 総合判定

**条件付き賛成**（文書として。実装承認、採用確定、法的適合、国内性、性能の判断ではない）

v0.1で指摘された構造上の大部分（外部送信の経路分離、承認の固定、結果不明の扱い、外部イベントの帰属、イベントキーの統一）は本文に反映されています。ただし次版へ進む前に、取消・失効と外部呼出の競合に関する仕様の穴（V2-01）と、外部へ出る追加指示の承認要件（V2-02）を塞ぐ必要があります。

確認範囲は、提供された本文、差分、採否表、静的検査結果だけです。実行テスト、外部一次資料の再取得、製品入力・status原本の照合は行っていません。

## 3. 残る必須修正（V2）

### V2-01（重大度：高）取消・失効と外部呼出の競合
- **章節**：03「固定承認と外部副作用」手順6・7、04 `dispatch_attempts`
- **根拠**：手順6で権限・承認・epoch・取消を再検査し、手順7で `attempt_started_at` を永続化します。両者が別操作のため、検査後に失効がcommitされ、その後にattempt記録が入る競合を防ぐ条件が書かれていません。「同じDBのversion/epoch条件で順序化」は方針だけです。
- **最小修正**：
  - attempt開始の永続化を「予約行の expected epoch/version/approval_hash が一致した場合だけ更新する単一の条件付き更新」とし、0件更新なら外部未呼出として拒否記録する。
  - `dispatch_attempts` に検査時の epoch/version を保存する列を追加する。
  - attempt記録後、I/O直前に再確認するかを明記する。再確認する場合は中止時の記録（未送信と言える根拠）を定義する。再確認しない場合は「受理後の取消は送信撤回を保証しない」をD11期待値に明記する。

### V2-02（重大度：高）外部へ出る追加指示の承認要件
- **章節**：11 IntegrationPort `resume` 行、03「作業中→送信承認待ち」、08 実装前判断5
- **根拠**：`resume` は「追加指示」で、外部へ送るpayloadになります。表には承認要件がなく、08は承認粒度を未決としています。
- **最小修正**：`resume` を含む新しい外部送信payloadは、既定で新snapshotと送信承認を必要とすると明記する。未決として残すのは「承認を省略してよい条件」だけにする。

### V2-03（重大度：中）作業中の取消の遷移がない
- **章節**：03 遷移表、取消の段落
- **根拠**：取消は「新dispatchを止めて協調的取消を送る」と書かれていますが、作業中からの取消を扱う行がありません。作業中→止まっているは障害・上限・権限不足の行のみです。
- **最小修正**：作業中の取消は「元状態＋`cancel_requested_at`」の属性とし、停止確認後にのみ止まっているへ移す、という方式を一つに決めて表へ1行足す。

### V2-04（重大度：中）結果不明→送信承認待ちの扱い
- **章節**：03 遷移表 行「結果不明→送信承認待ち」と、論理操作の段落
- **根拠**：遷移行は人の判断で許可され、本文は「確証または冪等保証がなければ再試行を許可しない」としています。遷移自体を拒否するのか、承認後の予約で止めるのかが不明確です。
- **最小修正**：遷移は許可するが、予約時に未実行の確証または有効な冪等保証を再検査し、満たさなければ予約を拒否して結果不明のまま残す、と明記する。

### V2-05（重大度：中）操作種類の語彙が不一致
- **章節**：06「操作の種類」、11「業務状態と外部実行」・表示契約、04 `action_kind`
- **根拠**：06は「顧客送信／外部への受け渡し／tool読取／tool更新」、11は「顧客送信／agent委任／tool読取／tool更新」です。11の表示例は「外部への受け渡し：Cursor」です。
- **最小修正**：04の `ActionSnapshot` に固定する列挙値を一つ定め、06・11の表示名はそこから対応させる。

### V2-06（重大度：中）承認版キーと提供元キーの一意性
- **章節**：03「論理操作・固定承認・試行の関係」、04 `external_actions` / `dispatch_attempts`
- **根拠**：03は「固定承認版の処理keyは一つ」としますが、04の制約はlogical operationの一意性だけです。提供元冪等キーの一意範囲（account単位かworkspace単位か）、保持期限と失効後の扱いも書かれていません。
- **最小修正**：承認版の予約に `unique(workspace, approval_version_id)` を追加する。提供元キーは `unique(provider_account_ref, provider_idempotency_key)` などで範囲を決め、保持期限切れ時の扱いを追記する。

### V2-07（重大度：中）証拠の確度の記述
- **章節**：02「Discordの事例」、09 Discord・直接依存の節、08 静的検査の記述
- **根拠**：本文は「公開Xで独立確認した」「台帳を統合した」と書いていますが、その根拠の証拠ファイル（discord-primary-post-evidence.txt、technical-license-ledger-v0.1.md、status）はこの審査パッケージに含まれていません。私はそれらを確認できていません。
- **最小修正**：「担当記録による。本snapshot外の証拠」と表記を改め、4担当・外部の最終差分確認で証拠ファイルを同一snapshotに含める。未取得の項目は未確認として残す。

### V2-08（重大度：低）静的検査の範囲の表現
- **章節**：08「レビューと完成判定」
- **根拠**：検査結果は、内部パスの存在確認と、1件のfragment参照の確認だけです。外部リンクは検査していません。
- **最小修正**：「静的リンク検査」の表現を「内部パス存在確認と1件のアンカー確認」に限定する。

### V2-09（重大度：低）Slintライセンス表記の揺れ
- **章節**：02 Slintのライセンス比較表、09 直接依存表
- **根拠**：02の比較表は「GPLv3」、09とともに改められた見出しは「GPL-3.0-only」です。
- **最小修正**：表記を一つに統一する。

## 4. 実装前の未決として残してよい項目

以下は文書上の判断待ちとして残してよい項目です。いずれも「実装前に止められる判断」です。

- Slintの許諾の選択、固定版の同梱条文、帰属表示。濱田さんと法務の判断事項です（02・09）。
- T6の正式な期待値の変更。提供元キーの再利用を承認するかどうか（03・08）。
- 短い自然返信の確定規則。権限ある人のUI確認を初期の安全案とすることは妥当（03・04）。
- 承認粒度（新run、追加prompt、担当交代時の承認継続）（03・08）。
- gatewayからserverへの認証（サービスidentity）。本文に明示がないため、実装前に設計が必要です（01・03）。
- LAN公開、TLS、端末認証、CLI連携区画の方式、管理hostと別端末のbridge（01・11）。
- 保存時暗号化、鍵管理、整合backupの手順（04・08）。
- controllerの高権限リスク、Podmanとengineの工数比較（05）。
- 「国内限定の外」の日本語表記。意味が誤読されやすいため、英語表記（Outside Pelway's domestic-only scope）と合わせて日本語の文言を再検討する（06・11）。
- 外部メールの扱い（08・10）。
- Adapter採用試験での資格情報境界（11）。
- 外部公式仕様（Cursor、Google Workspace、Claude Code等）の現況。本パッケージの記載に依っており、今回再確認していません。実装前に必要な範囲で再確認してください。
