**S1は実際の未整合です。私のv0.3の「重大矛盾なし」「必須修正なし」は、この点について撤回します。** ただし、DBとHTTPが非原子的だから解消不能、という結論にはなりません。単一local構成で送出と取消完了を直列化する方式は候補になりますが、取消の効力発生時点を正式に確認する必要があります。

**1. 原文との不整合と競合列**

まず参照位置を訂正します。提示された長期原文では、安全条件は「§6.2」ではなく、**§6の第2項と、その後の試験説明**です。§6.2という見出し自体は市場担当の節です。

該当原文は次の二つです。

> 権限取消後に新しい外部操作を出さない。

> 権限取消の反映を確認してから外部要求を開始する試験と、既に外部要求が出た後の試験を分けます。後者を必ず取り消せるとは保証しません。

現在案では、次の実行が可能です。

1. gateway Aの権限検査と`attempt_started`更新が永続commitする。
2. Aが一回限りの開始資格を受け取るが、まだ外部要求を出していない。
3. 権限取消がcommitし、取消の反映が確認される。
4. Aが保持していた資格で、新たにHTTP要求を開始する。

これは「既に外部要求が出た後」の例外には入りません。03手順8の「受理確定後に取消がcommitされても送信撤回は保証しない」は、**まだ出していない要求まで撤回保証の対象外にしている**ため、長期原文と合いません。

一回限り資格は重複開始を抑えますが、取消後の開始を防ぐ保証とは別です。直前再検査だけでも、再検査と送出の間に同じ競合が残ります。

**2. 最小推奨案は、単一の送出主体による送出と取消完了の直列化**

既存単一local構成に限り、次を方式候補として推奨します。

- 外部要求を実際に送出できる主体を一つに限定する。開始資格だけを持った別実行が、後から独立して送出できる構造を残さない。
- 取消要求を永続記録し、その時点から新しい開始受理を拒否する。表示は「取消要求済み・完了未確認」とする。
- 対象権限の取消完了と、最終権限検査から実際の要求送出までを、同じ排他制御で順序付ける。
- 取消側が先なら未送出要求を中止する。送出側が先なら、要求が実際に出た後に取消完了を確定する。
- 中断・停止・所有者喪失で安全を確認できなければ、送出禁止を維持し、取消完了を返さない。

ここでいう排他制御は、04の短いDB transactionとは別の送出制御です。**既存の「DB lock中に外部I/Oを行わない」を無断で変更する提案ではありません。**

また、HTTPライブラリへの登録や内部キュー投入だけで「外部要求が出た」と扱ってはいけません。そこで排他を解放し、取消完了後にバックグラウンド処理が送出できるなら、S1が再発します。送出境界と、未送出処理を確実に無効化できる条件の特定が必要です。不明なら完了を保留します。

この方式で狙える保証は、**取消完了後に対象権限で新しい要求を送出しないこと**です。ただし、これで元要件を満たすと確定できるのは、「権限取消」の効力発生が、この完了境界でよいと正式に確認された場合に限ります。従来の取消commitが既に効力発生を意味するなら、それを単なる要求記録へ読み替えることは仕様変更です。

障害等の扱いは次のとおりです。

| 条件 | 必要な扱い・保証の限界 |
|---|---|
| 送出前後のcrash | 外部結果は不明になり得る。`attempt_started`から自動再送しない。取消完了と操作結果の確定は別に扱う |
| gateway停止・応答断 | 停止したという推測で完了にしない。旧主体が後から送出できないことを確認するまで保留 |
| 再起動・交代 | 旧送出主体の停止と未送出キューの無効化を確認してから新主体を有効にする。復旧直後は送出禁止 |
| 複数gateway | 各gatewayのローカルlockだけでは成立しない。全送出を同じ主体に集約するか、旧主体の送出能力を確実に遮断する必要がある。DB fenceだけでは、資格を保持する旧主体のHTTPを止められない |
| 資格再利用 | 資格を実行主体・attemptに拘束し、再発行・再起動時の復元・別主体への移譲を禁止する。資格保持だけで取消制御を迂回できないようにする |
| 既に送出した要求 | 取消完了後に提供元へ到着・実行される可能性は残る。取戻し・副作用停止・exactly-onceは保証しない |

**送出済み要求の結果が不明でも、将来の送出能力を確実に止められれば、取消完了と結果不明は両立します。** 反対に、外部結果が判明しても、古いgatewayが後から送出できるなら取消完了にはできません。

**3. 技術で選べる部分と、正式判断が必要な部分**

同じ保証・意味の下での排他方式や内部記録の選択は、技術判断で進められます。一方、次はプロダクト担当の整理を経た濱田さんの正式仕様判断が必要です。

- 取消の効力発生を、要求受付・DB commit・送出停止確認のどこに置くか。
- 取消要求後、完了前に、競合中の要求が送出され得ることを認めるか。
- 完了までの待ち時間と、障害時に完了未確認が長期化する扱い。
- 「外部要求を出した」とする観測境界。

長期原文には、この受付と完了の契約は明記されていません。したがって、**完了を遅らせれば自動的に原文適合になる、と技術だけでは決められません。** 取消要求・既存commit以後の送出を許さない意味が必要なら、それに合わせて競合中の送出を阻止する必要があります。満たせなければ保留を続け、今回は保証緩和の例外を採りません。

代替として、直前再検査だけでは不十分です。複数gateway向けの新たな分散基盤の構築も、今回の最小案には含めません。
