全体として、国内本体と利用者選択連携の分離、外部副作用の結果不明、既存計画の保全は明確です。ただし、以下は実装前に契約を揃える必要があります。「文書不整合」と「実装前未決」を区別して、重要度順に示します。

1. **R01｜高｜実装前未決：取消・失効とdispatchの競合**
   
   **該当：**03「固定承認と外部副作用」「実行所有者、再開、引継ぎ、取消」、04「API」、10「通信policyを二つに分ける」
   
   dispatch直前の再検査と、DBでのdispatch確保は記載されていますが、取消・grant失効との直列化条件がありません。検査後に取消が確定し、古い検査結果のままdispatchを確保すると、「取消要求を記録し新dispatch禁止」に反します。fencing tokenだけではこの競合を防げません。
   
   **最小修正：**dispatch確保と取消・失効について、同じロックまたは条件付き更新で順序を確定すると明記してください。確保済み操作については外部送信前でも停止を保証できる範囲を定義し、境界前後の競合試験を追加します。

2. **R02｜高｜実装前未決：外部イベントのtask/runへの帰属確認**
   
   **該当：**04「永続データ」、11「共通の単位」「受信、再接続、重複、取消」
   
   署名検証と会社分離はありますが、受信payload内の`task_id`・`run_id`を、登録済み外部jobと照合する規則がありません。同じ会社内の別チャンネルのrunへ、正しく署名されたイベントが誤って関連付くと、成果物混入や状態変更が起きます。署名は送信元を確認しても、内部taskへの帰属までは保証しません。
   
   **最小修正：**submit時に保存した「workspace・integration・account・外部job/run・内部run」の対応から帰属を決定し、受信側が指定した内部IDは照合用に限定してください。不一致・未登録イベントは業務適用せず保留します。

3. **R03｜高｜実装前未決：再同期snapshotの一貫した取得点**
   
   **該当：**04「順序と再接続」
   
   snapshotとwatermarkを一緒に返すだけでは、一貫した取得点は保証されません。例えばtaskを読み取った後にtask更新がcommitし、その後のwatermarkを返すと、古いtaskを取得したまま更新イベントも飛ばせます。権限取消とsnapshot取得の競合も同様です。commit順cursorの行ロックは、この読取側の問題を解決しません。
   
   **最小修正：**全subject・権限・watermarkを同一の整合したDB読取snapshotで取得すると明記してください。分割取得するなら同じ取得点を維持する契約を定め、途中更新・権限取消の試験を加えます。

4. **R04｜高｜実装前未決：承認した入力と実際の外部agent入力の一致**
   
   **該当：**03「固定承認と外部副作用」、11「共通の単位」「IntegrationPortの能力」「三つの往復例」
   
   添付の内容hashは固定されていますが、外部agentが読む作業directory、repo、既存sessionのcontextをどこまで承認対象に含めるかがありません。承認後にdirectoryが変わる、または別taskの履歴を持つsessionを再利用すると、承認に表示されなかったデータが外部へ送られ得ます。
   
   **最小修正：**初期は不変のexport用入力一式に限定し、ファイル一覧・内容hash・sessionの所属と再利用条件をsnapshotへ結び付けてください。入力一式以外を読めないことをAdapterの利用条件にします。session再利用が必須でなければ、初期はtask間再利用を認めないだけでも足ります。

5. **R05｜高｜文書不整合：再承認後のoperation識別と重複実行防止**
   
   **該当：**03「固定承認と外部副作用」、04「external_actions」、11「受信、再接続、重複、取消」
   
   03は「承認一つに冪等キー一つ」、04はapprovalごとのexternal actionを定義する一方、11は送信した可能性のあるoperationを新IDで再submitしないとしています。「結果不明→送れていないとの人の判断→新承認」の際、同じ論理操作のID・提供元冪等キーを維持するのか不明です。新承認に伴って新キーを発行すると、遅れて完了した旧要求との二重実行を提供元が抑止できません。
   
   **最小修正：**論理operation、承認版、dispatch試行の関係を明記してください。同一payloadの結果不明解消後は提供元の契約に沿ってキーを維持し、新操作を作る場合は旧操作との関連と残存リスクを記録します。人の判断だけで未実行を技術的に確定した扱いにしないことも必要です。

6. **R06｜中｜文書不整合：inboxの重複排除キー**
   
   **該当：**04「永続データ」、11「受信、再接続、重複、取消」
   
   04はintegrationとsource event IDのunique、11は`unique(integration,account,source_event_id)`です。複数accountが同じevent IDを使う場合、04に従うと正当なイベントを重複として破棄します。全tenant表の会社分離とも制約表記を揃える必要があります。
   
   **最小修正：**両章を`workspace_id・integration_id・external_account・source_event_id`の同じ定義へ統一してください。同じキーでpayload hashが異なる場合は、通常の重複として黙って処理せず不整合として隔離します。

7. **R07｜中｜文書不整合：9状態と外部agentの往復が接続されていない**
   
   **該当：**01「仕事の往復」、03「9状態と遷移」、11「三つの往復例」
   
   03の外部送信成功は「顧客回答待ち」、そこからは「顧客の合意で完了」だけです。外部agentへsubmitし、patchを取り込み、修正依頼して次runへ進む往復を表現できません。03自身が追加対応を提案扱いとしていますが、01・11の往復を現行遷移だけで実装できるとは読めません。
   
   **最小修正：**9状態は維持し、agentのsubmit・進捗・終了をrun/operation側で表現するのか、task遷移の追加提案が必要なのかを明記してください。初期の模擬往復について、task・run・operationそれぞれの状態対応表を一つ追加すれば十分です。

8. **R08｜中｜実装前未決：連携失効後の結果照会・停止確認**
   
   **該当：**04「integrations/revoke」、10「通信policyを二つに分ける」、11「IntegrationPortの能力」
   
   revokeはbroker token利用と新dispatchを拒否する一方、外部停止・結果・保持の確認を継続するとしています。同じ資格情報を全面失効させると、cancelやobserveに認証できず確認不能になります。逆に旧tokenを残すと失効の意味が曖昧です。
   
   **最小修正：**通常操作の失効と、対象operationに限る停止・照会の扱いを分けてください。限定した照会経路を維持できないサービスでは「自動確認不能」とし、人による提供元確認へ移す契約を記載します。

9. **R09｜中｜実装前未決：添付・checkpointとDBの耐障害整合性**
   
   **該当：**01「永続化と正しさ」、03「実行所有者、再開、引継ぎ、取消」、04「artifacts / attachments」、05「試験と配布」
   
   DB状態・監査・outboxの同一transactionは明確ですが、別volume上のファイルとの確定順序がありません。DBに成功checkpointを記録した直後に未確定ファイルが失われると、再開時は成功済み手順を飛ばすのに成果物が存在しません。DBとvolumeを別時点でbackupした場合も同じ問題になります。
   
   **最小修正：**ファイルを一時領域へ保存し、内容hashと耐久化を確認してからDB参照を確定する順序を定義してください。復旧時の欠損検出と再開保留、孤立ファイルの処理を記載し、確定途中のcrashとDB/volume復旧を試験対象にします。
