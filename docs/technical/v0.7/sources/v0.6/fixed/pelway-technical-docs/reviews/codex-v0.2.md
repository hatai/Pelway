**1) 判定：文書として条件付き賛成です。実装承認ではありません。**

評価対象は提示された差分・改訂本文・採否記録・参照資料だけです。外部確認、shell操作、ファイル変更、実機試験は行っていません。外観・色・造形は評価対象外です。

**3) 残る必須修正**

**V2-01：最終検査とattempt開始を、一つの一意な受理として定義する**

- **重大度：高**
- **章節：** 03「固定承認と外部副作用」手順5〜7、04「永続データ」、01「仕事の往復」
- **根拠：** 手順6の再検査と手順7の永続化は別手順です。「同じDBのversion/epoch条件で順序化」する方針はありますが、検査成功後の失効を開始記録が拒否すること、同じ開始要求の再送で複数gateway実行が許可されないことが明記されていません。「未解決試行は最大1」だけでは、同じ試行からHTTPを二度開始することを防げません。
- **最小修正案：** 現権限・取消・epoch・fence・承認集合の検査と、予約済み→attempt_startedへの条件付き更新を**同一transaction**で確定する。transport開始資格はその更新に成功した一つの実行だけが取得し、重複要求や開始記録後の再起動では再取得できない、と明記する。commit結果や受理応答が不明なら送信せず照合へ進める。自動HTTP再試行も禁止する。
  
  04では`external_actions`のoperation一意制約と、複数履歴を持つ`dispatch_attempts`の制約を分けて記すと、この関係を誤読しにくくなります。01のsequence図もserverでの受理確定を経る形に合わせてください。

**V2-02：開始済み／結果不明の操作を、編集で承認待ちへ戻さない**

- **重大度：高**
- **章節：** 03「9状態と遷移」「論理操作・固定承認・試行の関係」
- **根拠：** 「承認後の編集は前承認を失効させ『送信承認待ち』に戻す」が無条件です。一方、同章はattempt_started後の結果保持と、unknownを別operationで迂回しないことを要求しています。編集を契機に開始済み操作を置き換える読み方が残ります。
- **最小修正案：** この編集規則をattempt_started前の未実行操作に限定する。開始後は元snapshot・operation・試行結果を保持し、編集内容は後続案として保存する。元操作がunknownなら、後続案の新ID／新承認による代替送信も解決まで保留する。既送信確定後の修正送信は、元送信との関連を持つ別操作にする。

**V2-03：DBの永続確定と、backup巻戻り後の外部操作保留を明記する**

- **重大度：高**
- **章節：** 03「固定承認と外部副作用」、04「同時更新と成果物の耐久化」、08「安全ゲート・障害注入」
- **根拠：** ファイルの耐久化は具体化されましたが、外部I/Oを許すDBの「永続化」の条件は未定義です。また、DBとvolumeが整合するbackupでも、その取得後に成功した外部操作の記録は復元されません。古いcheckpointだけを根拠に再開すると、外部側に残った副作用を再実行し得ます。
- **最小修正案：** attempt開始記録は、障害後にも保持されるDBの永続commit確認後だけ外部I/Oを許す、と定義する。具体的設定は実装前確認事項でよいです。過去backupからの復旧時は外部dispatchを既定停止し、復旧点以後の実行可能性を別の記録／提供元証拠で照合する。照合不能な操作は未実行と見なさず保留する。DB障害とbackup巻戻りも試験計画に追加する。

**V2-04：追加試験を既存の局所試作範囲へ混入させない**

- **重大度：中**
- **章節：** 08「試験の追跡表」「安全ゲート・障害注入の追跡」
- **根拠：** T13を「D1/D4/D10、合成データの局所試作」、T16を「D5/D7、同上」としています。しかしD1は本体全体、D4はsandbox／CLI区画、D7はhost全経路を含みます。提供された中期原文は、局所試作ではチャット基盤・認証・会社間分離・複数AI・VM保存復元を作らず、対象を局所経路に限定しています。
- **最小修正案：** 各行を「局所経路の部分試験」と「構成全体の試験」に分け、前者はD試験全体の合格に数えないと明記する。snapshot再同期・実権限・CLI区画等の試験は、対応機能を作る別見積もり／承認後の段階へ割り当てる。既存の局所試作へ自動追加しない。

**4) 実装前の未決として残してよい項目**

以下は、現行の停止条件を維持するなら文書完成を妨げません。

- **T6の正式採否。** 二つのkeyを分離する案は妥当。提供元の保持期限・再試行契約確認と正式仕様判断までは実装を止める。

- **承認期限・承認人数・担当交代・外部run再開の粒度。** 未定義の承認を有効扱いしないことが条件。
- **停止／照会の限定grant。** 分離できなければ自動確認不能として停止できるため、方式は未決でよい。
- **CLI区画、bridge認証、ローカル認証、LAN/TLS。** 現在の単一host合成検証から拡張しない条件で残せる。
- **暗号化・鍵管理・整合backupの具体方式、controller/runtime選定。** V2-03の復旧不変条件を先に明記し、方式決定と検証は着手前の阻害として残せる。
- **Slint等の固定版・許諾選択、rmcp移行部分、推移依存・NOTICE・SBOM。** 台帳の未確認表示は適切。固定配布物の確認完了にはしない。
- **国内host・無通信・性能・IME・読み上げの実機評価、国外端末・持出し・外部mail。** 現在の許可を広げず未決のまま維持する。
