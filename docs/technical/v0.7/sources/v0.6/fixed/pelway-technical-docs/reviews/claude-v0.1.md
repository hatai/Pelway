## 高

### R1｜高｜誤り＋未決｜01 全体図・ホスト節、04 API、10 台帳「client cache」
**複数の人が使う前提なのに、接続経路がloopbackだけになっている**
- 不整合：入口は「loopback限定」で、client cacheは「初期loopback利用」です。一方で03/04は、依頼者・判断者・承認者・送信権限者の分離、複数承認者、担当交代、会社・チャンネル分離を前提にしています。loopbackだけでは、別の人は別の端末から接続できません。
- 失敗シナリオ：承認者の分離を、1台のhost上の複数アカウントでしか試せません。LAN公開・TLS・端末認証が必要になった時点で、Origin/CSRF前提、国内端末境界（10）、cache削除方針がまとめて変わります。ローカル認証の方式（パスワード、OS利用者など）もどこにも定義がありません。
- 最小修正：01に1文を追加し、初版の利用形態を次のどちらかに明記してください。
  - (a) 単一hostでの多アカウント模擬（合成データ検証専用）
  - (b) 管理LAN公開
  
  (a)なら「LAN公開・TLS・端末認証は未決」を08の未決7項目に追加します。どちらの場合もローカル認証方式を未決として明記してください。

### R2｜高｜誤り｜03 9状態と遷移、01 仕事の往復、11 往復例、08 A5
**状態遷移表で、文書自身の主要フローを表現できない**
- 外部agentへの作業依頼は、外部送信なので「送信承認待ち→送信中→送信済み・**顧客回答待ち**」に入ります。しかし、そこから先の遷移は「顧客の合意→完了」しかありません。01の往復図にある「patchを取り込み人がdiffを判断」「修正依頼→次run」へ戻る遷移が存在しません。
- 顧客が修正を求めた場合の「送信済み・顧客回答待ち→作業中」も未定義です。
- 取消は「stopped＋停止確認中」と定義されています（03, A5）。しかし「止まっている」へ移る遷移は「作業中」と「送信中」からしかありません。判断待ち、送信承認待ち、結果不明、送信済みの状態で取消された場合の移り先がありません。
- 03は送信中の取消について「記録を消さず照会を残す」としながら、「送信済み疑いならstoppedへ遷移しない」とも書いています。この場合にtaskの状態をどうするかが書かれていません。
- 判断者の権限失効、承認期限切れのときの遷移もありません。
- 最小修正：9状態は変えず、03の表に「提案（PRD未承認）」と明記した行を追加してください。例：外部run成果の取込→判断待ち、送信済み→作業中（顧客の修正要求）、各待ち状態→止まっている（取消・権限失効）、送信中／結果不明への取消は状態を据え置きcancel_requested_atだけ記録。あわせて「外部agentへの依頼は顧客送信の状態列を使わない」か「使う」かを08の未決に追加してください。

### R3｜高｜未決（文書内の制約が衝突）｜11 local bridge・CLI、01 全体図 AD、05 network、03 隔離
**ローカルCLI agentを置ける実行区画がない**
- Claude Code CLIなどは、提供元への外向き通信と、任意のshell・ファイル操作の両方を必要とします。
  - task sandboxは「外部出口なし」なので動きません。
  - hostで直接動かすと、DB volume、秘密、host homeへ届く可能性があります。11の「作業directoryを限定」は、agentによるコマンド実行には効きません。
  - 01のADは「APP（外向き既定拒否）」の外に描かれていますが、CLIの実行権限の範囲が書かれていません。
- 「本人のCLIログインをBotへ複製しない」としていますが、代わりにどの資格情報で動かすのかも書かれていません。
- 最小修正：11に「CLI型agentはhost直実行しない。Pelway本体のvolume・秘密に届かない専用の連携実行区画（出口は当該提供元だけ）で動かし、承認済みのexport artifactだけを渡す」という制約を1行加えてください。資格情報の主体は未決として08に追加します。実装範囲は増えません。

### R4｜高〜中｜未決｜01 AD・GW、03 秘密、05 外部出口、10 policy
**Adapterの信頼区分と、資格情報の流れが定義されていない**
- 秘密はgatewayのbrokerにあります。しかし実際に外部を呼ぶのはAdapterで、05では「gatewayから許可済みAdapterへの別出口」とされています。tokenがどの形でAdapterへ渡るのか、API path・data制限（10が「application gatewayでも確認」と書いている点）をgatewayとAdapterのどちらで強制するのかが不明です。
- 失敗シナリオ：Adapterが提供元のhostname全体への出口とrefresh tokenを持つと、hostname単位の許可だけになります。そうなると、固定payload以外も送れてしまいます。
- 最小修正：01または11に次の3点を明記してください。
  - Adapterは信頼側の部品で、gatewayから固定payloadと短命のscope限定tokenだけを受け取る
  - refresh tokenはbrokerから出さない
  - 出口は連携ごとの許可リストに限る

### R6｜中｜誤り（潜在）｜04 external_actions、03 固定承認 §5、03 未決「複数承認者」
**二重dispatchを防ぐ一意キーが、承認行単位になっている**
- 一意制約は `unique(workspace, approval)` です。同じsnapshotに承認者が2人いて承認行が2つできると、dispatchが2件許されてしまいます。
- 最小修正：一意制約を `unique(workspace, action_snapshot_id)`（またはoperation_id）にしてください。approvalsはsnapshotへの多対1にします。複数承認者の規則は未決のままで構いません。

### R7｜中｜誤り｜04 evidence/revoke、10 停止、11 取消
**連携を取り消すと、「結果不明」を解消できなくなる**
- revokeするとbrokerが拒否します。そのため、`GET /v1/actions/{id}/evidence` で行う提供元への照会もできなくなります。送信中・結果不明のまま取り消した操作は、証拠なしでしか判断できません。
- さらに、GETで提供元へ外部通信が発生します。GETは安全なメソッドという前提に反し、識別子が国外へ出る送信にもなります。
- 最小修正：
  - 照会はPOSTにし、grant判定の対象であることを明記してください。
  - 「revoke後も、既存operationの読み取り照会だけを限定的に許すか」を未決として08に追加してください。許さない場合は、人が証拠なしで判断する手順になることを03に記載します。

### R8｜中｜未決｜03「送れていない→新承認」、04 冪等キー
**新しい承認で冪等キーも新しくなり、提供元側の重複防止が効かなくなる**
- 人が「送れていない」と判断したが、実際には送れていた場合を考えます。提供元が冪等キーに対応していても、新しい承認には新しいキーが付くので、二重送信になります。
- 最小修正：内容が同一のsnapshotで再承認するときは、元のoperationの冪等キーを再利用できる規則を、提供元の能力（describe_capabilities）次第の未決として記録してください。

### R9｜中｜誤り（主体が曖昧）｜01 シーケンス図、03 §4〜6・状態「送信中」
**dispatchを記録する主体と、最終検査の順序**
- 01の図ではgatewayが再確認して、そのまま外部へ送っています。一方、03 §5ではDBの条件付き更新でdispatchを確保します。gatewayにDBへの書込経路があるのか、server経由なのかが図に描かれていません（01の図ではGW→FILEだけです）。
- 状態が「送信中」に入るのはdispatchの記録時で、最終の権限検査はその後です。そのため「送信中→止まっている（呼出前の権限不足）」と「送信済みの疑い」をどう区別するかを、external_actionsの「dispatch開始」の記録時点で決める必要があります。
- 最小修正：03に順序を明記してください。条件付き更新（fence、epoch、snapshotを同時に照合）→呼出開始の記録→外部呼出。01の図にはGW↔Sのdispatch確保の矢印を追加します。

### R10｜中｜誤り｜03 子タスク・判断待ち→作業中、04 API

### R11｜中｜未決｜01 sandbox controller、05 起動構成・macOS推論
- controllerはruntimeのsocketを持つことになります。Docker Engineでは、これはhostのroot相当の権限です。controllerを置くコンテナや、その侵害時の影響範囲が書かれていません。
- Podman、Docker Engine、Apple containerの3系統でcontroller実装が必要になる工数が、見積もりにも未決にも入っていません。Windowsで「Podmanまたは Docker Engine」と二択にすると、試験の組合せも倍になります。
- macOSでhost側の推論をLinux VM内から呼ぶ経路は、VMから見るとloopbackではありません。sandboxのnetworkから到達できないことを確認する試験がありません。
- 最小修正：
  - 08の未決にcontrollerの権限と3 backendの工数を追加してください。
  - Windowsは初版で1つに絞ると記載してください。
  - 10の試験に「sandboxからhost推論のportへ到達できない」を追加してください（D4の拡張で足ります）。

### R13｜中｜未決｜04 順序と再接続
- workspaceの行ロックをcommitまで保持する方式は、channelのseq採番行や承認行とのロック順序を決めないとdeadlockの危険があります。長いtransaction（添付処理、inbox取込）があると、workspace全体が停止します。
- snapshotとwatermarkを同じDBスナップショットで取得するという条件が書かれていません。条件がないと、取りこぼしや二重適用が起きます。
- audit_eventsのprev_hashチェーンがworkspace単位なのか全体なのかも未記載です。
- 最小修正：ロック取得順（workspace行→その他）、ロック保持中に外部I/Oをしないこと、snapshot取得時の分離レベル、hash chainの範囲を04に1〜2行で追記してください。
