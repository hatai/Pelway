## 結論

**文書だけでは解消できず、正式な判断が1つ必要。** 技術で、窓を「取消完了の宣言前」に閉じ込める最小の方式は示せる。ただし、§6の2の「権限取消後」を**取消要求のcommit時点**と読むと、どの方式でも満たせない。**取消完了の宣言時点**と読めるかどうかは定義の判断なので、技術担当は決めない。

## 事実（設計に依存しないこと）

- DBのcommitと外部への送出（最初のbyte）は原子的にできない。最後の検査から送出までの間隔は小さくできるが、0にはならない。
- 厳密な読み方（取消要求のcommit後には1byteも出ない）を満たせるのは、外部提供元の側で資格を先に失効させ、提供元がその後の要求を即時に拒否すると保証している場合だけ。保証の有無と伝播時間は提供元ごとに未確認。
- 03手順8の「受理後の取消は撤回を保証しない」は今も実装済みの保証ではなく、§6の2の例外として認められてもいない（03:60と同じ）。

## 最小方式の提案（未実装・未検証）

- **M1 取消を2段階にする。** `revoke_requested` は開始受理（03手順6）と同じlockとtransactionの境界でepochを上げる。それ以降の開始受理は0件更新で拒否する。`revoke_completed` は、次の4つを全部確認した後にだけ記録する。
  - (a) epoch以降の開始受理が拒否される。
  - (b) 受理済みでtransportを開始していない全attemptが、自己中止したか、transport開始が観測された。
  - (c) egress proxyで、その操作のtransport資格の失効が反映された。
  - (d) 提供元のtoken失効に対応するAdapterでは、その失効を実行した。
- **M2 送出直前の強制点はPelwayが管理するegress proxyにする。** gatewayのnetworkはproxy以外をdenyにする（A8と同じ）。proxyは接続ごとにtransport資格とepochを検査し、接続を開いたかどうかを独立の記録として残す。gateway自身の検査だけには頼らない。
- **M3 分類と記録。** `revoke_completed` の時点でtransportを開始済みのものは「取消完了前に出た外部要求」とし、§6の2の後段（出た後の取消は保証しない）として扱う。自己中止は、proxyの独立記録で接続がないことを確認できた場合だけ未送信にする。確認できなければ `outcome_unknown` を保つ（03手順8の現行規則と矛盾しない）。

M1〜M3で保証できるのは「取消完了の宣言後には新しい外部操作が出ない」こと。取消要求から完了までの間に、proxyの検査を通った送出は残り得る。

## 正式判断が必要な点（濱田さん、プロダクト担当）

- **J1：** §6の2の「権限取消後」を「取消完了の宣言後」と定義してよいか。認めない場合、厳密な読み方は技術的に満たせない。その場合は、実外部I/Oを提供元側の即時失効を公式に確認できるAdapterだけに限るか、外部I/Oを無効のままにする。
- **J2：** 取消要求から完了までの上限時間と、完了できないとき（proxyが応答しないなど）の扱い。技術案では、完了を宣言せず「停止確認中」を保つ（A5と同じ考え方）。
- **J3：** 完了前は「取り消しました」と表示しない。U3-02の文言案と同じなので、採否はUI担当とあわせて判断してほしい。

## 実外部I/Oを有効にする前の必須条件（実装の阻害）

1. J1〜J3の判断。
2. M1〜M3の実装と、次の競合・障害試験の合格。
   - 取消と開始受理の同時実行。
   - proxy検査を通った直後の取消。
   - gatewayを各段階で停止させる。
   - proxyの停止と再起動。
   - DBの切替。
3. proxyを迂回できないことの確認（container network、DNS、IPの直接指定）。
4. Adapterごとに、提供元の資格失効の有無と伝播時間を公式仕様で確認する。

- **文書の完成条件として技術担当が求めるもの：** S1を「判断待ち」として、理由、J1〜J3、上記の必須条件と一緒に記録すること。解消済みとは書かない。
- **完成宣言をJ1の判断まで止めるか：** 企画係と濱田さんの判断。技術担当としては、外部I/Oを無効にしたまま文書を判断待ち付きで完成とすることに技術上の矛盾はない。

## product-s1.mdとの突合せ（2026-11-08追記）

方向は一致している。取消要求で以後の開始受理を拒否し、完了の宣言までは「取り消しました」と出さず、定義はJ1（product案A/B/C）として濱田さんが判断する。技術側からは次の3点を補う。

- **開始資格の期限切れは、「新しい送出がもう始まらない」ことだけを示す。送っていないことの証拠ではない。** 期限前にtransportを開始した要求は、期限後も送信中か結果不明のまま保つ。取消完了で止まっているへ移せるのは、transportを開始していないと確認できた試行だけ。
- **時計ずれ：** 期限はgatewayの時計では判定しない。proxyが、server/DBで発行した期限とepochを、proxy自身の単調時計か、DBの時刻照会で検査する。通常はproxyでの資格失効（M1(c)）で完了とする。期限は、proxyへ失効を反映できないときの予備にする。予備を使うときは「期限＋ずれの余裕」が過ぎるまで完了を宣言しない。余裕の値は実測するまで未定。
- **プロセスの停止：** 開始受理の後にgatewayが停止した場合、gateway側の記録では送ったかどうかを判定しない。proxyの独立記録に接続がなく、しかもproxyでの失効の反映か期限切れを確認できたら、未送信にできる。それ以外は結果不明として照合する。proxy自体が停止した場合も、その試行は結果不明。
- **一時停止していた処理が後から送る場合（M2の補足）：** proxyは接続を開くときだけでなく、**外部への要求ごと**に資格とepochを検査する。HTTPのkeep-aliveや接続の再利用で、検査済みの接続を後から使い回させない。そのため、TLSを終端する出口か、要求ごとの資格を検査できる方式が必要になる。方式は未決で、実外部I/Oを有効にする前の必須条件に含める。この検査も期限切れと同じく、送っていないことの証拠にはならない。
