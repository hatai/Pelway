# プロダクト担当 S1切分け（v0.5作業稿向け・提案）

2026-11-08（日本時間）。対象はClaude v0.3のS1（開始受理後・transport呼出前の取消窓）。長期§6.2（long-term-milestones.md 203行、plan-gates.md 91行）の文言は変更・緩和しない。以下はすべて提案で、採用済みではない。実装・工数・既存局所試作への試験追加は含まない。v0.4への賛成（product-v0.4.md）はその固定版に限り、S1解消を意味しない。

## 1. 結論

- 文書だけで窓をゼロにはできない（DBとHTTPは非原子、03手順8・08 S1と同じ認識）。
- ただし「取消要求」と「取消完了」を分ける二段階の定義なら、§6.2を「取消完了後に新しい外部操作を出さない」と読んで満たせる見込みがある。
- この読み方は§6.2の解釈の確定にあたる。プロダクトや企画だけで採用せず、濱田さんの明示判断を要する。判断までは実外部I/Oを有効にしない（03:60、04:100の保留を維持）。

## 2. 提案する境界（二段階）

|時点|起きること|画面での見せ方|
|---|---|---|
|取消要求commit|`cancel_requested_at`を記録。以後の開始受理（03手順6）を同じlock/transactionで全て拒否。新しいtransport開始資格は出ない|元状態のまま「取り消し依頼 · 停止確認中」（v0.4 A5どおり）|
|要求前に開始受理済みの試行|撤回を保証しない。送信中→送信済み/結果不明を照会で確定|「取消前に送信を開始していた1件」として送信中/結果不明を別表示。「取り消しました」とは出さない（U3-02、D11）|
|取消完了|technical-s1.mdのM1〜M2に従い、Pelway管理の送出口（egress proxy）で当該操作のtransport資格の失効反映を確認できた場合だけ。期限経過だけでは完了にしない。確認できなければ完了を宣言せず停止確認中を保つ（technical-s1 J2）|止まっている。結果不明の試行が残れば、その件だけ結果不明を保持|

- §6.2の「新しい外部操作」は、取消要求commitより後に開始受理された操作と定義する。要求前に開始受理された試行は「既に外部要求が出た後」の側に分類する。この分類が判断事項。
- I/O直前の自己中止検査は窓を縮める追加策として許すが、それだけで未送信の証拠にはしない（03手順8を維持）。送出口の独立記録で接続なしを確認できた場合だけ未送信とする（technical-s1 M3）。
- 23:20版では取消完了の条件に開始資格の期限経過も含めていたが、technical-s1.mdと突き合わせ、送出口での失効確認に一本化した（2026-11-08 23:22 日本時間に修正）。

## 3. 濱田さんに判断してもらう点

1. 案A（推奨）：§6.2の「権限取消後」を取消完了時点と解釈し、上の二段階で運用する。取消要求から取消完了までの間に、要求前に開始受理された送信が出る可能性を、画面と監査に明示する。
2. 案B：取消要求の時点を厳密な基準にする。その場合、文書だけでは満たせないため、実外部I/Oは提供元側で取消できる経路が確認できるまで有効にしない。
3. 案C（不採用を推奨）：開始受理後の窓を§6.2の例外として別判断で認める。保証を弱めるため。

## 4. 実外部I/Oを有効にする前の必須条件（案Aの場合）

- 上記判断の記録（08とdisposition）。
- 技術側で、送出口の迂回不能、失効反映の確認、プロセス停止・停滞時の扱いを確定し検証すること（technical-s1.mdの範囲）。完了までの上限時間と超過時の見せ方はJ2として濱田さんの判断に含める。
- 試験候補（今回は追加しない）：取消要求と開始受理の競合、開始受理後のgateway停滞が期限を超える場合、開始受理後のプロセス死亡。どれも取消要求後の新規開始受理が0件、要求前の試行の結果が隠れないことを確認する。

## 5. 文書完成と実装阻害の分け方（提案）

- 実装阻害：S1の判断と技術検証が済むまで、実外部I/Oの採用・試験は止める。
- 文書完成：二段階の定義、案A〜C、第4節の条件が08とdispositionに未決として明記されれば、プロダクト側は文書として不足なしとみなす。完成と呼ぶかどうかは企画の判断に委ね、S1を解消済みとは扱わない。
