# MVPと段階的ロードマップ

本書は提案です。日付の約束や開発開始の承認ではありません。MVP全体の範囲は[PRD](prd.md)にまとめ、ここでは検証と実装の順序を定めます。

## 1. 顧客課題を確かめる

広い候補をIT系チームとし、その中の取引先と案件を進める小規模チームを最初の検証候補にします。どちらも未検証の仮説です。主な利用者と購入判断者に、現在の依頼、AI利用、承認、引き継ぎの実例を聞きます。転記や説明し直しの負担と、独立チャットへ移る負担を比較します。顧客候補や受注実績があるとは主張しません。

## 2. 一つの業務で協業を示す

架空の依頼を使い、調査AIと資料AI、人間の依頼者と承認者が同じチャンネルで仕事を進める流れを検証します。最初は台本付きモックでも構いませんが、実際のツール操作と混同しない表示にします。相談の決定、外部送信、顧客の合意は別の状態として扱います。

## 3. 限定した実行経路を実装する

認証と会社間分離、チャンネル、役割付きAI、タスク状態、判断待ち、承認、成果物、最小限の監査ログを実装候補にします。まず一つのAIで実行経路を確認し、完成条件には複数の役割を持つAIの協業を含めます。外部への更新は承認を強制できる連携に限定します。

## 4. 変更と障害を試す

担当交代、本文や宛先の変更、同時承認、期限切れ、権限取消、VM停止、送信後の応答断、予算超過を試します。PRDの受け入れ条件を使い、成否が分からない外部操作を自動再実行しないことを確認します。結果は未実施・合格・不合格を区別して記録します。

## 5. 限定試用で範囲と料金を見直す

説明し直す回数、判断待ちの理解、引き継ぎ後の再開、LLM使用量と実行時間を測ります。導入・運用コストを含めて、既存チャットと個人向けAIを使う場合より価値があるか評価します。現時点では成功率、費用削減率、試用人数の実績を示しません。

## 後で検討するもの

Rustデスクトップ、コーディングエージェントとの連携、連携先の拡張、高度な委任や複数承認者の設定を候補にします。採用順序と納期は未決です。社内wikiと外向けQ&Aの自動生成は、このロードマップにも戻しません。

技術文書の3〜5か月という見立ては、外部基盤を使うエンジニア2〜3人の仮定に限る概算です。上記全範囲の納期を保証せず、PRDを固定してから再見積もりします。
