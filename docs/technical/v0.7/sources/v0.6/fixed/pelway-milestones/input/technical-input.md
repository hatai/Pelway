# 長期マイルストーンへの技術・原価の意見（技術担当）

- 作成: 2026-11-08（日本時間）
- 位置づけ: **提案**。数字はすべて仮定で、実測ではありません。支出・アカウント作成・公開は行っていません。
- 前提にした文書: `publish/docs/roadmap.md`、`publish/docs/technical.md`、`publish/docs/prd.md`
- 範囲外: 社内wiki・外向けQ&Aの自動生成。UIの判断はUI担当に任せます。

## 1. 段階ごとの技術の通過条件（提案）

roadmap.md の順序（顧客検証 → MVP → 試験導入 → 有償化 → 拡張）に、技術の確認を差し込みます。

### 段階0（顧客検証と並行）：技術の下調べ

| 項目 | 内容 |
|---|---|
| 成果物 | 下調べの結果をまとめた記録。対象は、実行環境の保存と復元、外への通信の制限、LLMの予算上限、最初の連携2〜3個の冪等性と結果照会の可否 |
| 通過条件 | (1) 選んだ実行環境で、作業場を止めて再開したとき、10回中10回ともファイルが失われない。(2) 許可していないあて先への通信が遮断されることを確認できる。(3) 予算上限に届くと、新しいLLM呼び出しが止まる。(4) 連携ごとに「冪等キーあり／結果照会あり／どちらもなし」を公式ドキュメントで確認して記録する |
| 見直し条件 | 保存と復元が安定しない場合は、別の提供元を試すか、作業場を残さない設計に変える |
| 中止条件 | 外への通信を制限できる提供元が見つからず、自前での運用も工数の仮定に収まらない場合は、実行環境の方式を濱田さんと見直す |
| 依存 | なし（顧客検証と並行できる） |
| 工数の仮定 | エンジニア1人で2〜4週 |
| 予算の仮定 | 各社の無料枠の範囲（例: E2B Hobby の一度きりの$100分。[E2B 料金](https://e2b.dev/pricing)、2026-11-08確認）。**アカウント作成と支出には濱田さんの判断が必要** |

### 段階1：MVP

| 項目 | 内容 |
|---|---|
| 成果物 | technical.md §2の構成で、PRDのMVP範囲が動くもの。障害を人為的に起こす試験の一式 |
| 通過条件 | 下の「障害試験」がすべて合格すること。ほかに、(1) 会社をまたいだデータの読み書きを試し、すべて拒否される。(2) 実行環境の中から外部ツールの鍵が見つからない（検査で確認）。(3) すべての社外操作が監査ログに残る |
| 見直し条件 | 障害試験に不合格が残る場合は、試験導入に進まない |
| 依存 | 段階0の結果、PRDの確定 |
| 工数の仮定 | エンジニア2〜3人で3〜5か月（technical.md の仮定と同じ。PRDの確定後に見積もり直す） |
| 予算の仮定 | 開発中の原価は、AI社員3人をライト区分で動かすと部分原価で月$84ほど（technical.md §9の単価と仮定から計算）。これに会社単位の固定費が加わる |

**障害試験（MVPの通過条件）**

| 試験 | 合格の基準 |
|---|---|
| 送信後に応答を途切れさせる（各連携で繰り返す） | 自動で再実行された件数が0件。すべて「結果不明」の判断待ちになる |
| 承認したあと、実行の前に権限を取り消す（依頼者、チャンネル、接続アカウントの各段階で） | 実行された件数が0件 |
| 承認したあとに送信内容や宛先を変える | すべて承認がやり直しになる |
| 同じ承認を2人が同時に押す | 実行は1回だけ |
| 実行環境を途中で止める | 最後に記録した段階から再開し、社外操作の二重実行が0件 |
| 予算の上限に届く | 新しいタスクを受け付けず、管理者に通知が届く |

### 段階2：試験導入（無償）

| 項目 | 内容 |
|---|---|
| 成果物 | 実際の使用量の記録（1タスクのトークン数、実行時間、失敗率、結果不明の件数）。脅威の洗い出しの記録 |
| 通過条件 | (1) 1タスクの実測の部分原価が分かる。(2) 実測をもとに、粗利60%を取れる料金を計算し直せる。(3) 結果不明になったタスクが、すべて人の確認で決着している |
| 見直し条件 | 1タスクの実測の部分原価が、仮定（区分ごとの部分原価をタスク数で割って約$0.066〜0.070）の2倍を超える場合は、モデルの振り分け、キャッシュ、料金の前提を見直す |
| 中止条件 | 料金の仮説の範囲で粗利が取れず、原価を下げる手段も見つからない場合は、有償化に進まない |
| 依存 | 段階1の通過、試験導入の協力先（事業側） |
| 予算の仮定 | 例として3社 × AI社員3人を標準区分で動かすと、部分原価で月$900ほどになり、これに固定費が加わる。**金額と実施には濱田さんの判断が必要** |

### 段階3：有償化

| 項目 | 内容 |
|---|---|
| 成果物 | 課金とタスク数・利用額の上限、データの保持と削除の手順、事故が起きたときの対応手順、外部によるセキュリティ診断の結果 |
| 通過条件 | (1) 上限を超えた利用が課金か停止のどちらかに必ずなる。(2) 会社の削除依頼から、決めた期限内にデータが消える。(3) 診断で重大な指摘が残っていない |
| 未確認で、この段階までに答えが必要なこと | 日本国内に限った推論や保存を求める顧客にどう応えるか（technical.md §4） |
| 依存 | 段階2の実測原価、料金の決定（事業側と濱田さん） |

### 段階4：拡張

Rustデスクトップ、連携先の追加、複数の承認者などが候補です。どの連携も、追加する前に段階0と同じ冪等性の確認と、障害試験の合格を条件にします。

## 2. 技術の直近30・60・90日（提案）

- **30日**: 段階0の下調べを計画します。調べる項目、合格の基準、無料枠で済むかを決めます。PRDの受け入れ条件から障害試験の一覧を確定します。1タスクの使用量の記録方法も決めます。
- **60日**: 濱田さんの承認があれば、段階0の下調べを実施します。実行環境の提供元を決め、最初の連携の冪等性の調査結果を出します。
- **90日**: 障害試験を自動で回せるようにします。脅威の洗い出しの初稿を作ります。顧客検証の結果を受けて、MVPを見積もり直します。

## 3. 濱田さんの判断が必要な点

- 段階0で、外部サービスのアカウントを作るか、無料枠を使うか
- 試験導入の規模と、その期間の原価を誰が負担するか
- 有償化の前に、外部のセキュリティ診断にお金をかけるか
- 開発の体制（工数の仮定は2〜3人。現在の体制は未確認）

## 4. 批判的な観点（既存の指摘から）

- 承認内容の変更、権限の取り消し、障害後の再開は検証項目です。競合との違いを確認できるまでは、独自性とは呼びません。
- 部分原価の8〜9割がLLMというのは、今回の仮定での話です。実測で置き換えるまでは、料金の根拠にしません。
