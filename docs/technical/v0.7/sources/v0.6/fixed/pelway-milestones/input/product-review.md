# 長期マイルストーン草案 v0.1 へのレビュー：プロダクト担当

2026-11-08 作成。対象は `long-term-milestones.md` の §5 P1・P2・P4 と §7 です。どれも［提案］です。

## 賛成する点

- P1 で、人間の別アカウント2つとAIの2つの役で検証すること。外部への更新を1種類の連携から始めること。単一アカウントの台本で代わりにしないこと。
- §6 の安全性の通過条件10項目。PRD §7 の受け入れ条件A〜C、技術文書の§6と食い違いはありません。

## 直してほしい点

1. **§5 P1：MVPの範囲が290時間に収まるかの線引きがない（優先度：高）**
   PRD §7 のMVPは9項目あります。週15時間の1人開発では、全部は入らない可能性が高いです。そこでP1に「削らないもの」と「P2へ回せるもの」を分けて書くことを提案します。
   - 削らないもの：メンションでの依頼、役割を持ったAI、状態を分けること、決定の固定、送信の承認、引き継ぎ欄、最小限の監査ログ、結果不明の扱い
   - P2へ回せるもの：スマホ版の4画面、「今日」の画面、進み具合の1行表示
   - ただしスマホ版を回すと、代表が外出先で承認する場面はP1では試せません。この点も書いておきます。
2. **§5 P1：通過条件にPRDの受け入れ条件を名前で書く（優先度：高）**
   「引き継ぎから次の行動を説明できる」だけでは、承認内容の変更（B）と失敗後の再開（C）が抜けて読めます。「PRD §7 の受け入れ条件A〜Cにすべて合格」と書いてください。
3. **§5 P1：価値の条件「10組以上で8組」の試験相手がいない（優先度：高）**
   P1の時点では、試験導入のチームはまだいません。10組を誰で集めるのかが、依存関係に書かれていません。案は2つです。
   - P0で協力に同意したチームのメンバーに限る。この場合は組数を減らす。
   - 組数の条件はP2に移す。P1は受け入れ条件A〜Cと安全試験だけにする。
4. **P0とP2：チーム数が合わない（優先度：中）**
   P0の通過条件は「2チーム以上が協力に同意」で、P2は「3チームで各4週間以上」です。このままだと、P1の途中でもう1チームを探す作業が見えません。P0の条件を3チームにするか、P1の依存関係に「3チーム目の募集」を足してください。
5. **§5 P1：最初の1種類の連携を、PRDの使い方の例に合わせる（優先度：中）**
   PRDの#案件Bの例は、取引先への提案を送るところが中心です。「取引先へのメール送信」を最初の候補として書くことを提案します。結果不明と二重送信の試験も、この連携で行えます。ただし、メールの連携で冪等性を確かめられるかは技術担当の確認が必要です。
6. **§7：範囲を固定する時期を書く（優先度：中）**
   30日の行に「MVPを機能別に再見積もり」とあります。90日の行に「MVPの範囲を固定し、P1の着手を判断する材料にする」を足してください。固定できなかった場合は、削る候補を出すことにします。
7. **§5 P4：拡張の候補に、PRDでMVPの外にしたものを入れる（優先度：低）**
   次の項目を、デスクトップ版などと同じく「1つずつ選ぶ候補」に入れてください。
   - 担当を指名して任せる「田中に任せる」
   - 条件付きの決定
   - AIが決定の候補を出すこと
   - 複数の承認者
   - CC
   - 「今日」の画面の作り直し
   - 翌朝に出てくる矛盾の扱い
