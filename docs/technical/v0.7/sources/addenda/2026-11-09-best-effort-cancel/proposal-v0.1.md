# 選択外部連携とベストエフォート取消：追補たたき台 v0.1

状態：企画案。未採用・担当レビュー待ち・プロ会議の反証/法務所見待ち。新方針の打診を設計案にしたもので、ユーザーの正式採用判断を代替しない。

## 1. 基準と依頼の範囲

基準は凍結v0.6の [08](../../reviews/v0.6-snapshot/pelway-technical-docs/08-decisions-open.md) のS1/J1〜J3と [11](../../reviews/v0.6-snapshot/pelway-technical-docs/11-integrations.md)。旧版、原計画、既納ZIPは変更しない。新規実装、接続、試験送信、支出、Git、利用者PC操作は行わない。現時点では実外部I/O無効を維持する。

新方針はGrok Botが事業チームで伝えた濱田さんからの検討依頼に基づく。必要データの海外送信とベストエフォート取消を検討し、ゼロ送信保証を完成条件にしない方向。全面免責や実装許可まで受けたとは扱わない。

## 2. 企画の推奨と代替

| 案 | 評価と採否案 |
|---|---|
| P：利用前説明・同意、承認済み範囲だけの外部送信、未開始処理の抑止、開始済み処理のベストエフォート取消 | 推奨。厳密なゼロ送信保証を求めない代わりに、開始境界と競合の残余リスク、権限と結果の記録を明確にする。プロ会議/担当の反証を受けて正式判断に上げる |
| Q：v0.6の厳密保証を維持 | 代替。S1の方式/検証未達の間は実外部I/O無効を維持。新打診の負担軽減にはならない |
| R：利用者責任の規約だけで自由送信・取消保証なし | 不採用を推奨。会社ルール・承認範囲・不正送信抑止・サービス側の責任は規約の一文で置換できない |

Pは旧S1を同じ要件のまま技術的に解いた案ではなく、保証契約を変える提案である。v0.6で不採用推奨だった保証緩和と異なる扱いを検討することを明示し、旧案Cを過去に採用済みと読み替えない。

## 3. 維持する境界

- 本体AI処理・保存・ログ・バックアップの国内要件は維持。外部サービスへの許可を本体の外部LLMへの自動切替や全履歴送信へ流用しない。
- 外部連携の選択/接続と、業務データを送る個別操作の承認は別。接続だけで会話、添付、repo、ログ等を同期・索引化・送信しない。
- 認証/能力確認で外部へ出るアカウント情報等は業務データと区別して事前説明する。「接続時に一切通信しない」という架空の約束はしない。
- 送信先/接続アカウント/目的/対象データ/操作/外部への委任範囲を承認時に固定。権限は会社ルール・依頼者・Bot・task・連携grant・接続アカウント・個別承認の共通部分を超えない。
- 外部読取でも検索語・文書ID・プロンプト等は送信データ。業務データを含む自動検査やログ転送を「接続確認」と呼んで除外しない。
- 範囲変更、追加prompt、resume、新run、副作用再試行は既存の新snapshot/承認規則を維持。今回、包括承認や省略ルールを追加しない。

## 4. 取消境界の最小案（技術/製品の確認前）

タスク取消、特定操作取消、連携権限の取消を区別し、それぞれの対象範囲を記録する。連携取消はその対象の未開始操作全体を抑止する。

| 場面 | 推奨する契約 |
|---|---|
| キュー/待機中で、操作ごとの開始手続に入る前 | 取消記録と開始資格判定を同じ管理側で順序付け、取消後の開始を拒否。承認済み・キュー投入済みというだけでは開始済みにしない |
| 特定の要求が開始手続に入る場合 | 対象request/attemptの識別、承認版/権限の直前確認、開始判定の記録を要する。内部の開始判定と実際のネットワーク送出は別の事実 |
| 開始判定と実送出の間に取消が競合 | 可能な限り再確認して抑止するが、開始手続に入った要求が取消後に実送出される残余リスクを明示。未送出なのに「既送信」と分類しない。契約上の開始点は正式判断待ち |
| 外部へ送った/送った可能性がある場合 | 対応能力があれば取消要求を出す。受理は停止証明ではない。送出・到着・実行・停止・保持/削除は別に扱う |
| 取消後の続き/復旧/旧処理 | 未開始の後続要求を開始しない。再開・追加prompt・自動再試行で取消を回避しない。送信の可能性がある操作は照合へ回し自動再送しない |

「開始済み」はタスク全体や長いキューへの包括資格にしない。開始記録を先に大量発行する方式は未開始処理の抑止を空洞化するので不可。直前確認後に停止した処理が後で送る問題は、Pでも残余リスクと抑止策の検討対象であり、消えたとしない。技術から最小の実現方式と限界を受け取る。未開始抑止までベストエフォートに弱める案は採らない。

## 5. 説明・同意・承認

利用開始前に、国外処理/保存の可能性・未確認点、必要送信データの範囲、開始手続と取消競合、開始済み外部送信の停止/撤回/削除を保証しないこと、外部サービスの条件を説明し、説明版/同意者/権限/時刻を残す。規約リンクだけで済ませず、操作承認画面でも対象と取消制約を確認できるようにする案。

利用者は送信権限と利用先を選択する責任を負う。一方、Pelway側の範囲外送信・表示誤認・権限検査不備等の責任まで一律免除するとは書かない。第三者/個人データや勤務先契約への適合を利用者の同意だけで満たすとはしない。法的な有効性、必要な表示と同意主体は法務所見待ち。

## 6. 最小表示・監査案

- 取消要求を受け付けた事実、未開始操作を抑止した事実、外部への停止要求の受付、実停止の確認、外部操作の結果を別項目で保持する。新しい業務状態をむやみに増やさない。
- 「送信済み」は送信証拠がある操作にだけ使う。内部開始判定だけでは送信済みにしない。
- 停止要求済みと停止確認済みを分ける。確認不能は結果不明/停止未確認のまま。タスク全体を「取り消しました」だけで覆わない。
- 未確定操作が残る場合は同じ要約行で件数と未確定内容を示し、各操作の履歴へ辿れるようにする。正確な日英文言はUI入力待ち。
- 監査はactor/権限/連携account/対象operationとattempt/承認snapshot/説明同意版/取消要求/開始判定/実送出の証拠/外部応答/照合結果を結び付ける。秘密をログへ残さず、payloadの全文を監査用途で無制限に複製しない。
- タイムアウトで「停止した」「未送信」と自動確定しない。確認待ちを人へ上げる時間と担当はJ2で正式判断する。

## 7. S1/J1〜J3の差分

| v0.6の課題 | Pを正式採用した場合の変更 | 残るもの |
|---|---|---|
| S1：取消完了後に新送出ゼロを証明できない | 厳密ゼロ送信保証を採用/完成の条件から外す要件変更。旧S1の技術的解消とは記録しない | 未開始処理抑止、開始境界、遅延処理/復旧時の抑止、誤表示防止、方式と検証 |
| J1：効力発生点/案A〜C | Pの契約、開始点、取消対象、競合残余リスクを正式判断。旧A〜Cの過去判断は上書きしない | 利用前説明・同意、会社権限と個別承認、操作別の開始判定 |
| J2：上限時間/超過時対応 | 「ゼロ送出を保証する取消完了時間」と「停止要求の処理/人へのエスカレーション時間」を分ける | 値/通知先/対応責任者/照合の終え方。未確認を完了扱いしない |
| J3：表示契約 | 厳密保証を前提にした「以降の送信なし」の文言を流用しない | 送信/停止要求/停止確認/結果不明の区別、件数、日英/読み上げ |
| 実外部I/O無効 | 本追補の採用だけでは自動解除しない | 別の実装/試験/接続許可、個別連携の仕様確認、適用される既存安全ゲート |

長期計画§6第2項等の旧保証を現行採用条件から外すなら、どの後続計画/受入項目へ追補を優先適用するかも承認記録に指定する。原本は変更しないまま、旧保証を維持したと主張して同時にPを採る矛盾を避ける。関係しない冪等性、権限、会社間分離、国内本体等は維持する。

## 8. 致命的懸念と次の確認

1. 未開始キューまで「開始済み」とする定義は不可。取消の実効性が失われる。操作単位の境界と後続要求の抑止を技術/製品で確認する。
2. 同意を理由に全履歴送信や外部agentへの無制限委任を許さない。提供元内の副作用を制約できない場合の委任範囲は、既存の読取/隔離作業/差分返却案を維持する。
3. 全面免責、第三者データ送信、会社規程との衝突についてプロ会議の法務所見を待つ。ここでは適法と断定しない。
4. ベストエフォートなら未知の結果を消して再送してよい、とはしない。重複副作用の防止は別要件。
