# UI担当のレビュー（long-term-milestones.md 草案）

2026-11-08（日本時間）。ここに書いたことは、すべて提案です。

全体として、段階の順番と、安全性の条件（§6）には賛成します。直してほしい点は次のとおりです。

1. **状態の名前が文書ごとに違う（§7 の60日の行）**：「送信中」という状態が出てきますが、PRD の状態の名前にはありません。PRD にあるのは「送信承認待ち／送信済み · 顧客回答待ち／結果不明」です。PRD に「送信中」を足すか、この文書から消すか、どちらかに揃えてください。
2. **顧客検証の段階で、理解できるかの確認方法がない（P0）**：成果物に「理解の確認の記録」を足してください。
   - **やり方**：架空の業務を使ったモックで、「判断待ち／送信済み · 顧客回答待ち／結果不明」を見せ、それぞれ何を意味するか、次に何をするかを、ヒントなしで答えてもらいます。
   - **見直しの条件**：半分以上の人が読み違えた状態があれば、その状態の名前と表示を直し、もう一度確かめます。
3. **MVPの「10組中8組」の数え方（P1）**：
   - **母数**：始めた試験のすべてに、途中でやめたものも入れます。
   - **失敗とみなすもの**：
     - 進行役に聞いた、またはヒントを受けた。
     - 次の行動を間違えた。
     - 旧版の内容のまま承認した。
     - 「結果不明」のものを再送しようとした。
     - 制限時間（開始前に決める。案は5分）を超えた。
   - **参加者の条件**：引き継ぎを受ける人は、それまでのやり取りを見ていない人にします。設計に関わった人は入れません。
4. **MVPの通過条件にアクセシビリティを足す（P1）**：主な画面が WCAG 2.2 AA を満たすことを条件にします。見るのは、コントラスト、キーボードだけでの操作、フォーカスの見え方、押せる部分が24px以上あること、状態を色だけで伝えないことです。ダークモードで群青の図形のコントラストが2.74しかない問題も、このときまでに直します。
5. **安全試験（§6の3と4）に、画面側の確認も対にする**：
   - 承認をやり直すときは、変わった項目（本文、宛先、添付、接続アカウント）を画面で強調して見せます。
   - 「結果不明」の画面には再送ボタンを出しません。試験では、参加者が再送してしまった件数が0件であることを確かめます。
6. **試験導入での承認の負担の測り方（P2）**：「毎回の承認で時間短縮が消える」かどうかを判断できるように、判断待ちになってから決まるまでの時間の中央値と、1つの仕事あたりの承認の回数を記録します。
7. **拡張（P4）でデスクトップ版を選ぶとき**：ブラウザ版と同じデザインの決まりで作れることを、着手の条件に入れてください。

工数（仮定）：MVPまでの画面設計に4〜6週、デザインの決まりの作成に約2週。これが§7の時間枠に入っているかは、事業企画係さんに確認をお願いします。
