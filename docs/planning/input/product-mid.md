# 中期マイルストーン：プロダクト設計からの入力

2026-11-08 作成。土台は長期計画v0.5とGrok Botさんのたたき台（mid-term-milestones.md v0.1）です。どれも［提案］で、時間・人数・期日は確定値ではありません。

## 1. 90日を全部準備に使う必要があるか

結論：必要はないと考えます。ただし、30日の見積もりが出てから、外への送信もアカウントも使わない「土台の試作」に限って、顧客検証と並行して進める案を推します。

| 案 | 中身 | 良い点 | 危ない点 |
|---|---|---|---|
| A. たたき台どおり | 90日まで検証と下調べだけ。P1aは91日から | 顧客の結果を見てから作れる。人の時間が分散しない | 状態の扱いや承認のやり直しの難しさが、91日以降にならないと分からない |
| B. 土台だけ並行（推奨） | 31日から、合成データ・ローカルだけで、状態の移り変わり、決定と承認の固定、結果不明で止まる仕組みを作る。送信先は偽物（実際には送らないダミー）にする | どの顧客を狙っても必ず要る部分なので、顧客検証の結果で無駄になりにくい。動く試作を面談で見せられる。受け入れ条件B・Cの難しさが早く分かる | 人間の担当が1人なら、面談と実装で時間を取り合う。面談の週を優先し、実装は空いた週だけにする |
| C. P1aを前倒し | 31日からP1aを全部始める | 早い | 顧客検証の前に、連携先やAIの役割を決めてしまう。推奨しない |

B案でも、P1a/P1bの境界は変わりません。理由は2つあります。

- B案の試作は、実データ・実アカウント・実際の送信を使いません。
- B案はP1aの一部を先に作るだけで、P1aの通過とは数えません。メール送信の連携は、技術担当さんが冪等性を確認してから、P1aで行います。

B案に着手するのは、次の3つがそろったときです。

- 30日の人時見積もりで、土台の部分が他と分けて見積もられている。
- 濱田さんが、面談の時間を削らない範囲で実装の時間を出せる。
- 新規支出ゼロのまま、ローカルで動かせる。

## 2. たたき台へのプロダクト側の追加と修正

1. **最初の2週間に、プロダクトの作業を足す。** 足すのは次の2つです。
   - 2週目：MVPの機能を分解した表。技術担当さんが4週目に見積もるための元になります。
   - 2〜3週目：モックに足す場面の指示書（「結果不明」「承認のやり直し」「送信中」）。見た目の判断はUI担当さんです。
2. **受け入れ条件A〜Cの試験一覧を前に出す。** たたき台では59〜72日ですが、4週目に初版を作ることを提案します。B案を取る場合、この一覧が土台の試作の合格基準になるからです。59〜72日には、面談の結果を反映した改訂版を作ります。
3. **面談ガイドにプロダクトの質問を入れる（2週目）。** 入れたいのは次の3つです。
   - 今、引き継ぎで何が抜けるか。
   - 承認したあとに内容が変わったとき、どうしているか。
   - 送れたかどうか分からなかったことがあるか。
   PRDの［仮説］の行を確かめるためです。
4. **73〜90日の「範囲固定」の進め方。** 面談の結果を、PRDの［仮説］の行ごとに「確かめられた／崩れた／未確認」に分けます。崩れた行に関わる機能は、P1aの範囲から外す候補にします。
5. **180日の判断材料に1つ足す。** P1aで受け入れ条件A〜Cのそれぞれがどこまで進んだか、合格・不合格・未実施で示します。

## 3. 濱田さんの判断が必要な点（追加）

- B案（土台だけ並行）を取るかどうか。取る場合、31〜90日のうち実装に回してよい週の上限。
