# 長期マイルストーン：プロダクト設計からの意見

作成：プロダクト設計係（2026-11-08）。この文書は事業企画係に渡す材料です。区分は［合意済み］［提案］［濱田さんの判断が必要］の3つです。数字はどれも、検証前の仮の基準［提案］です。濱田さんが承認するまで、目標として扱いません。

## 前提［合意済み］

- 作業は会話の中で進める。AIはメンションされたときだけ話す。AIは必ずAIだと表示する。
- 社内での決定、提案の送信、顧客の合意は、別々の状態として扱う。承認した内容は添付も含めて固定し、変わったら承認をやり直す。
- 成否が分からない外部操作は、自動では再実行しない。「結果不明」として人に確認を頼む。
- wikiやQ&Aの自動生成は、範囲に入れない。見た目の判断はUI担当が行う。

## 段階ごとに、プロダクトとして出すものと通過条件

| 段階 | 期間の目安［提案］ | プロダクトとして出すもの | 通過条件［提案］ | 中止・見直しの条件［提案］ |
|---|---|---|---|---|
| 0. 顧客検証 | 0〜3か月 | 聞き取りの台本、#案件Bのモック（PC版・スマホ版、モックと明記する）、課題と仮説の一覧 | 最初の検証候補にあたるチームのPLと代表から、依頼・承認・引き継ぎの実例を集められた。「説明し直し」や「判断待ちが埋もれる」が、実例で何度も出てきた | 実例が集まらない、または困りごとが既存のチャットと個人向けAIで足りている → 対象顧客か課題を見直す |
| 1. MVP | 3〜9か月 | PRD §7の9項目。受け入れ条件A〜C（担当交代・承認内容の変更・失敗後の再開） | 受け入れ条件A〜Cがすべて合格。技術文書の故障試験（VM停止、応答断、権限取消、予算超過）で「未実施」が残っていない | 結果不明の扱いか、実行直前の許可確認を満たせない → 外部への送信機能を外して、範囲を絞り直す |
| 2. 試験導入 | 9〜15か月 | 少数のチームでの試用。監査ログを見る画面、利用量と上限の表示 | 試用チームが、Pelwayの中だけで1つの案件を最後まで回せた（依頼から送信、顧客回答待ちまで）。安全性の事故がない。事故の定義は情報セキュリティ担当と決める | 承認や送信を、Pelwayの外でやり直す運用が定着した → 承認の流れを見直す |
| 3. 有償化 | 15〜21か月 | 料金表、請求、管理者向けの権限設定 | 試用チームのうち、代表が自分の判断で払うと決めたチームがある。部分原価を料金が上回ることを、実際の利用量で確かめた | 原価が料金の参考値を上回り続ける → 料金かAIの使い方を見直す |
| 4. 拡張 | 21〜24か月以降 | Rustのデスクトップ版、連携先の追加、複数承認者・委任（「田中に任せる」など）、条件付き決定、AIの決定候補 | 有償の顧客から要望が出たものの中から、優先順位を決める | — |

## 責任者［提案］

- 段階ごとの判断：事業企画係（最終判断は濱田さん）
- 受け入れ条件と画面の流れ：プロダクト設計係
- 故障試験、原価、許可の確認：技術・コスト設計係
- 見た目と、操作のしやすさ：UI担当
- 競合と顧客の情報：市場・競合リサーチ係

## 依存関係

- MVPの受け入れ条件Cは、技術文書の§6（結果不明の扱い）が決まっていることが前提です。
- 試験導入には、利用規約、データの扱い、AIだと表示するルールの確認が必要です（情報セキュリティ・法務のプロに相談）。
- 有償化には、実際の利用量で測った原価が必要です。今の数字は部分原価で、参考値にとどまります。

## 直近のプロダクト作業［提案］

- **30日**：聞き取りの台本を作る。今あるモック（PC版・スマホ版）に、「結果不明」と「承認のやり直し」の場面を足す。この2つを足す変更は、UI担当が確認する。
- **60日**：聞き取りの結果を、PRDの［仮説］の行に反映する。受け入れ条件A〜Cを、試験の手順書にする（誰が、何を操作し、何が表示されれば合格か）。
- **90日**：MVPの範囲を固定して、技術の再見積もりに渡す。固定できなければ、その理由と、削る候補を出す。
