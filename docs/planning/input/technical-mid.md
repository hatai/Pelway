# 中期マイルストーンへの技術・原価の意見（技術担当）

- 作成: 2026-11-08（日本時間）
- 位置づけ: **提案**。時間の数字はすべて仮定で、実測ではありません。支出、アカウント作成、公開は行っていません。
- 前提: 長期計画 v0.5。P1aとP1bの安全境界は変えません。

## 1. 90日を準備だけに使う必要はあるか

**結論（提案）**: 全部を準備に使う必要はありません。3週目ごろから、顧客検証と並行して、ローカルだけで動く最小の技術試作（ここでは「P0-T2」と呼びます）を始められます。条件は、新規支出ゼロのままにできることです。ただし、人間の担当が1人なら面談と同じ時間枠を使うので、週ごとにどちらかを優先する形になります。

### 比較

| 案 | 内容 | 利点 | 問題 |
|---|---|---|---|
| A. 準備に専念する（たたき台v0.1） | 90日までは机上の調査と見積もりだけ。試作は91日以降 | 面談に時間を集中できる | 一番の技術的な不確実さ（状態の遷移、承認のやり直し、結果不明での停止）が、90日の判断の時点でまだ机上のまま。人時の見積もりの根拠も弱い |
| **B. 最小の試作を並行する（推奨）** | 3〜10週ごろに、ローカルだけで動く試作で状態遷移と障害時の振る舞いを確かめる | 90日の判断材料に実測が加わる。P1aの人時見積もりの精度が上がる | 面談と時間を取り合う。範囲が広がりやすい（下の境界で止める） |
| C. P1aを前倒しする | 30日以降にP1aそのものに着手する | 早く形になる | 顧客の検証前に作り込む危険がある。P1aには承認された費用と実装責任者が要る。推奨しない |

### 案BのP0-T2の境界（全部満たすこと）

- **データ**: 合成データだけを使う。実顧客データ、実在の取引先、実在の認証情報は使わない。
- **外部送信**: しない。メールはローカルの受信用ダミーサーバー（例: Mailpit。オープンソース）に送る。実在の宛先には届かない構成にする。
- **LLM**: 決まった応答を返す仮のLLMを使う。実際のLLM APIを使う場合は、別に支出の承認を得る。
- **環境**: 開発者のPC上のコンテナだけで動かす。クラウドのアカウントは作らない。
- **範囲**: タスクの状態遷移（受付 → 実行中 → 判断待ち → 送信中 → 送信済み／結果不明／止まっている）、承認と承認のやり直し、実行直前の権限検査、応答断の再現の4つに限る。チャットの画面、会社間の分離、複数AIの協業は作らない。
- **扱い**: P1aの通過条件のどれにも数えない。P1aに着手したら、作り直す前提にする。

### P0-T2の合格条件（提案）

- 仮のメールサーバーで応答断を20回起こし、自動の再送が0件、20回とも「結果不明」になる。
- 承認したあとに宛先か本文を変えると、20回とも承認がやり直しになる。
- 承認したあと、実行の前に権限を取り消すと、各条件5回とも実行が0件になる。
- 実際にかかった人時を記録し、P1aの人時見積もりに使う。

### 見直し・中止の条件

- 予定時間（下の仮定）の1.5倍を超えたら止めて、残りは90日の判断に持ち越す。
- 面談の実施が遅れている週は、P0-T2を止めて面談を優先する。

## 2. 最初の30日の技術（週単位、提案）

| 週 | 技術の成果物 | 人の作業 |
|---|---|---|
| 1週 | 技術下調べの計画（調べる項目、合格の基準、無料枠で済むか）。費目一覧の枠 | なし（3点の決定を待つ） |
| 2週 | メール送信の提供元2〜3候補について、冪等キーと結果照会の公式仕様の調査（出典と確認日を付ける）。P0-T2の設計メモ | 計画の確認だけ |
| 3週 | P0-T2の状態遷移と承認の部分（案Bを選んだ場合） | 実装（人時の仮定は下記） |
| 4週 | MVPの機能別の人時見積もり（P1aとP1bを分ける）。総原価の初版（提供元ごとに費目を置き換え、二重計上はしない。無料枠は条件を確認するまで計上しない） | 見積もりの確認 |

## 3. 人時の仮定（根拠と一緒に）

- **P0-T2の実装**: 20〜40人時を仮定します。根拠は、状態機械（状態とその移り方を決めた仕組み）、承認の記録、仮の連携、障害を起こす試験だけに範囲を絞り、画面を作らないことです。私の見積もりで、実績ではありません。
- **P1aの人時**: 4週の見積もりで出します。それまでは290時間を比較仮定として扱い、確定値にしません。
- **botの作業**: 調査、草案、試験手順は人の工数に数えません。実装、実行、合否の判断は人がします。

## 4. 91〜180日（たたき台v0.1への意見）

- 「P1bは180日の範囲外」に賛成です。
- 151〜180日に安全試験をまとめて行う案には反対です。安全試験は機能と一緒に作り、各月の終わりにその時点で実行できる試験を回す形にしてください。最後の月にまとめると、不合格が出たときに直す時間が残りません。
- 121〜150日のメール送信の試験は、許可したテスト宛先だけに届く構成と、送信の承認を前提にしてください。

## 5. 濱田さんの判断が必要な点（技術から）

- 案Bを選ぶ場合、3〜10週のうち、P0-T2に使ってよい人時の上限。
- 開発者のPCでコンテナを使ってよいか（会社のPCではなく、個人の環境を使う前提）。
