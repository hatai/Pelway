# スキーマ移行の運用規則（Issue #223）

`crates/pelway-db/migrations/` の SQL 移行（sqlx migrate、`sqlx::migrate!` で
バイナリに埋め込んで起動時に適用）に課す規則。移行は表の所有者（開発では
スーパーユーザー）が実行する（`src/lib.rs` の `migrate`）。

## 前リリース互換の原則

本番では移行の適用後もしばらく前リリースのコードが動く。したがって
**すべての移行は、適用直後のスキーマで前リリースのコードが動くものだけを
許可する**。レビューはこの互換を確認項目にする。

- 追加（表・列・インデックス・制約の追加、既存行への NULL 許可の緩和）は
  安全で、常にこの形で出す。
- 削除（表・列・インデックス・制約の削除、型の変更）は前リリースを壊す
  ため、直接は行わない。次項の deferred で 1 デプロイ遅らせる。
- NOT NULL の付与や列の型変更も前リリースの書き込みを壊すため、削除と
  同じ扱い（二段階）で行う: まず前リリースが書ける形のまま新しい制約を
  アプリ側で守り、前リリースが消えた後の PR で確定する。

## deferred 削除（削除を 1 デプロイ遅らせる仕組み）

削除は、スキーマとコードから外す PR と同じ PR で **deferred と印した移行**
として書き、適用を次のデプロイへ送る。

- **印の形式（Issue #223 の未決事項への決定）**: 移行ファイルを
  `migrations/deferred/` サブディレクトリに置く。sqlx の移行ソース
  （sqlx-core `migrate/source.rs` の `resolve_blocking`）はディレクトリ
  エントリを無視するため、`deferred/` の中は `sqlx::migrate!` の埋め込み
  にも実行時の適用にも現れない（`tests/migration_rules.rs` がこの挙動を
  確認する）。ファイル名は発行時の番号を避け、内容と紐づく名前にする
  （例: `deferred/drop-audit-retention.sql`）。
- **適用の仕組み**: 適用は次のデプロイ（前リリースのコードが環境から消え
  た後）の最初の PR で、`deferred/` のファイルを `migrations/` の末尾
  （その時点の最大番号 + 1）へ移動して確定する。移動だけで中身を書き
  直さない（番号は移動時に付くため、checksum の変更は起きない）。
- `deferred/` に置いたまま次のデプロイを逃したものは、その次の PR で必ず
  繰り上げる。`deferred/` に残ったファイルの数だけ「未適用の削除」が
  あることになり、放置はスキーマとコードの不一致を長引かせる。

## 改名の手順

列・表・制約などの改名は、追加と削除の組合せで 4 段階に分ける。各段階は
それぞれ前リリース互換の原則を満たす PR とする。

1. **追加**: 新しい名前の表・列を追加する（移行は追加だけ）。
2. **移行**: 既存行のデータを新しい名前へ複写する移行を足す。この時点で
   両方の名前が並存し、前リリースは旧名で書き続ける。
3. **コード切替**: アプリのコードを新名の読み書きに切り替える PR（移行
   なし、または複写の再実行を冪等に足す）。切り替え後も旧名への書き込み
   がないことを確認するまで進めない。
4. **旧の deferred 削除**: 旧名の表・列を `migrations/deferred/` の移行で
   外す（上の仕組みで次のデプロイに適用）。

## 待機中の列の制約

削除（または改名の旧側）を待っている列は、適用までの間も前リリースが
読み書きする。その間の制約:

- **NULL 許可のままにする**: 前リリースの INSERT はその列に値を出し
  続けるが、新コードは書かなくなる。NOT NULL を残すと新コードの行で
  違反するため、削除確定まで NULL 許可にしておく（NOT NULL の列は削除
  PR の前段で NULL 許可へ緩める追加移行を挟む）。
- **UNIQUE・CHECK は前リリースの書き込みを満たすものだけ残す**: 新コード
  が供給しない値に前リリースの書き込みが違反する制約は、削除確定まで
  外すか緩める。
- **デフォルトを残す**: 前リリースが列を省略した INSERT を出す場合に
  失敗しないよう、DEFAULT は削除確定まで残す。
- **外部キーは依存する側から外す**: 参照されている表・列の削除は、参照
  する側の列削除（または外部キー削除）が適用済みになってから行う。
  `deferred/` 内の移行どうしにもこの順序を保つ。
